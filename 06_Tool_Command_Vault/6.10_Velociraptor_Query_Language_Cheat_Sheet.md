# Velociraptor Query Language (VQL) - Field Reference Guide

## 1. Core Architecture: The VQL Paradigm
While VQL visually resembles SQL, its underlying mechanics are entirely designed for endpoint telemetry. We are not querying a static, indexed database; we are evaluating functions against live operating system states, memory artifacts, and ETW streams.

Key architectural concepts to remember:
* Plugins: The data generators. Functions like `info()` or `parse_pe()` that yield rows of data based on the current system state.
* Artifacts: Encapsulated YAML files containing VQL queries. They abstract the complexity of VQL into reusable, deployable modules (e.g., `Windows.System.Pslist`).
* Read-Only Nature: Baseline VQL operates safely without altering the compromised host's state, adhering to strict DFIR non-destructive principles.

## 2. Essential Syntax & Tactical Operators
VQL requires specific operators to filter high-noise endpoint data effectively.

* Regex Matching (=~): The backbone of threat hunting. Use it instead of exact string matching to catch variations in attacker command lines.
* Stacking (GROUP BY & count): The primary method for establishing a baseline and finding anomalies (the "least frequency of occurrence" technique).

## 3. Tactical Hunt Snippets

### Scenario A: Environmental Baselining & Stacking
Before hunting for adversaries, establish what "normal" looks like. This query stacks OS versions across the fleet to identify rogue or outdated endpoints.

```SQL
    SELECT OS, Platform, PlatformVersion, count() AS Count 
    FROM source() 
    GROUP BY OS
```

### Scenario B: Lateral Movement & Credential Abuse
Attackers frequently use compromised credentials across multiple machines. This snippet isolates successful logons (Event ID 4624) for a specific compromised user, explicitly filtering out their legitimate workstation to highlight lateral movement.

```SQL
    SELECT EventTime, Computer, EventData.SubjectUserName, EventData.TargetUserName 
    FROM source() 
    WHERE (EventData.TargetUserName =~ "suspect1" AND NOT Computer =~ "suspect1workstation") 
    AND NOT EventID = 4634
```

### Scenario C: Unsigned Binary Hunting
APT actors and ransomware payloads often lack valid Authenticode signatures. This query forces the endpoint to validate PE signatures, dropping known good corporate binaries, and surfacing untrusted executables sorted by rarity.

```SQL
    SELECT Name, Exe, Authenticode.Trusted, count() AS Count 
    FROM source() 
    WHERE Authenticode.Trusted = "untrusted" 
    AND NOT Exe = "C:\\Path\\to\\whitelisted\\corporate_agent.exe" 
    GROUP BY Exe 
    ORDER BY Count
```

### Scenario D: Binary Renaming Detection
Adversaries often rename native tools (like powershell.exe to svchost.exe) to bypass rudimentary detections. Rely on the `Windows.Detection.BinaryRename` artifact to extract the `OriginalFilename` from the PE header and compare it against the file's current name on disk.

## 4. Performance & Safety Guardrails
Running VQL across thousands of endpoints can trigger severe operational impacts if not properly throttled. Always configure the following constraints during mass hunts:

* CPU Limit: Ensure the Velociraptor agent does not consume more than 10-15% of the endpoint's CPU, preventing business disruption.
* Ops/Sec: Throttle the I/O operations per second, especially when hashing large directories or querying massive EVTX files, to prevent disk queuing on critical servers.
