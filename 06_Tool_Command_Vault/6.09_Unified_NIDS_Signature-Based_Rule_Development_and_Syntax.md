# Unified NIDS Signature-based Rule Development and Syntax Guidelines (Suricata & Snort 3)

## 1. The Rule Framework: Header & Metadata

Every modern NIDS rule (whether Snort or Suricata) relies on a strict foundational structure to determine routing, applicability, and lifecycle management before any deep packet inspection occurs.

### 1.1 The Rule Header
The header defines the core 5-tuple and the action to be taken.
* **Format:** `[action] [protocol] [src_ip] [src_port] [direction] [dst_ip] [dst_port]`
* **Example:** `alert tcp $HOME_NET any -> $EXTERNAL_NET any`
* **Directionality:**
  * `->` (Unidirectional): Triggers only on traffic moving from the source to the destination.
  * `<>` (Bidirectional): Triggers on traffic moving in either direction (useful for internal lateral movement detection).

**Engine-Specific Configurations:**
* **Variables:** `$HOME_NET` and `$EXTERNAL_NET` are defined in the engine's core configuration (`suricata.yaml` for Suricata, or `snort.lua` for Snort 3). Properly defining these is critical for preventing false positives caused by reverse traffic flows.

### 1.2 Rule Metadata
Metadata keywords are mandatory for SIEM integration and rule lifecycle management.
* `msg:"..."`: The human-readable alert title that appears in `fast.log` or your SIEM. It should follow a standardized naming convention (e.g., `ET MALWARE Possible PowerShell Empire Activity Outbound`).
* `sid:1000001`: Signature ID. Uniquely identifies the rule. (Custom rules typically start at 1,000,000 or higher).
* `rev:1`: Revision number. Must be incremented every time the rule logic is updated to ensure proper version control.

## 2. Stateful Protocol Analysis (`flow`)

Applying the `flow` keyword is the most effective way to reduce CPU overhead and false positives. It ensures the IDS engine only inspects packets within a valid, established connection context.

* **Syntax:** `flow:established,to_server;`
* **`established`**: Instructs the engine to ignore TCP handshake packets (SYN, SYN-ACK) and only inspect the payload of fully established connections.
* **`to_server` / `to_client`**: Restricts the inspection to a specific direction within that stateful session. Analyzing an HTTP GET request makes sense `to_server`, but looking for a malicious `Set-Cookie` header requires `to_client`.

## 3. Engine Execution & Performance Optimization

NIDS detection engines do not execute rules in the order they are written. Understanding the Multi-Pattern Matcher (MPM) is critical for writing rules that do not cause network latency or packet drops.

### The Pre-Filter
The `fast_pattern` modifier is the primary performance safeguard for any complex rule. 

* **Mechanism:** The engine extracts the longest, most unique string tagged with `fast_pattern` and loads it into the MPM search tree. If this exact string is absent in the packet payload, the engine immediately drops the rule evaluation, bypassing all expensive PCRE and buffer checks.
* **Best Practice:** Always apply `fast_pattern` to a highly unique string sequence. For example, `.php HTTP/1.1\r\nCookie: session=` is an excellent candidate because it defines a strict sequence of URI termination, protocol version, line break, and a specific header, which is extremely rare in benign traffic.
* **Syntax Independence:** The physical placement of `fast_pattern` within the rule string does not dictate its execution order. It acts as an absolute prerequisite for the rule to trigger deeper inspection.

## 4. Payload Navigation: Modifiers vs. Buffers

Navigating the packet payload effectively prevents evasion techniques like whitespace injection and protocol smuggling. When operating in a dual-engine environment, understanding engine-specific buffer nomenclature is critical for successful rule deployment and auditing.

### Absolute Positioning (Fixed-Position Matching)
Used primarily for binary carving, raw TCP/UDP payload inspection, or as a fallback when protocol parsers fail.

| Modifier | Function | Evasion Defense Context |
| :--- | :--- | :--- |
| `dsize` | Verifies the exact length of the packet payload. | Excellent for filtering hardcoded beacon sizes (e.g., `dsize:9;` for Cerber UDP check-ins) before regex evaluation. |
| `offset` | Starting byte for the search. | Finding magic bytes (e.g., `MZ` at `offset:0`). |
| `depth` | Maximum bytes to search from the start. | Restricting searches to specific protocol headers. |
| `distance` | Bytes to skip after the *previous* match. | `distance:0` prevents zero-byte gap evasions (e.g., `POST/login.php` without any spaces). |
| `within` | Maximum search window after the distance. | Ensures the subsequent match occurs within a logical boundary. |

### Sticky Buffers (Protocol-Aware Matching)
Relies on internal parsers to normalize traffic. This is the modern standard for application-layer protocols (HTTP, DNS, TLS). Parsers automatically strip evasion attempts (e.g., substituting spaces with tabs `\t`, random carriage returns `\r\n`) and place the normalized data into predefined buffers.

**Syntax Evolution & Engine Compatibility:**
To effectively audit legacy rules and write cross-compatible modern signatures, you must recognize how buffer syntax has evolved across engines:

* **Legacy Suricata (Suffix - For Auditing Only):** Historically, buffers were appended *after* the content. 
    *Example:* `content:"GET"; http_method;`
* **Modern Suricata (Prefix - Recommended):** Suricata now uses dot-notation placed *before* the content for clarity and engine efficiency.
    *Example:* `http.method; content:"GET";`
* **Snort 3 (Native):** Snort 3 generally utilizes underscore-notation and acts as a sticky buffer natively.
    *Example:* `http_method; content:"GET";`

**Advantage:** Drastically reduces false positives and CPU overhead by restricting the search space to a specific protocol field (e.g., targeting `http.client_body` or `http_client_body` instead of the entire packet). 
**Warning:** Relying on raw payload scanning instead of sticky buffers for HTTP traffic (e.g., legacy Ursnif detection missing HTTP modifiers) is considered highly inefficient and prone to false positives.

## 5. PCRE (Perl Compatible Regular Expressions) Fundamentals

PCRE should be utilized exclusively as a final validation step after cheaper `content` matches and `fast_pattern` checks have been satisfied. Writing efficient PCRE is crucial for preventing IDS engine overload.

### 5.1 Literal Evaluation within Character Classes (`[...]`)
Understanding how meta-characters behave inside versus outside brackets is essential for avoiding syntax errors and evasion.
* **Inside Brackets (`[...]`):** Most regex meta-characters lose their functional meanings and are evaluated as literal characters. 
  * A dot `.` literally means a period, not "any character".
  * A hyphen `-` placed at the very end of the class (e.g., `[a-z0-9.-]`) is treated as a literal dash, not a range indicator.
* **Outside Brackets:** Meta-characters enforce logic. To match a literal dollar sign, it must be escaped as `\$`; otherwise, it functions as an End-of-Line anchor.

### 5.2 Anchors for Exact Matching (`^` and `$`)
Without anchors, a regex will trigger on partial matches, leading to bypasses and false positives.
* `^` asserts the start of the buffer or string.
* `$` asserts the end of the buffer or string.
* *Example Context:* `pcre:"/^(?:login|admin)\.php$/U"` ensures the URI is *exactly* `login.php` or `admin.php`. Without `^` and `$`, an attacker could bypass the rule by appending the target string to a benign request (e.g., `GET /normal.php?q=login.php`).

### 5.3 Performance Tuning: Non-Capturing Groups `(?:...)`
By default, standard parentheses `(...)` create a "capturing group," forcing the IDS engine to allocate memory and store the matched string (e.g., into memory variable `$1`). 
* **Best Practice:** Always use `?:` inside grouping parentheses (e.g., `(?:php|api|rest)`) unless the matched value is explicitly required for a subsequent rule operation. This instructs the engine to match the pattern but drop the result, saving critical CPU cycles during high-throughput traffic inspection.

### 5.4 Common Threat Hunting Regex Patterns
1. **Negative Matching (Allowlisting Command Injection):** Instead of building an exhaustive blocklist of malicious characters (which is prone to 0-day bypasses), use `!` to invert the PCRE and define an allowlist of legitimate characters.
   * *Example:* `pcre: !"/^[\sa-z_0-9.-]*$/i"` triggers only when a character *outside* the defined safe set (e.g., `;`, `|`, `` ` ``) is observed in the payload.
2. **Base64 Payload Detection (e.g., PowerShell Empire C2):**
   C2 frameworks frequently encode payloads. Base64 processes data in 4-character blocks and pads the end with equal signs.
   * *Regex Prototype:* `(?:[A-Z0-9+/]{4})*(?:[A-Z0-9+/]{2}==|[A-Z0-9+/]{3}=|[A-Z0-9+/]{4})`
   * *Logic:* Matches consecutive 4-character blocks, followed by the strict `=` or `==` padding rules at the end of the string.

### 5.5 PCRE Execution Modifiers: Suricata vs. Snort
Modifiers are appended immediately after the closing slash (e.g., `/CRi`). They can be combined freely, and their order does not alter execution logic.

* `i` (Case-Insensitive): Ignores case constraints during matching.
* `R` (Relative): Initiates the regex match exactly where the previous `content` match terminated (acting as a sequential continuation).
* **Engine Differences for HTTP Buffers:**
  * **Suricata:** Utilizes the `U` modifier to force execution inside the `http_uri` buffer (e.g., `pcre:"/foo/U";`). The `RU` macro combines Relative and URI.
  * **Snort 3:** Typically binds the PCRE directly to the preceding sticky buffer instead of using specific suffix modifiers like Suricata's `U` (e.g., `http_uri; pcre:"/foo/";`).

## 6. Real-World C2 Detection Mechanics

Signatures for modern Command and Control (C2) frameworks require a fusion of string matching, behavioral analysis, and anomaly detection.

* **Patchwork APT (Protocol Structural Profiling):**
    Utilizes HTTP sticky buffers (`http_uri`, `http_client_body`, `http_header`) to pinpoint Base64 strings like `.php?profile=` and hardcoded parameters like `ddager=`. Combines this with negative matches (`!"Accept"`) to expose clients failing to implement standard RFC HTTP headers.
* **Cerber Ransomware (Performance & Thresholding):**
    Combines strict payload validation (`dsize:9`) with a `fast_pattern` string (`hi`) and a trailing `pcre` regex (`/^[af0-9]{7}$/R`). Crucially, it applies `detection_filter:track by_src, count 1, seconds 60` to suppress alerts for noisy, automated beaconing, reducing alert fatigue.
* **PowerShell Empire (Anomaly Identification):**
    Focus on the *absence* of standard behaviors combined with specific artifact structures. Detection logic includes matching pseudo-legitimate URIs (e.g., `login/process.php`), validating Base64 encoding structures within the `session` cookie via PCRE, and using negative content matches (`!"Referer"`, `!"Cache"`) to flag the unnatural absence of standard browser headers.
* **Covenant (Statistical Filtering):**
    Utilize interval-based behavioral analysis for beaconing detection. Applying `detection_filter: track by_src, count 4, seconds 10` shifts the detection paradigm from a single string match to a frequency threshold, identifying automated check-ins while eliminating accidental human-generated false positives.
* **Sliver (Structural Contrast):**
    Identify frameworks that attempt to blend in by contrasting "legitimate-sounding" directories with anomalous parameters. Detection relies on complex PCRE to map dynamic URI paths (e.g., `/api/v1/login.php`) that conclude with excessively short, randomized query parameters (e.g., `?a=123`) used for session tracking.

## 7. Advanced Detection in Encrypted Channels (TLS & JA3)

When SSL/TLS encryption hides the application-layer payload, NIDS engines shift their inspection focus to the unencrypted handshake metadata, specifically the X.509 certificate exchange and client fingerprinting.

### 7.1 TLS Certificate Metadata Inspection
Suricata's `tls` keywords and Snort's SSL preprocessors allow for deep inspection of the server’s identity before the encrypted tunnel is established. 

* **OID (Object Identifier) Navigation:** X.509 certificates use standardized OIDs to identify fields within the ASN.1 structure.
  * `55 04 06`: `countryName`
  * `55 04 07`: `localityName`
  * `55 04 0a`: `organizationName`
  * `55 04 03`: `commonName (CN)`
* **Detection Logic (Dridex & Patchwork Strategy):** Modern malware often utilizes self-signed certificates with anomalous characteristics.
  * **Length Validation:** Using `byte_test` to confirm if the `commonName` length (e.g., `> 13` bytes) aligns with expected malicious patterns. (Alternatively, using `distance` and `within` around the hex length byte to tightly bound custom strings like Patchwork's `toigetgf`).
  * **Pattern Matching:** Combining `content` matches for OIDs with `pcre` to identify randomized or pseudo-legitimate strings in certificate fields.

### 7.2 JA3 Client Fingerprinting
JA3 provides a unique representation of an SSL/TLS client by creating a digest of the `Client Hello` packet parameters.

* **Mechanism:** The engine collects five specific fields: `TLS Version`, `Accepted Ciphers`, `List of Extensions`, `Elliptic Curves`, and `Elliptic Curve Formats`.
* **The JA3 Hash:** These fields are concatenated and hashed (MD5) to create a fingerprint that can uniquely identify specific malware families or offensive tools.
* **Sliver C2 Detection Example (Suricata natively):**
  ```bash
  alert tls any any -> any any (msg:"Sliver C2 SSL"; ja3.hash; content:"473cd7cb9faa642487833865d516e578"; sid:1002; rev:1;)
  ```
