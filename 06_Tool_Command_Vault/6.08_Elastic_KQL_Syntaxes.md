# Elastic KQL — Syntax Cheat Sheet

> **Focus:** Query Language for Kibana Discover, Security, and Alerting — Filtering, Aggregating, Correlating.
>
> **Core Concept — Query vs. Pipeline:** KQL itself is purely a **filter language** (what Splunk calls "Finding"). Aggregation, analysis, and output formatting are handled separately — by **ES|QL** (Elasticsearch Query Language, the pipeline syntax introduced in 8.11), **Lens/TSVB** for visualisations, or the **Detection Rules** DSL. This sheet covers both layers: KQL for filtering and ES|QL for analysis. Keep that split active as you read.
>
> **Exam Strategy:** KQL queries go in the search bar or under `query.bool.filter`. ES|QL pipelines go in the `esql` field of an API call or the Timeline's ES|QL tab. Replace `<FIELD>` with `host.name`, `user.name`, or `process.name`.

## Basic Logic & Filtering
*Use these operators to build your initial filter before any aggregation.*

| Operator | Syntax Example | Notes |
| :--- | :--- | :--- |
| **AND** | `event.code: "4624" and host.os.type: "windows"` | Explicit — must write `and` (lowercase). Space alone does **not** imply AND in KQL. |
| **OR** | `user.name: "admin" or user.name: "root"` | Parentheses recommended for clarity: `(user.name: "admin" or user.name: "root")`. |
| **NOT** | `not user.name: "SYSTEM"` | Lowercase. Negates the condition that follows. |
| **Wildcard** | `process.executable: *\\Temp\\*` | `*` matches zero or more characters. Avoid leading wildcards — full index scans are expensive. |
| **Exists** | `process.command_line: *` | Returns events where the field is not null/absent. |
| **Missing** | `not process.command_line: *` | Returns events where the field is null or absent. |
| **Range** | `event.duration > 5000` | Operators: `>`, `>=`, `<`, `<=`. Works on numeric and date fields. |
| **Phrase match** | `process.command_line: "powershell -enc"` | Quoted strings match the exact phrase in order. |

> **⚠ KQL is case-insensitive for values but case-sensitive for field names.** `process.name: "cmd.exe"` and `process.name: "CMD.EXE"` match the same events, but `Process.Name` will not resolve if the ECS field is `process.name`.

## Statistics & Aggregation (ES|QL)

*How to collapse raw events into an actionable table. All examples assume the ES|QL pipeline editor or `POST /_query` API. The `FROM` source replaces Splunk's `index=` prefix.*

### 2.1 Frequency Analysis — Stacking

*Find the most common offenders.*

```esql
FROM logs-*
| WHERE event.code == "4625"
| STATS count = COUNT(*) BY source.ip
| SORT count DESC
| LIMIT 20
```

- **Use Case:** "Which IP generated the most failed logins?"
- `COUNT(*)` — counts all rows in the group. Use `COUNT_DISTINCT(<FIELD>)` to count unique values.

### 2.2 Rare Analysis — Anomaly Detection

*Find things that happened only once — often malicious.*

```esql
FROM logs-*
| STATS count = COUNT(*) BY process.name, host.name
| WHERE count < 5
| SORT count ASC
```

- **Use Case:** "Show me processes that only ran once across the fleet."

### 2.3 Listing & Grouping Values

*Collapse multiple events per entity into one row to understand scope.*

```esql
FROM logs-*
| STATS
    cmd_count    = COUNT(*),
    unique_hosts = COUNT_DISTINCT(host.name),
    cmd_list     = VALUES(process.command_line)
  BY user.name
```

| Function | Returns | Deduplicates? |
| :--- | :--- | :--- |
| `VALUES(<X>)` | Array of all unique values of X in the group | Yes |
| `COUNT_DISTINCT(<X>)` | Integer count of unique values of X | N/A |
| `COUNT(*)` | Total event count in the group | No |

> **Note:** ES|QL does not have a `list()` equivalent that preserves duplicates — use `COUNT(*)` alongside `VALUES()` when you need both the unique set and the repetition count.

### 2.4 Event Deduplication

*Remove duplicate events from multi-source ingestion, index rollover overlaps, or Beats restart.*

#### Dedup via aggregation (preferred — ES|QL)

```esql
FROM logs-*
| STATS first_seen = MIN(@timestamp), last_seen = MAX(@timestamp), count = COUNT(*)
  BY event.id, host.name
| WHERE count > 1
```

#### Dedup in KQL (Discover — collapse duplicates visually)

KQL has no native `dedup` command. In Kibana Discover, use the **Unique count** aggregation on `event.id` in Lens, or add a `collapse` step in ES|QL. For Detection Rules, rely on `timestamp_override` and `rule.max_signals` to control duplicate alerting.

**Key Behaviours:**
- `event.id` is the canonical ECS deduplication key — always present when Filebeat/Winlogbeat is configured correctly.
- Duplicate documents silently inflate `COUNT(*)` baselines — verify cardinality with `COUNT_DISTINCT(event.id)` vs `COUNT(*)` before relying on a threshold.

## Field Handling

*Extracting, normalising, renaming, and computing new fields before aggregation.*

### 3.1 Runtime Field Extraction (GROK / DISSECT)

*Extract structured values from the raw message field when the pipeline did not parse them at ingest.*

#### GROK (regex-based, flexible)

```esql
FROM logs-*
| GROK message "%{IP:extracted_ip} .* From: %{EMAILADDRESS:sender_email}"
| STATS count = COUNT(*) BY sender_email
```

#### DISSECT (delimiter-based, faster)

```esql
FROM logs-*
| DISSECT message "%{src_ip} %{} %{dest_port} %{action}"
| STATS count = COUNT(*) BY action, dest_port
```

**Extraction strategy — three steps:**
1. **Find the log:** Inspect `message` in Discover. Example: `SrcIP=10.10.10.5 Action=Drop`
2. **Identify the anchor:** What is directly left of the target? Anchor: `SrcIP=`
3. **Construct the command:** `| DISSECT message "SrcIP=%{src_ip} Action=%{action}"`

> **DISSECT vs GROK:** DISSECT is significantly faster and preferred when delimiters are consistent. Use GROK only when the log format is irregular or regex anchoring is required.

### 3.2 Rename Fields

```esql
FROM logs-*
| RENAME host.name AS "Host System", process.executable AS "Process Path"
| KEEP `Host System`, `Process Path`, @timestamp
```

> **Note:** Field names with spaces require backtick quoting in subsequent commands.

### 3.3 Derive New Fields (EVAL)

*Compute conditional labels, arithmetic, string manipulation, and type conversion.*

#### Conditional logic

```esql
| EVAL is_suspicious = CASE(
    COUNT(*) > 100, "HIGH",
    COUNT(*) > 10,  "MEDIUM",
    "LOW"
  )
```

```esql
| EVAL severity = CASE(
    event.severity >= 9, "CRITICAL",
    event.severity >= 7, "HIGH",
    event.severity >= 4, "MEDIUM",
    "LOW"
  )
```

#### String operations

```esql
| EVAL domain_lower = TO_LOWER(dns.question.name)
| EVAL full_path    = CONCAT(process.working_directory, "\\", process.name)
| EVAL short_cmd    = SUBSTRING(process.command_line, 0, 80)
```

#### Arithmetic

```esql
| EVAL mb_sent      = network.bytes / 1024 / 1024
| EVAL ratio_pct    = success_count / total_count * 100
```

#### Type conversion

```esql
| EVAL port_str     = TO_STRING(destination.port)
| EVAL count_num    = TO_INTEGER(event.count_field)
| EVAL ts_readable  = DATE_FORMAT("yyyy-MM-dd HH:mm:ss", @timestamp)
```

**Key Behaviours:**
- `EVAL` creates a new column or **overwrites** an existing one.
- `CASE()` returns `null` if no condition matches and no fallthrough is provided — always add a default as the final argument.
- Chain multiple `| EVAL` commands rather than nesting deeply.

### 3.4 Structured Field Parsing

*ES|QL auto-parses ECS fields. For non-standard nested JSON stored as a string:*

```esql
FROM logs-*
| EVAL parsed_json  = MV_EXPAND(json_message_field)
| GROK parsed_json  "\"key\":\"%{WORD:extracted_value}\""
```

For Winlogbeat `winlog.event_data.*` fields, no extra parsing is needed — Winlogbeat expands Windows XML Event Log fields into ECS-mapped sub-fields automatically.

### 3.5 Multi-Value Field Operations

*Work with array-type fields produced by `VALUES()` or multi-value ECS fields.*

```esql
| EVAL  item_count = MV_COUNT(process.args)
| WHERE MV_COUNT(process.args) > 5
```

```esql
| WHERE MV_CONTAINS(related.ip, "10.0.0.1")
```

| Function | Purpose |
| :--- | :--- |
| `MV_COUNT(<X>)` | Count elements in a multi-value field |
| `MV_CONTAINS(<X>, <val>)` | True if the array contains the value |
| `MV_EXPAND(<X>)` | Explode one multi-value row into N rows |
| `MV_FIRST(<X>)` / `MV_LAST(<X>)` | Extract first or last element |
| `MV_SORT(<X>)` | Sort array elements |

**Key Behaviours:**
- `MV_COUNT()` returns `0` for null fields — never throws an error.
- `MV_EXPAND()` multiplies row count — apply after aggregations, not before, unless you intend to fan out.

### 3.6 Field Normalisation Across Sources (COALESCE)

*Unify the same logical value stored under different field names across data sources.*

```esql
| EVAL src_ip = COALESCE(source.ip, client.ip, network.forwarded_ip)
| EVAL actor  = COALESCE(user.name, winlog.event_data.SubjectUserName, source.user.name)
| WHERE src_ip IS NOT NULL
    AND src_ip != "-"
    AND src_ip != "::1"
    AND src_ip != "127.0.0.1"
```

**Key Behaviours:**
- Returns the first non-null value — field order matters.
- Always filter out null, dash, and loopback values after normalisation to eliminate local-logon noise.

#### Common ECS source field mapping

| Logical Value | ECS / Winlogbeat Fields | Recommended COALESCE Order |
| :--- | :--- | :--- |
| Source IP | `source.ip`, `client.ip`, `network.forwarded_ip`, `winlog.event_data.IpAddress` | `COALESCE(source.ip, client.ip, network.forwarded_ip, winlog.event_data.IpAddress)` |
| Actor / Username | `user.name`, `winlog.event_data.SubjectUserName`, `winlog.event_data.TargetUserName` | `COALESCE(user.name, winlog.event_data.SubjectUserName, winlog.event_data.TargetUserName)` |
| Process Name | `process.name`, `process.executable`, `winlog.event_data.NewProcessName` | `COALESCE(process.name, process.executable, winlog.event_data.NewProcessName)` |
| Host Name | `host.name`, `host.hostname`, `winlog.computer_name` | `COALESCE(host.name, host.hostname, winlog.computer_name)` |

> **⚠ Process ID Format Warning:** Windows Security Event 4688 (`winlog.event_data.ProcessId`) stores PID in **hexadecimal**. Sysmon Event 1 (`process.pid`) stores it in **decimal**. Direct comparison always fails — convert before joining: `| EVAL pid_dec = TO_INTEGER(winlog.event_data.ProcessId)` (Elastic's `TO_INTEGER` handles the hex prefix automatically in recent versions; verify on your stack version).

## Time Analysis

*Timeline analysis for Incident Reports and trend visualisation.*

### 4.1 Time Chart — Visual Trends (ES|QL)

```esql
FROM logs-*
| WHERE event.code == "4625"
| STATS failed_logins = COUNT(*) BY BUCKET(@timestamp, 1 hour)
| SORT @timestamp ASC
```

- **Use Case:** "Show me a per-hour breakdown of failed login attempts — which hour spiked?"
- `BUCKET(@timestamp, 1 hour)` groups events into fixed-width time buckets. Also accepts `30 minutes`, `1 day`, `1 week`.

### 4.2 Time Bucketing — Text Timeline

*Produce a table-friendly timeline for Incident Reports.*

```esql
FROM logs-*
| STATS
    count       = COUNT(*),
    processes   = VALUES(process.name)
  BY BUCKET(@timestamp, 30 minutes), host.name
| SORT @timestamp ASC
```

- **Use Case:** "Give me a 30-minute-bucket timeline of every process that ran on each host."

### 4.3 Format Time for Reporting

```esql
| EVAL readable_time = DATE_FORMAT("yyyy-MM-dd HH:mm:ss", @timestamp)
| KEEP readable_time, host.name, event.code, process.name
```

- **Common format tokens:** `yyyy` year · `MM` month · `dd` day · `HH` hour (24h) · `mm` minute · `ss` second
- **Use Case:** "My Incident Report needs timestamps in `YYYY-MM-DD HH:MM:SS`, not epoch milliseconds."

## Anomaly Detection & Event Correlation

*Find outliers and relate events together across ECS-mapped sources.*

### 5.1 Statistical Outlier Detection

*Detect anomalies by comparing current activity against a baseline. Uses time bucketing as a prerequisite.*

#### Reusable template

```esql
FROM logs-*
| STATS metric = COUNT(*) BY entity_field, BUCKET(@timestamp, <INTERVAL>)
| STATS
    mu    = AVG(metric),
    sigma = STD_DEV(metric),
    current = MAX(metric)
  BY entity_field
| EVAL z_score = (current - mu) / sigma
| WHERE z_score > <THRESHOLD>
| SORT z_score DESC
```

#### `<INTERVAL>` — choose based on data volume

| Interval | Best For |
| :--- | :--- |
| `1 hour` | Authentication or network connection spikes |
| `15 minutes` | Process creation or DNS query bursts |
| `1 day` | Data exfiltration volume trending |

#### `<THRESHOLD>` — confidence level

| Threshold | Confidence |
| :--- | :--- |
| `z_score > 2` | 95% — standard sensitivity |
| `z_score > 3` | 99.7% — high precision, fewer false positives |

### 5.2 High-Performance Multi-Event Correlation (STATS over multiple event codes)

*Reconstruct attack chains across disparate log events without expensive joins. Equivalent to the SPL `stats` correlation pattern.*

```esql
FROM logs-*
| WHERE event.code IN ("1", "3")                        -- Sysmon: Process Create + Network Connect
| STATS
    cmd_line     = VALUES(process.command_line),         -- field specific to event.code 1
    dest_ip_list = VALUES(destination.ip),               -- field specific to event.code 3
    first_seen   = MIN(@timestamp),
    last_seen    = MAX(@timestamp)
  BY process.entity_id, host.name
| WHERE cmd_line     IS NOT NULL
    AND dest_ip_list IS NOT NULL
| KEEP first_seen, last_seen, host.name, process.entity_id, cmd_line, dest_ip_list
| SORT first_seen ASC
```

**Implementation Guide:**
- `<Primary_Correlation_Key>`: The unique identifier linking events (`process.entity_id` for Sysmon, `winlog.event_data.TargetLogonId` for logon session correlation). This is the linchpin.
- `<Secondary_Grouping_Key>`: Optional further segmentation (e.g. `host.name`, `user.name`).
- Why `VALUES()`? It creates an array of unique values across all correlated events, gracefully handling one-to-many relationships without row explosion.
- ECS `process.entity_id` is generated by Elastic Agent / Sysmon and is globally unique — prefer it over `process.pid` which reuses values after process exit.

### 5.3 Subsearch / Lookup Pattern

*Find A, then use A to find B — the KQL equivalent of Splunk's subsearch.*

KQL does not support inline subsearches. Use one of these patterns instead:

#### Pattern A — ES|QL ENRICH (for enrichment lookups)

```esql
FROM logs-*
| WHERE event.code == "4624"
| ENRICH threat_intel ON source.ip WITH threat_label, confidence_score
| WHERE threat_label IS NOT NULL
| STATS count = COUNT(*) BY source.ip, threat_label
```

#### Pattern B — Sequential query in Timeline / Rule

Run the first query, copy the results into the second query as a KQL `OR` list:

```kql
source.ip: ("1.2.3.4" or "5.6.7.8") and event.code: "4648"
```

#### Pattern C — ES|QL LOOKUP JOIN (≥ 8.17, tech preview)

```esql
FROM logs-*
| WHERE event.code == "4625"
| STATS failed_count = COUNT(*) BY source.ip
| LOOKUP JOIN threat_ip_index ON source.ip
| WHERE is_known_threat == true
```

### 5.4 Stateful Event Sequencing — EQL (Event Query Language)

*Elastic's dedicated language for ordered event sequence detection. Use for MITRE ATT&CK-aligned detection rules, not ad-hoc hunting.*

> **EQL ≠ KQL ≠ ES|QL.** EQL is a third syntax used exclusively in Detection Rules and the Timeline's EQL tab. It is order-sensitive and purpose-built for sequence correlation.

#### Sequence detection (equivalent to SPL `transaction`)

```eql
sequence by host.id with maxspan=5m
  [process where process.name == "cmd.exe"]
  [process where process.name == "net.exe" and process.parent.name == "cmd.exe"]
  [network where destination.port == 445]
```

#### Detect incomplete chains

```eql
sequence by host.id with maxspan=2m
  [process where process.name == "lsass.exe" and event.action == "start"]
  ![file where file.name : "*.dmp"]            -- "!" = event must NOT follow
```

**Key Behaviours:**
- Each bracket `[...]` is one event condition in the required order.
- `with maxspan=<TIME>` — maximum allowed time between the first and last event in the sequence.
- `!` prefix on a bracket — the sequence matches only if this event does **not** occur (equivalent to SPL `keepevicted=true` + `closed_txn=0`).
- `by <FIELD>` inside each bracket — join on a field that may differ per event type (e.g., `[process where ... ] by process.pid` then `[network where ... ] by process.pid`).
- EQL sequences are evaluated in strict time order — no pre-sorting required.

#### EQL vs ES|QL — when to use which

| Dimension | EQL | ES|QL |
| :--- | :--- | :--- |
| Event ordering | Order-sensitive (mandatory sequence) | Order-insensitive |
| Incomplete chain detection | Native (`!` prefix bracket) | Manual (`MV_CONTAINS` absence check) |
| Performance | Optimised for sequence workloads | Faster for volume aggregations |
| Primary use case | Detection Rules, Timeline pivots | Hunting, ad-hoc investigation, reporting |
| Time window | Per-entity relative (`maxspan`) | Absolute shared bucket (`BUCKET`) |
