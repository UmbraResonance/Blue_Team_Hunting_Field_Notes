# Portable Executable (PE) Architecture

## 1. Core Concept
The PE format is the standard data structure for executable files, object code, DLLs, and kernel modules in Windows. It dictates how the Windows OS Loader maps the binary from disk into the Virtual Address Space (VAS) of a process.

## 2. Critical PE Sections (The "W^X" Principle)
* **`.text` (Code Section)**: Contains executable machine instructions. Expected permissions: `Read` + `Execute` (R-X). *Hunting Red Flag: `Write` + `Execute` (RWX) indicates potential self-modifying code or unpacking.*
* **`.data`**: Initialized global/static variables. Expected permissions: `Read` + `Write` (RW-).
* **`.rdata`**: Read-only data, string literals, and often the Import Directory. 

*The Export Directory, though primarily associated with DLLs, is the PE component parsed by API-hashing loaders to locate function addresses without using the IAT. See [8.1.10 Manual Mapping and IAT Reconstruction](./8.1.10_Manual_Mapping_and_IAT_Reconstruction.md) Section 4 for the runtime parsing chain.*

* **`.bss`**: Uninitialized data. Takes up zero space on disk (Raw Size = 0) but is allocated in memory.
* **`.rsrc`**: Resources (icons, version info). *Hunting Red Flag: High entropy data hidden here may indicate an encrypted payload.*
* **`.reloc`**: Relocation table necessary for Address Space Layout Randomization (ASLR) and Reflective DLL Loading.

## 3. Imports and Exports
* **Import Directory (`.idata`)**: Lists external DLLs and functions the binary relies on (e.g., WINAPI calls).
    * **Imphash (Import Hash)**: An MD5 hash of the ordered import list. Crucial for clustering malware families.
* **Export Directory (`.edata`)**: Exposes internal functions for other modules to call. Mandatory for legitimate DLLs.

## 4. Metadata and Directories
Beyond executable sections, PE files contain metadata structures that describe the build environment and execution prerequisites.
* **DOS Header & Magic Number**: Every valid Windows PE file begins with the DOS header. The first two bytes contain the `MZ` (0x5D4A) magic number, which the Windows OS Loader uses to verify the file type before parsing the rest of the structure.
* **Debug Directory**: A directory typically generated by the compiler. It contains debugging information, most notably the absolute path to the PDB (Program Database) file and the GUID used to match the executable with its symbol file.
* **Rich Header**: An undocumented, plaintext block inserted by Microsoft Visual Studio linkers between the DOS stub and the PE header. It contains an array of key-value pairs detailing the exact toolchain components (compilers, assemblers, linkers) and their versions used to build the binary.

*The **TLS Directory** (Data Directory entry 9) registers callbacks that the Windows loader invokes before the documented entry point executes. Legitimate uses include per-thread variable initialization, but the TLS Directory is also a standard anti-analysis primitive for pre-entry-point debugger detection and environment checks. See [8.1.27 Exception Handling and TLS Callbacks](./8.1.27_Exception_Handling_and_TLS_Callbacks.md) Section 2 for the loader's execution order and the analyst workflow implications.*

## 5. PE Overlay and Security Directory
* **The Overlay**: Data appended to the absolute end of a PE file, physically residing *after* the last defined PE section. Because the overlay falls outside the boundaries defined by the section headers, the Windows OS Loader does not map this data into the virtual memory space of the process.
* **Security Directory (Authenticode)**: When a Windows binary is digitally signed, the PKCS#7 `WIN_CERTIFICATE` structure is stored in the Security Directory. The actual cryptographic data for this directory is conventionally appended as the file overlay.

## 6. Packer and Loader Stub Mechanics
Software packing is a mechanism to compress or encrypt the original executable structure.
1. **Structural Transformation**: The original PE sections (e.g., `.text`, `.data`) are compressed/encrypted and packed into new, often proprietary sections.
2. **The Loader Stub**: A small, natively executable piece of code is injected into the binary. The PE's primary Entry Point is redirected to this stub rather than the original program's `main` function.
3. **Execution at OEP (Original Entry Point)**: Upon execution, the OS Loader executes the stub. The stub dynamically allocates memory, decrypts/decompresses the hidden sections into these memory regions, resolves the required API imports (rebuilding the IAT), and finally transfers the execution flow to the **Original Entry Point (OEP)** of the unpacked code.
