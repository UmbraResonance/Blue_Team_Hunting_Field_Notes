## 3. Handle Inheritance (The Passing of the Voucher)

Handle inheritance allows a child process to inherit specific access rights to objects already opened by the parent. This is essential for resource sharing and coordinated execution.

### 3.1 Process-Level Inheritance Logic
For a handle to be inherited by a child process, two conditions must be met:
1.  **Object-Level Flag**: The handle must be opened/created with the `bInheritHandle` member of the `SECURITY_ATTRIBUTES` structure set to `TRUE`.
2.  **Creation-Level Flag**: The `CreateProcess` call must have its `bInheritHandles` parameter set to `TRUE`.

If both are true, the child process receives a copy of the handle at the **same index (ID)** as the parent, inheriting the same access mask.

### 3.2 Registry Handle Hierarchy (Relative Activation)
In the registry subsystem, handles (`hKey`) are intrinsically hierarchical. Almost every registry API requires a "Parent Handle" to resolve a subkey path. There are three primary patterns for managing this inheritance and access:

#### A. Predefined Root Handles (The Static Parents)
Windows provides a set of constant, global handles that act as the ultimate roots of the registry tree. These are effectively "vouchers" that are always valid within every process context.
* `HKEY_LOCAL_MACHINE (HKLM)`: System-wide configuration.
* `HKEY_USERS (HKU)`: All loaded user profiles.
* **Fact**: These are not real kernel handles but special constants (e.g., `0x80000002`) recognized by `ntdll.dll` to redirect calls to the correct kernel hive.

#### B. Relative Opening (Open Handle as Parent)
This is the most common form of registry "inheritance" in code. A program opens a handle to a key (e.g., `HKLM\Software`) and then uses that handle as the `hKey` parameter for subsequent `RegOpenKeyEx` calls to access subkeys (e.g., `\Microsoft`).
* **Mechanism**: The kernel uses the parent handle's existing `FileObject` (for the hive) and relative path to quickly resolve the target without traversing the entire registry root again.
* **Security Insight**: If the parent handle is inherited by a child, the child can perform operations relative to that handle even if it lacks permissions to access the root keys directly.

#### C. Pseudo-Handles (Context-Dependent Special Usage)
A Pseudo-handle is a symbolic reference that the OS resolves dynamically based on the current process or thread identity.
* `HKEY_CURRENT_USER (HKCU)`: This is the most critical pseudo-handle. It dynamically maps to the current user's SID under `HKEY_USERS`.
* **Special Usage**: When an application uses `HKCU`, the registry redirector determines which hive to access based on the **Process Token**. If a process is impersonating another user, `RegOpenCurrentUser` can be used to acquire a real handle to that user's specific hive, which can then be inherited by children to maintain a consistent user-land view.

### 3.3 The Pseudo-handle Exception (Process/Thread)
Unlike standard handles, pseudo-handles returned by `GetCurrentProcess()` or `GetCurrentThread()` are constants (e.g., `-1` or `-2`). 
* **Fact**: These are **not** inheritable. 
* **Logic**: If a child process used an inherited pseudo-handle for "Current Process," it would mistakenly point to itself rather than the parent process. To pass access to the parent process object, the parent must use `DuplicateHandle` to create a real, inheritable handle to itself.
