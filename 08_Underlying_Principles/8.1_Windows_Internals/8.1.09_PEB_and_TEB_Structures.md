# PEB (Process Environment Block) & TEB (Thread Environment Block)

> **Core Principle**: The PEB and TEB are user-mode data structures that the Kernel provides to processes/threads for fast metadata access. Because they reside in user-mode memory, they are prime targets for evasion and anti-analysis.

## 0. What is a Thread? (The Unit of Execution)

> **Core Concept:** While a **Process (`_EPROCESS`)** is the "Container" that owns resources, a **Thread** is the actual entity that the OS kernel schedules to execute code.

### **Resource Sharing vs. Isolation**
* **Shared Resources:** All threads within a single process share the same **Virtual Address Space (VAS)** and the same **Handle Table** (access to files, keys, etc.).
* **Private Context:** To manage its specific execution flow, each thread maintains its own:
    * **Stack:** Private memory for tracking function calls and local variables.
    * **Register State:** Current CPU state (RIP/EIP, RSP/ESP, etc.).
    * **TEB:** The user-mode metadata structure specifically for that thread (detailed below).


### **2. Kernel Representation (`_ETHREAD`)**
* In Ring 0, every thread is represented by an **`_ETHREAD`** structure.
* **The "Backlink" (Forensic Truth):** Each `_ETHREAD` contains a pointer that leads directly back to its parent `_EPROCESS`.
* **Detection Pivot:** If a process is hidden via DKOM (unlinked from the process list), forensics tools can still discover it by scanning for active `_ETHREAD` structures and following the pointer back to the "hidden" container.

## 1. PEB (Process Environment Block)
The PEB contains process-wide information. It is accessed via the `gs` segment register (x64) or `fs` (x86).

### Key Fields for Attackers & Defenders:
* **BeingDebugged (Offset 0x2)**: A boolean flag set by the OS if a debugger is attached. Malware reads this directly (without calling `IsDebuggerPresent`) to self-terminate.
* **Ldr (`PEB_LDR_DATA`)**: A structure containing **three** separate doubly-linked lists (`LIST_ENTRY`) tracking all loaded DLLs:
    1. `InLoadOrderModuleList`: Order in which DLLs were loaded into memory.
    2. `InMemoryOrderModuleList`: Order by virtual memory address from lowest to highest.
    3. `InInitializationOrderModuleList`: Order of `DllMain` execution (critical for resolving system dependencies).
    * **Evasion (Module Unlinking)**: Advanced malware modifies the `Flink` and `Blink` pointers across *all three* lists to completely hide a malicious DLL from standard user-mode enumeration tools (e.g., `tasklist` or Process Explorer). "Lazy" malware might only unlink from the first list.
* **ProcessParameters**: Contains the command line and environment variables.

## 2. TEB (Thread Environment Block)
The TEB stores information about the currently running thread.
* **StackBase / StackLimit**: Defines the thread's memory stack boundaries.
* **TlsSlots**: Thread Local Storage; used by malware to store persistent data across function calls without using global variables.

## 3. Hunting & Forensic Insights
* **Static Analysis**: Search for assembly instructions like `mov rax, gs:[60h]` (PEB) or `mov rax, gs:[30h]` (TEB). These are strong indicators of manual environment inspection or anti-debugging logic.
* **Memory Forensics ("The Triangulation Strategy")**:
    * **The Misconception**: User-mode tools rely on the PEB, which can lie.
    * **The Truth (VAD Tree)**: The Kernel tracks memory-mapped files (DLLs) via the process's **VAD Tree**, not via a direct list in `_EPROCESS`.
    * **Execution (`windows.ldrmodules`)**: Use Volatility to cross-reference the three PEB `Ldr` lists against the actual mapped segments in the VAD Tree. If a DLL base address appears in the VAD Tree (marked as an executable image) but is missing from one or all of the three `Ldr` lists (`False` in Volatility output), it is definitive proof of **Module Unlinking** evasion.
