# Manual Mapping & IAT Reconstruction

> **Core Principle**: Standard DLL loading via `LoadLibrary` is highly visible to EDRs. Manual Mapping is a technique where the malware acts as its own Windows Loader to remain "Fileless" in memory.

## 1. The Manual Loading Process
Instead of asking the OS to load a DLL, the malware:
1. **Allocates Memory**: Typically uses `VirtualAlloc` with `RWX` permissions.
2. **Writes Sections**: Copies the DLL's headers and sections into the allocated space.
3. **Relocation**: Manually adjusts the memory addresses within the DLL to match its new base address.
4. **IAT Reconstruction**: Manually resolves the addresses of functions the DLL needs from other libraries (e.g., `ntdll.dll`, `kernel32.dll`).

## 2. Bypassing AMSI (Antimalware Service Interface)
* **The Gap**: AMSI is deeply integrated into the standard Windows Loader and script engines.
* **Native Evasion**: By manually mapping a **Native DLL** (C++/Rust), the malware never triggers the "Image Load" event that AMSI relies on for scanning.

## 3. Detection Heuristics
* **Memory Scanning**: Look for memory pages marked as `RX` or `RWX` that do not have a corresponding file on disk (**Unbacked Memory**).
* **IAT Anomalies**: Check for IAT entries that point to addresses within the process's private memory rather than the export tables of legitimate system DLLs.
* **Sysmon Event 7**: Lack of Sysmon ID 7 (Image Load) for a known malicious capability while the process is clearly exhibiting that behavior.

## 4. Manual API Resolution (API Hashing)
 
A manually-mapped payload faces a secondary problem after the image is placed in memory: it has no Import Address Table populated by the OS loader. The payload must resolve every Win32 API address itself, at runtime, without calling `LoadLibrary` or `GetProcAddress` — because invoking those APIs would defeat the point of bypassing the loader in the first place, and because their presence in the payload's own minimal IAT would produce the exact static-analysis signatures reflective loading is designed to avoid.
 
The standard solution is **API hashing**: at runtime, the payload walks the PEB's loaded-module list to locate the base address of `kernel32.dll` (or `ntdll.dll`), parses that module's Export Directory in memory, and computes a rolling hash of each export name. When the hash matches a precomputed constant embedded in the payload, the corresponding function address is retrieved from the Export Address Table. Only the hash constants are stored in the payload — the human-readable API names (`VirtualAlloc`, `NtAllocateVirtualMemory`, etc.) never appear in the binary.
 
### 4.1 The Three-Stage Resolution Chain
 
The resolution process combines three OS structures covered elsewhere in this repository. Understanding each stage's role clarifies why the technique evades both static and dynamic detection.
 
**Stage 1 — PEB Walk to locate `kernel32.dll`**
 
The payload reads the `PEB` pointer from the `GS` segment register at offset `0x60` (on x64) or the `FS` segment at offset `0x30` (on x86). From the PEB, it dereferences the `Ldr` field (`PEB_LDR_DATA`) and walks one of the three loaded-module linked lists described in [8.1.09 PEB and TEB Structures](./8.1.09_PEB_and_TEB_Structures.md). The `InMemoryOrderModuleList` is the conventional choice because its order is stable and well-documented across Windows versions.
 
The walk iterates through `_LDR_DATA_TABLE_ENTRY` structures, comparing each entry's `BaseDllName` against a hashed target (for example, a hash of the Unicode string `"kernel32.dll"`). On match, the payload retrieves the `DllBase` field — the base address of the target module in the current process's address space.
 
Because this walk reads memory rather than calling APIs, it produces no telemetry. The `PEB` is user-mode memory; no syscall is issued; no hooked function is invoked.
 
**Stage 2 — PE Export Directory Parse**
 
With the module's base address in hand, the payload parses the target module's PE header structure in memory. The path is:
 
`DllBase` → `IMAGE_DOS_HEADER.e_lfanew` → `IMAGE_NT_HEADERS.OptionalHeader.DataDirectory[IMAGE_DIRECTORY_ENTRY_EXPORT]` → `IMAGE_EXPORT_DIRECTORY`
 
The Export Directory provides three parallel arrays:
* `AddressOfNames` — an array of RVAs (relative virtual addresses) pointing to export name strings.
* `AddressOfNameOrdinals` — an array of 16-bit ordinals mapping each name to a function slot.
* `AddressOfFunctions` — an array of RVAs pointing to the actual function entry points.
The PE structure and data directory layout are detailed in [8.1.15 Portable Executable Architecture](./8.1.15_Portable_Executable_Architecture.md). The critical property for API resolution is that the Export Directory is always accessible in memory once the module is loaded — it is not stripped by the loader and not protected by additional access checks beyond the module's normal read permissions.
 
**Stage 3 — Hash-Match Loop**
 
The payload iterates through `AddressOfNames`, reads each exported function name, computes a hash using an algorithm embedded in the payload, and compares the result against a precomputed target hash. On match, the same index is used into `AddressOfNameOrdinals` to retrieve the function's ordinal, which becomes the index into `AddressOfFunctions` to retrieve the function's RVA. Adding that RVA to `DllBase` yields the absolute virtual address of the target API.
 
Common hash algorithms encountered in real-world malware:
 
| Algorithm | Characteristic | Signature |
| :--- | :--- | :--- |
| **ROR13** | Rotate-right 13 bits, add character, repeat. Used in Metasploit shellcode and many early implementations. | Look for `ror eax, 0Dh` in tight loops. |
| **DJB2** | Multiply-by-33 accumulator. Common in custom loaders. | `shl eax, 5` followed by `add eax, <register>` representing `hash * 33 + char`. |
| **CRC32** | Standard CRC with a fixed polynomial. Sometimes uses the SSE4.2 `crc32` instruction on modern CPUs. | Presence of `crc32` opcode or a 256-entry lookup table in `.rdata`. |
| **Custom XOR-based** | Per-sample variants; often incorporate a per-binary seed to prevent cross-sample hash-database lookups. | Short arithmetic loops operating one byte at a time over an ASCII-looking memory region. |
 
### 4.2 Why This Technique Evades Static Analysis
 
The static-analysis evasion has four independent layers, each reinforcing the others:
 
* **No API strings**: The binary contains no references to `VirtualAlloc`, `NtWriteVirtualMemory`, or any other sensitive API name. YARA rules that search for API-name substrings produce zero matches.
* **No IAT entries**: The `__imp_` symbols that IDA and Ghidra rely on to label API calls do not exist. The disassembler shows `call eax` or `call qword ptr [rbp+...]` with no symbol resolution.
* **Imphash uselessness**: Because the legitimate IAT is empty or contains only benign entries (`LoadLibrary`, `GetProcAddress`, or nothing at all), the imphash is either a universal "empty-import" value or matches thousands of unrelated samples. As noted in [4.1.01 Static Analysis Triage](../../04_Malware_Analysis_Cheatsheets/4.1_Static_Analysis/4.1.01_Static_Analysis_Triage.md), imphash is rendered meaningless when the IAT is sparse.
* **Hash constants look like noise**: The precomputed 32-bit hash values embedded in the payload appear as arbitrary dwords in the `.rdata` section. Without knowing the hash algorithm, there is no way to reverse a hash back to an API name; the analyst must either recognize the algorithm pattern or brute-force the hash against a dictionary of known API names.

### 4.3 Hell's Gate and Syscall Number Harvesting
 
A significant evolution of API hashing, introduced by the **Hell's Gate** technique family (and its descendants Halo's Gate and Tartarus' Gate), extends the resolution process beyond locating function addresses. Instead of using the resolved function pointer, the payload reads the syscall stub prologue directly from `ntdll.dll`'s memory and extracts the **syscall number** encoded in the `mov eax, <imm32>` instruction at byte offset 4 of each Nt-function stub.
 
With the syscall number harvested, the payload executes the syscall directly from its own code — never calling into `ntdll.dll` at all. This defeats inline hooks placed on the `ntdll.dll` function prologue, because the hooked code is never executed. The mechanics of this evasion and the corresponding detection approach are covered in [8.1.29 EDR User-Mode Hooking and Unhooking Mechanics](./8.1.29_EDR_Hooking_and_Unhooking_Mechanics.md) Section 3.1.
 
The Halo's Gate refinement handles the case where an EDR has hooked the target function by walking forward or backward through neighboring syscall stubs (which typically have sequential syscall numbers) and computing the target's number by offset. This makes the technique robust against hook placement on any individual function.
 
### 4.4 Dynamic Detection Approach
 
Because API hashing is implemented entirely in user-mode memory reads and arithmetic, it produces no direct syscall or API telemetry during the resolution phase itself. Detection shifts to downstream behaviors and to memory artifacts:
 
* **ETW thread stack walks**: When the resolved API is finally called, the call originates from the manually-mapped payload's memory region — not from any legitimately loaded module. ETW-TI thread stack walks (see [8.1.04 ETW Architecture and Telemetry Orchestration](./8.1.04_ETW_Architecture_and_Telemetry_Orchestration.md)) identify this as unbacked-memory code execution.
* **Memory forensics**: Volatility's `ldrmodules` plugin cross-references the three PEB `Ldr` lists against the VAD tree, identifying executable memory regions that are not registered as loaded modules. See [8.1.09 PEB and TEB Structures](./8.1.09_PEB_and_TEB_Structures.md) Section 3 on "The Triangulation Strategy."
* **Memory integrity signals**: When combined with Hell's Gate-style syscall execution, the payload's code segment contains `syscall` instructions that are not inside any legitimate module. Live response tools that scan for `0F 05` (the `syscall` opcode) in unbacked RX memory produce high-fidelity alerts.
### 4.5 Analyst Workflow for Recognizing API Hashing
 
During static triage, three indicators cluster around API hashing:
 
First, the binary's import table is anomalously sparse — often only `LoadLibrary`, `GetProcAddress`, or nothing at all — despite the sample being a substantial executable that clearly does meaningful work. This disproportion between payload size and import count is the opening signal.
 
Second, the code contains tight loops performing one-byte-at-a-time arithmetic on memory regions that, when dumped, resolve to ASCII strings of export names. The loops will typically feature rotate, XOR, or multiply instructions against accumulator registers, terminating on a null byte.
 
Third, the binary reads from the PEB (`gs:[60h]` on x64, `fs:[30h]` on x86) early in execution. This is the universal fingerprint of module enumeration and is rare in legitimate code outside of specific runtime initialization paths.
 
Recognizing these three indicators together allows the analyst to pivot immediately from "the IAT is empty, I can't see what this does" to "this is an API-hashing loader, and I need to identify the hash algorithm to reverse the resolution." Tools like FLOSS and capa automate parts of this recognition, but understanding the underlying mechanism is what makes the automated output interpretable.
