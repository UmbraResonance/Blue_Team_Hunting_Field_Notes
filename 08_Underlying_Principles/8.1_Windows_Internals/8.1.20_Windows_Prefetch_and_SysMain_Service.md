# Windows Prefetch & Memory Management

> **Core Concept:** The SysMain service monitors application startup to pre-load necessary code and data into RAM, accelerating application launch times.
> **Blue Team Impact:** Prefetch files (`.pf`) are the gold standard for proving **Program Execution** and determining execution frequency (RunCount).

---

## 1. Technical Architecture

Prefetching is handled by the Windows Cache Manager and the SysMain service (formerly SuperFetch). 

### **1.1 The Prefetch Generation Workflow (Ring 3 ↔ Ring 0 Lifecycle)**
Understanding Prefetch through the lens of the Execution Ecosystem (see `8.1.05_The_User_Mode_Ecosystem_and_Call_Stack.md`) reveals a cross-boundary operation:

1. **Application Launch (Ring 3 -> Ring 0):** An execution request (e.g., calling `CreateProcess`) flows through Subsystem DLLs (`kernel32.dll`), hits the Native API (`ntdll.dll`), and uses a Syscall to enter the Kernel.
2. **Page Fault Interception (Ring 0):** As the newly created process attempts to access code/data not yet in physical RAM, it triggers Page Faults. The **Windows Cache Manager** (operating in Ring 0) intercepts these faults to retrieve the data from disk, silently recording every file and DLL the process touches.
3. **The 10-Second Tracing Window:** The kernel maintains this intense monitoring for the first 10 seconds of the process's life.
4. **Handoff to SysMain (Ring 0 -> Ring 3):** The kernel passes this telemetry back to User Mode. The **SysMain service** (a Ring 3 Service Process hosted inside `svchost.exe`) receives the data.
5. **Artifact Compilation (Disk Write):** SysMain compiles the trace data, hashes the execution path, and writes the final `.pf` file to `C:\Windows\Prefetch` (e.g., `CMD.EXE-0A75EDD0.pf`).

### **1.2 Prefetch Data Structures**
Inside a parsed Prefetch file, several critical forensic data points exist:
* **Run Count:** The total number of times the executable has been launched.
* **Execution Timestamps:** Windows 10/11 stores the last 8 execution timestamps (UTC).
* **Referenced Files/Directories:** A list of handles opened during the first 10 seconds, which can reveal payloads loaded by living-off-the-land binaries (LoLBin).

## 2. Adversary TTPs

### **Scenario A: LoLBin Payload Discovery (T1218)**
* **Mechanism:** An attacker executes a malicious DLL via `rundll32.exe`. 
* **Detection:** The `RUNDLL32.EXE-*.pf` file will contain references to the specific malicious `.dll` loaded during that execution, exposing the payload even if the command line arguments weren't logged.

### **Scenario B: Prefetch Wipe (T1070.004)**
* **Mechanism:** Malware deleting its own `.pf` file immediately after execution to disrupt forensic timelines.
* **Artifact:** The deletion will generate USN Journal (`$J`) entries, and the execution might still be caught in memory or ShimCache.

## 3. Detection Engineering (SOC Red Flags)

| Red Flag | Description | Correlation |
| :--- | :--- | :--- |
| **Execution from Temp/Public** | Prefetch files generated for binaries executing from `C:\Users\Public` or `AppData\Local\Temp`. | Check against [[4.0_Common_Malware_Behaviors_and_TTPs]]. |
| **Missing .pf for Known Process** | A process was observed running (e.g., in memory), but no corresponding Prefetch file exists on disk. | Indicates potential anti-forensics or execution from a non-standard volume. |
| **Suspicious Loaded Modules** | `svchost.exe` or `powershell.exe` prefetch files referencing known malicious payload paths. | Use `PECmd.exe` as detailed in [[6.02_Windows_DFIR_Master_Notes]]. |
