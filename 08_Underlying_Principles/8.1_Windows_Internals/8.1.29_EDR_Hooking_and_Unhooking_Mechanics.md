# EDR User-Mode Hooking and Unhooking Mechanics

> **Core Concept**: Endpoint Detection and Response (EDR) products need visibility into malicious behavior at the API-call level, but the Windows kernel exposes only a limited set of event callbacks to third-party drivers. To close this visibility gap, EDRs inject a monitoring DLL into every user-mode process and rewrite the entry points of sensitive `ntdll.dll` and `kernelbase.dll` functions so that every call is first routed through the EDR's inspection logic. This rewriting is what the industry calls "user-mode hooking."
> **Blue Team Impact**: Understanding where and how EDR hooks live is prerequisite to three things: (1) reading EDR telemetry with an accurate mental model of what it can and cannot see, (2) recognizing the specific mechanical patterns malware uses to evade or remove hooks, and (3) explaining — when an incident post-mortem asks "why did our EDR miss this?" — whether the answer is a bypass, a blind spot, or an actual rule failure.

---

## 1. Why User-Mode Hooking Exists

The architectural pressure toward user-mode hooking comes from the limits of what the kernel exposes. Microsoft publishes a restricted set of kernel callbacks for third-party security drivers: process creation (`PsSetCreateProcessNotifyRoutineEx`), thread creation (`PsSetCreateThreadNotifyRoutine`), image load (`PsSetLoadImageNotifyRoutine`), registry (`CmRegisterCallbackEx`), and a minifilter framework for file system activity. These callbacks give an EDR visibility into coarse events — a process was created, a DLL was loaded — but not into the *intent* of a running process.

Intent lives at the API-call boundary. Whether a process is performing legitimate inter-process communication or injecting shellcode is determined by *which* `NtWriteVirtualMemory` calls happen, against *which* targets, with *which* argument patterns. The kernel's callback surface does not expose this. ETW-TI (see [8.1.04 ETW Architecture and Telemetry Orchestration](./8.1.04_ETW_Architecture_and_Telemetry_Orchestration.md)) narrows the gap for certain injection-related events but is restricted to PPL-protected consumers and does not cover the full Nt-API surface.

User-mode hooking closes the remaining gap by interposing EDR code between the application and `ntdll.dll`'s syscall stubs. The cost is architectural: because the hooks live inside the process being monitored, the monitored process can theoretically see, modify, or remove them. This is the trust asymmetry that every EDR bypass technique exploits.

### 1.1 The Hooking Contract
When an EDR boots, its kernel driver typically injects a monitoring DLL into every process that loads (triggered by the `PsSetLoadImageNotifyRoutine` callback on `ntdll.dll`). The monitoring DLL locates the exports in `ntdll.dll` — `NtAllocateVirtualMemory`, `NtWriteVirtualMemory`, `NtProtectVirtualMemory`, `NtCreateThreadEx`, `NtMapViewOfSection`, and several dozen others — and rewrites their prologues to redirect execution into the EDR's inspection routines.

After inspection, the EDR's routine either (a) calls a saved copy of the original instructions to continue the API, (b) blocks the call and returns a synthesized error, or (c) flags the behavior for telemetry and proceeds transparently. The entire decision loop happens in the calling thread's context, before the syscall instruction executes.

## 2. Hook Implementation Patterns

Different EDRs hook different function sets at different layers. The three patterns below cover substantially all commercial implementations.

### 2.1 Inline Hook (Trampoline / Detour)
The dominant technique. The first few bytes of the target function (typically 5 bytes on x86, 12–14 bytes on x64 to accommodate an absolute jump) are overwritten with a `JMP` instruction that redirects execution to the EDR's inspection routine. The original bytes are saved to a **trampoline** — a small executable stub that, after EDR processing, executes the saved instructions and jumps back to the original function just past the overwritten region.

A typical pre-hook `NtAllocateVirtualMemory` prologue in Windows 10/11 x64:
```
mov  r10, rcx         ; 4C 8B D1
mov  eax, 18h         ; B8 18 00 00 00     ; syscall number
test byte ptr [...]   ; F6 04 25 ...
jne  ...              ; 75 ...
syscall               ; 0F 05
ret                   ; C3
```

After an EDR inline hook is applied:
```
jmp  <EDR inspection routine>   ; E9 XX XX XX XX  (5 bytes) or indirect jmp (14 bytes)
...remaining bytes of prologue are clobbered...
```

* **Telemetry implication**: Every call to the hooked function passes through the EDR routine. Arguments, return values, and calling context are fully inspectable.
* **Evasion implication**: The first six-to-fourteen bytes of every hooked export no longer match the on-disk `ntdll.dll`. This mismatch is itself the detection signal for anti-cheat-style integrity checks, and conversely, the repair target for every unhooking technique.

### 2.2 IAT Hook (Import Address Table)
Less common in modern EDRs but still seen in older products and in some anti-cheat systems. Instead of modifying `ntdll.dll`, the EDR walks a specific module's Import Address Table and overwrites the function pointers so that calls to (for example) `kernel32.dll!VirtualAlloc` resolve to an EDR-controlled address.

IAT hooking is architecturally weaker than inline hooking: it only catches calls that resolve through the hooked module's IAT. Malware that uses `GetProcAddress` to resolve APIs dynamically, or that walks the PEB's `Ldr` lists to find function addresses (see [8.1.09 PEB and TEB Structures](./8.1.09_PEB_and_TEB_Structures.md)), bypasses IAT hooks entirely. For this reason, modern commodity malware often bypasses IAT hooks as a side effect of API hashing, not as an explicit evasion choice.

### 2.3 Kernel Callback + ETW-TI Combination
Strictly speaking not a "hook" in the user-mode sense, but functionally equivalent for detection purposes. The EDR's kernel driver subscribes to the Microsoft-approved callback set (`PsSetCreateProcessNotifyRoutineEx`, `ObRegisterCallbacks` for handle interception, etc.) and subscribes to ETW-TI as a PPL-protected consumer. This combination gives high-fidelity visibility into process creation, handle duplication, and remote thread creation without modifying any user-mode memory.

The limits, as mentioned above, are coverage breadth. Kernel callbacks do not fire for every `NtWriteVirtualMemory` call — only for specific events the kernel exposes. An EDR relying solely on this layer has large blind spots around memory manipulation, which is why most commercial products combine kernel callbacks *and* user-mode hooks rather than choosing one.

## 3. The Evasion Landscape

Because user-mode hooks are mutable memory inside the attacker's own process, every hook is theoretically evadable. In practice, evasion techniques cluster into four mechanical patterns.

### 3.1 Direct Syscall Execution
The malware bypasses `ntdll.dll` entirely. Instead of calling `NtAllocateVirtualMemory` and going through the hooked prologue, the malware embeds its own copy of the syscall stub — loading `r10`, loading the syscall number into `eax`, and executing `syscall` directly. The hooked function is never reached.

The challenge for the attacker is obtaining the correct syscall number. Syscall numbers are not stable across Windows builds; `NtAllocateVirtualMemory` might be `0x18` on one build and `0x19` on another. Modern direct-syscall frameworks (SysWhispers3, Hell's Gate, Halo's Gate) resolve this at runtime by reading the syscall number directly from `ntdll.dll`'s own stubs — which works because the `mov eax, <number>` instruction at offset 4 of each Nt function is preserved even after the prologue is hooked (the hook's `JMP` overwrites bytes 0–4, not the syscall number encoded at byte 5 onward, depending on hook implementation).

* **Detection angle**: Direct syscalls originate from code that is not part of any loaded `ntdll.dll` mapping. ETW-TI's thread stack walks identify this: a syscall event whose return address does not resolve inside `ntdll.dll`'s VAD is structurally suspicious. See [8.1.05 The User-Mode Ecosystem and Call Stack](./8.1.05_The_User_Mode_Ecosystem_and_Call_Stack.md) for the call-stack analysis approach.

### 3.2 Indirect Syscall Execution
A refinement of direct syscalls. Instead of executing `syscall` from within the malware's own code segment (which leaves a telltale unbacked return address), the malware jumps to the `syscall` instruction *inside* `ntdll.dll`, reusing the legitimate `syscall; ret` gadget that exists at the end of every Nt-function stub. This way, from ETW-TI's perspective, the syscall originates from inside `ntdll.dll`, satisfying stack-walk heuristics.

* **Detection angle**: Indirect syscalls are significantly harder to detect via stack walking alone. Detection shifts to correlating the syscall behavior (e.g., a process writing to another process's memory) with the absence of corresponding hook-emitted telemetry.

### 3.3 Unhooking by Restoration
The malware locates `ntdll.dll`'s file on disk, reads the fresh bytes of the affected function prologues, and overwrites the in-memory (hooked) prologues with the clean disk bytes. After restoration, subsequent API calls execute the original, unhooked code path. Syscalls proceed normally, but the EDR's inspection routine is never invoked.

The standard technique reads `ntdll.dll` via `NtOpenFile` / `NtReadFile` rather than `CreateFileW` — because if `CreateFileW` is hooked, the EDR may flag the access pattern. Some implementations instead load a second, unhooked copy of `ntdll.dll` into a disposable memory region using `NtMapViewOfSection` and patch from there.

* **Detection angle**: Restoration writes into the `.text` section of `ntdll.dll`. ETW-TI's `ProtectVirtualMemory` provider emits events when memory protection is flipped to writable — the prerequisite for restoration — and the target address range (inside `ntdll.dll`) is a high-fidelity filter. EDRs that detect their own unhooking typically rely on this signal.

### 3.4 Hook Evasion via Alternate Paths
The most subtle category. Instead of removing the hook, the malware uses an API path the EDR did not hook. Common examples:

* Using `ZwXxx` variants when the EDR only hooked `NtXxx` (they resolve to the same syscall but have separate export entries in older `ntdll.dll` versions; in modern Windows they are aliased and share a prologue, so this evasion is less effective than it once was).
* Using legitimate Windows APIs that happen to reach the target behavior through an unhooked code path (e.g., using `NtCreateUserProcess` when the EDR only hooks `NtCreateProcessEx`).
* Using wrapped APIs whose implementations live in less-commonly-hooked DLLs (`kernelbase.dll` vs. `kernel32.dll`, or specific `advapi32.dll` exports).
* Calling directly into documented-but-uncommon RPC or COM interfaces to trigger the desired kernel behavior indirectly.

Alternate-path evasion does not leave a clean detection signal at the API layer. Detection must shift to behavioral analytics further up the kill chain.

## 4. Memory Integrity Signals

Because every bypass category either modifies hooked regions or executes code from unexpected locations, memory integrity checks are the closest thing to a universal detection primitive. Three signals recur across EDR implementations:

| Signal | What It Catches | Where to Find It |
| :--- | :--- | :--- |
| **`.text` section hash mismatch between in-memory `ntdll.dll` and the on-disk binary** | Inline hook restoration (Section 3.3); any foreign process patching of `ntdll.dll` | Live response: compare `!dh` output in WinDbg against fresh file read. EDR self-check routines. |
| **Syscall execution from unbacked memory (RWX or RX with no backing file)** | Direct syscalls executed from malware's own code segments (Section 3.1) | ETW-TI thread stack walks; Volatility `malfind` on memory dumps. |
| **`VirtualProtect` calls targeting `ntdll.dll` `.text` range** | Unhooking preparations | ETW-TI `Microsoft-Windows-Threat-Intelligence` `ProtectVirtualMemory` events. |

The practical reality is that any individual signal can be defeated — the integrity check can be disabled if the attacker reaches kernel-mode, the stack walk can be evaded with indirect syscalls, the `VirtualProtect` event can be missed if ETW is tampered with. Defense-in-depth requires all three signals to be consumed and correlated, not treated as independent detections.

## 5. Interaction with AMSI and Script-Host Scanning

EDR hooks and AMSI (see [8.1.28 AMSI and Script Scanning Architecture](./8.1.28_AMSI_and_Script_Scanning_Architecture.md)) are architecturally complementary: AMSI scans content at the scripting-host layer, EDR hooks scan behavior at the API layer. A PowerShell payload that bypasses AMSI still has to call Win32 APIs to do anything useful, at which point the EDR's hooks engage.

This complementarity is why modern malware frequently combines an AMSI bypass with an unhooking routine. The two bypasses operate on different mechanisms, but both share the same precondition: code execution inside the target process. Either bypass on its own is significant; their combination in a single payload is a strong indicator that the attacker has designed for a mature detection stack.

## 6. Operational Implications for Detection Engineering

Three principles follow from the mechanics above.

First, EDR telemetry is a signal of *what the EDR was able to see*, not a ground truth of *what happened*. An absence of telemetry does not equal an absence of activity. Detection rules should be designed with awareness of which hooks the EDR relies on and which evasion categories those hooks are vulnerable to.

Second, integrity signals (Section 4) are a different detection layer than behavioral signals and should be treated as such. A rule that alerts on `ntdll.dll` `.text` modification catches a class of evasions that no amount of behavioral analytics will catch, and vice versa. Both layers need rules.

Third, the correlation window between a memory-integrity event and a behavioral event is small. An unhooking routine followed immediately by a suspicious API call is the signature; the unhooking event alone is ambiguous (it could be a legitimate compatibility shim or a security product in a weird state) and the API call alone (after unhooking) may produce no EDR telemetry at all. Rules that correlate across the two layers produce the highest signal density.
