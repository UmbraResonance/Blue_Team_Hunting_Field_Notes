# 8.1.33 PowerShell Language Modes and Policy Enforcement

> **Core Principle**: PowerShell is not a single language — it is a **family of restricted dialects** selected at runtime per-session, controlled by the process-level variable `$ExecutionContext.SessionState.LanguageMode`. In its unrestricted form (`FullLanguage`), it has access to the entire .NET runtime. In its most restricted form (`NoLanguage`), it cannot execute arbitrary code at all. **Constrained Language Mode (CLM)** sits between — PowerShell's answer to the reality that a general-purpose scripting runtime installed on every Windows host is a gift to attackers. CLM is not enabled by default; it activates automatically when an application control policy (WDAC or AppLocker in Allow mode) is in force on the system.
>
> **Blue Team Impact**: Understanding language modes tells you (a) what PowerShell-based TTPs are structurally blocked vs. what merely produces telemetry, (b) why `$ExecutionContext.SessionState.LanguageMode` is an essential single-line triage check during incident response, (c) where the gaps are — the documented bypass paths that turn CLM back into `FullLanguage` — and (d) how to detect enforcement drift, where CLM should be active but isn't. For detection engineers, CLM is the closest PowerShell has to a kernel mitigation: when on, most offensive tooling simply doesn't work.

---

## 1. The Four Language Modes

PowerShell defines four language modes. Each restricts what scripts can do by progressively disabling language features, cmdlets, and .NET type access.

| Mode | Full .NET Access | `Add-Type` | `Invoke-Expression` | Non-allowlisted cmdlets | Typical Context |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`FullLanguage`** | ✓ | ✓ | ✓ | ✓ | Default on unmanaged hosts; admin interactive sessions |
| **`RestrictedLanguage`** | ✗ | ✗ | ✗ | Limited | DSC configuration parsing; data sections |
| **`ConstrainedLanguage`** | Limited to allowlist | ✗ | ✗ | Limited | Hosts with WDAC or AppLocker policy enforcement |
| **`NoLanguage`** | ✗ | ✗ | ✗ | ✗ | Runspaces created programmatically with language disabled |

### 1.1 `FullLanguage` — The Default
On any standard Windows installation without application control, PowerShell runs in `FullLanguage`. This means:
- Arbitrary .NET type instantiation: `[System.Net.WebClient]::new().DownloadString(...)` works.
- `Add-Type -TypeDefinition` compiles and loads arbitrary C# code.
- `[System.Reflection.Assembly]::Load($bytes)` — the reflective loading path covered in [8.1.31](./8.1.31_CLR_and_In_Memory_Assembly_Loading.md).
- Win32 APIs via P/Invoke through `Add-Type`.
- COM object creation via `New-Object -ComObject`.

Essentially every PowerShell-based offensive technique assumes `FullLanguage`. This is not a design flaw — it is the deliberate capability profile for a general-purpose administration shell. The question is what happens when that profile is inappropriate.

### 1.2 `ConstrainedLanguage` — The Defensive Mode
`ConstrainedLanguage` restricts PowerShell to a curated set of allowed operations:

- Only "approved" .NET types can be used (primitives, strings, basic collections, `System.IO.Path`, `System.Management.Automation.*`).
- `Add-Type` is blocked entirely.
- `Invoke-Expression` is blocked.
- COM object creation (`New-Object -ComObject`) is blocked.
- Reflection-based type loading (`Assembly.Load`, `GetType` of arbitrary types) is blocked.
- Unsigned scripts outside the allowlist cannot promote themselves to `FullLanguage`.

The allowlist of types is hardcoded into PowerShell itself. It is deliberately minimal — enough for typical administration cmdlets to function, insufficient for offensive tooling to operate.

### 1.3 `RestrictedLanguage` — The Configuration Mode
`RestrictedLanguage` is more restrictive than `ConstrainedLanguage`: only a small set of cmdlets, no variable expressions beyond simple parameters, no loops or conditionals with arbitrary expressions. Primarily used by Desired State Configuration (DSC) for parsing configuration blocks.

Rarely encountered in malware analysis because it is unsuitable for general scripting.

### 1.4 `NoLanguage` — Embedded Host Mode
`NoLanguage` exists for programmatic runspaces where only pre-compiled cmdlets should be callable, with no script parsing at all. A developer embedding PowerShell in their application might create a `NoLanguage` runspace to expose specific functionality without risk.

Encountered almost never in malware analysis.

## 2. How Constrained Language Mode Gets Activated

CLM is not something administrators typically enable directly. It activates **automatically** as a consequence of system-wide application control policy. Understanding this automatic activation is essential for detection engineering.

### 2.1 WDAC (Windows Defender Application Control)
When a WDAC policy is deployed and in "enforce" mode on a host, PowerShell detects this at session startup by querying the code integrity state. If WDAC is enforcing code integrity on user-mode code (UMCI), PowerShell activates CLM for all non-allowlisted scripts.

The check is performed via the `WldpGetLockdownPolicy` API in `wldp.dll` (Windows Lockdown Policy). PowerShell calls this and acts on the result.

### 2.2 AppLocker in Allow Mode
Before WDAC, AppLocker provided the same effect. If AppLocker policy is configured to enforce DLL rules (including script rules) in **Allow mode** (allowlist), PowerShell activates CLM.

Modern systems typically use WDAC; AppLocker remains supported but is considered legacy.

### 2.3 The `__PSLockdownPolicy` Environment Variable
Historically, Microsoft exposed a developer-facing environment variable `__PSLockdownPolicy` that could force CLM without full application control. Setting this environment variable to `4` enables CLM process-wide.

This mechanism exists primarily for testing and should not be treated as a production security control. However, it is occasionally seen in hardened enterprise configurations as a defense-in-depth measure.

### 2.4 Per-Session Activation
Individual runspaces can be created with CLM directly:
```csharp
var config = InitialSessionState.CreateDefault();
config.LanguageMode = PSLanguageMode.ConstrainedLanguage;
var runspace = RunspaceFactory.CreateRunspace(config);
```
Applications embedding PowerShell often do this to limit what scripts they host can do. Exchange's compliance search, JEA (Just Enough Administration), and some SCCM components use this approach.

### 2.5 The Trust Boundary
CLM is **per-process** and **per-session**. A `FullLanguage` process can spawn a child `powershell.exe` that also runs `FullLanguage` if no policy is in effect. CLM does not propagate across process boundaries on its own — it propagates because the same WDAC policy applies to the child process at its startup check.

This means that detection engineers cannot assume CLM is active on a host without checking. The best check is the script itself querying `$ExecutionContext.SessionState.LanguageMode`.

## 3. Why CLM Breaks Offensive Tooling

The specific restrictions in CLM map almost exactly to the capabilities offensive PowerShell tooling depends on.

| Offensive Technique | CLM Effect |
| :--- | :--- |
| **Reflective .NET loading** (`Assembly.Load($bytes)`) | Blocked — `[Reflection.Assembly]` is not in the allowlist |
| **P/Invoke via `Add-Type`** | Blocked — `Add-Type` is unavailable |
| **COM Automation attacks** (`New-Object -ComObject WScript.Shell`) | Blocked — `-ComObject` parameter is unavailable |
| **Direct syscalls via dynamic compilation** | Blocked — cannot compile C# at runtime |
| **AMSI bypass via `amsiInitFailed` reflection** | Blocked — reflection on non-allowed types is blocked |
| **`Invoke-Expression` of decoded content** | Blocked — `IEX` is unavailable |
| **Cobalt Strike PowerShell stagers** | Blocked — all staging techniques depend on one of the above |
| **Empire / PowerShell Empire** | Blocked — framework architecture assumes FullLanguage |
| **PowerSploit / PowerView** | Mostly blocked — core functions depend on reflection |
| **Legitimate admin scripting** | Mostly works if using standard cmdlets |
| **Reading event logs, querying AD, managing services** | Works — these use native cmdlets |

The asymmetry is deliberate. CLM restricts what *scripts* can do without restricting what *compiled cmdlets* can do. Microsoft's security team and the PowerShell team explicitly designed the allowlist to cover most legitimate administration while defeating most offensive tooling.

### 3.1 The Detection Angle
If a host has CLM enforced, a huge category of PowerShell-based attacks simply fail silently or produce explicit errors. The *attempts* still produce PowerShell Event 4104 telemetry — the script block was parsed and attempted — but execution stops at the policy check.

This means Event 4104 content on a CLM-enforced host is *richer* for defenders than on an unrestricted host: the attacker's intent is fully logged, but the payload never fires. Hunting for 4104 events mentioning `Add-Type`, `[Reflection.Assembly]`, or `-ComObject` on CLM-enforced hosts produces high-fidelity attempted-attack alerts without the noise of successful admin scripting.

## 4. Documented Bypass Paths

CLM is robust but not invincible. Four structural bypass paths are publicly documented. Understanding them is essential for accurate detection engineering.

### 4.1 PowerShell v2 Downgrade
Windows retains `powershell.exe` v2.0 engine compatibility on many systems for backward compatibility with legacy scripts. PowerShell v2 **predates CLM** — it has no concept of language modes and always runs with full capability.

If v2 is still available on the host (`powershell.exe -Version 2`), an attacker can explicitly launch it to obtain an unrestricted PowerShell session regardless of policy.

**Detection**:
- Event 4103 / 4104 with `EngineVersion = 2.0`
- Sysmon EID 1 command line containing `-Version 2` or `-v 2`
- Loaded modules include `System.Management.Automation.dll` from a v2 path

**Remediation**: Remove PowerShell v2 entirely via Windows Features. This is considered a baseline hardening step and should be part of any PowerShell security posture.

### 4.2 Runspace Escape
PowerShell allows programmatic creation of new runspaces with explicitly specified language modes. If the attacker can execute *any* code in `ConstrainedLanguage` (even the limited operations permitted), they might be able to construct a new runspace object and invoke code inside it with `FullLanguage` — because the runspace creation API is in the type allowlist.

Historically, several such paths existed. Microsoft has patched most of them, but the general pattern remains: any API in the allowlist that indirectly provides access to `PSLanguageMode` configuration is a potential escape path.

**Detection**: Specific escape techniques have specific signatures; these are moving targets. Microsoft's PSScriptAnalyzer and the PowerShell security team periodically publish known bypass patterns.

### 4.3 Signed-Script Trust Abuse
WDAC policies typically allow execution of Microsoft-signed scripts in `FullLanguage`. If an attacker can inject malicious code into a Microsoft-signed script that is then invoked in `FullLanguage` context, CLM restrictions are bypassed.

Several public attacks of this form exist — typically abusing legitimate Microsoft scripts that accept scriptblock parameters or dot-source behavior.

**Detection**: Monitoring which Microsoft-signed scripts are executed, and which parent processes invoke them in unexpected patterns. This is a configuration-hygiene problem as much as a detection problem — organizations should enumerate which signed scripts their WDAC policy permits and audit for abuse patterns.

### 4.4 COM Server Loading
Some .NET COM servers can be loaded even in CLM via `New-Object` with an allowed COM-registered class. If a COM server itself provides reflection or code-execution functionality, CLM can be bypassed at the COM layer.

This is related to the COM Automation architecture covered in [8.1.30](./8.1.30_COM_Automation_and_IDispatch_Interface.md) — the attacker uses a COM object as the execution vehicle because the COM object itself runs outside CLM's type restrictions.

## 5. The Triage Check

Regardless of what detection infrastructure is available, a one-line check resolves the most important question during incident response:

```powershell
$ExecutionContext.SessionState.LanguageMode
```

This returns one of the four modes. During IR on a suspected compromise:

- **`FullLanguage` on a host that should have CLM** → enforcement drift. WDAC policy may have been removed, corrupted, or bypassed. Treat as a defensive gap, not yet as an active compromise indicator.
- **`FullLanguage` on a host that never had CLM** → baseline; evaluate based on other indicators.
- **`ConstrainedLanguage`** → policy is active; any attack attempts should be visible in 4104 logs as failed operations.

This check should be part of any PowerShell-involved incident response playbook. It takes one second and provides categorical context for everything else.

## 6. The 4104 Log Perspective

PowerShell Script Block Logging (Event ID 4104, see [1.3 Windows Event Core](../../01_Hunting_Cheatsheets/1.3_Windows_Event_Core.md)) operates *before* language mode evaluation. Every parsed script block is logged, regardless of whether it subsequently executes successfully.

This produces a useful asymmetry:

| Event | On `FullLanguage` host | On `ConstrainedLanguage` host |
| :--- | :--- | :--- |
| Attacker runs `[Reflection.Assembly]::Load(...)` | 4104 logs the script; execution succeeds | 4104 logs the script; execution fails with language mode error |
| Attacker runs `IEX $decoded` | 4104 logs the decoded content; execution succeeds | 4104 logs the decoded content; execution fails |
| Attacker runs `Add-Type -TypeDefinition "..."` | 4104 logs the C# source; compilation succeeds | 4104 logs the C# source; `Add-Type` not available error |

On a CLM host, **the attacker's intent is logged but the outcome is neutralized**. This is exactly the desirable state: full defensive visibility plus attack prevention.

The corresponding ETW event for the failure is in the PowerShell operational log (Event ID 4100 — Executing Pipeline errors) or in the Security log via AppLocker / WDAC block events (EventID 8028 / 3077 in `Microsoft-Windows-CodeIntegrity/Operational`).

## 7. Detection Engineering Summary

Specific detection rules belong in `01_Hunting_Cheatsheets/1.1_Master_Hunting_Matrix.csv` and `1.3_Windows_Event_Core.md`. This document provides the architectural understanding behind them.

### 7.1 Core Detection Patterns
- **Enforcement drift**: Host that previously reported `ConstrainedLanguage` now reports `FullLanguage` → WDAC/AppLocker policy failure or tampering.
- **PowerShell v2 invocation**: Any launch with `-Version 2` on a system where v2 has not been intentionally preserved.
- **4104 content on CLM host**: High-value signal because attempts produce log content without execution risk.
- **Language mode drift mid-session**: `$ExecutionContext.SessionState.LanguageMode` changing from `ConstrainedLanguage` to `FullLanguage` within the same session — indicates active bypass in progress.

### 7.2 The Broader Context
CLM is one mitigation in a broader PowerShell security stack:
- **Script Block Logging (4104)** — visibility
- **Constrained Language Mode** — restriction
- **Just Enough Administration (JEA)** — privilege limitation
- **AMSI** — content scanning (see [8.1.28](./8.1.28_AMSI_and_Script_Scanning_Architecture.md))

Each layer catches different classes of attack. Mature defense deploys all four; understanding each independently clarifies what is and isn't caught by which.

---

## 8. Summary: The Four Invariants

Regardless of attacker technique:

1. **CLM is process-level and session-level.** Every new session re-evaluates policy at startup; per-process state is independent.
2. **CLM is triggered by external policy (WDAC / AppLocker), not by PowerShell configuration.** Turning CLM "on" means deploying application control.
3. **Event 4104 logs pre-execution.** Attack intent is logged even when CLM blocks execution.
4. **Four bypass paths exist structurally** — v2 downgrade, runspace escape, signed-script abuse, COM layer — and each has specific remediation. Policy hardening addresses all four.

For the detection engineer, these invariants mean CLM is a high-value defense when correctly deployed, and enforcement drift is itself a critical signal worth monitoring.
