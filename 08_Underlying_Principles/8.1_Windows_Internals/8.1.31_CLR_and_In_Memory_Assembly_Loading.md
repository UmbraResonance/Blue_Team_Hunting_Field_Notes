# 8.1.31 CLR and In-Memory Assembly Loading

> **Core Principle**: The Common Language Runtime (CLR) is a user-mode virtual machine hosted inside any process that executes .NET code. Unlike native PE loading, the CLR can load and execute an **entire assembly from a byte array in memory** — without ever writing a file to disk, without invoking the Windows loader's image-load path, and without producing a Sysmon Event 7 (Image Load) for the payload itself. This capability, exposed through `System.Reflection.Assembly.Load(byte[])`, is the architectural foundation of "fileless" .NET execution techniques including Cobalt Strike's `execute-assembly`, PowerShell reflective loading, and nearly every modern C2 post-exploitation toolkit.
>
> **Blue Team Impact**: Understanding the CLR's load path tells you (a) why a PowerShell process can execute a full C# binary without any on-disk artifact, (b) why AMSI's .NET integration (since 4.8 / Windows 10 1709) is the single most important defensive signal for this class of activity, and (c) why native-process CLR hijacking (a `notepad.exe` loading `clr.dll`) is a high-fidelity injection indicator. The choice between detecting at the AMSI layer vs. the CLR-hosting layer vs. the ETW `DotNETRuntime` layer depends on knowing what each layer sees — which is what this document provides.

---

## 1. What the CLR Is (and What It Is Not)

The CLR is not the "framework libraries" — it is the **execution engine** that loads, verifies, JIT-compiles, and runs .NET assemblies. It is implemented primarily in `clr.dll` (for .NET Framework) or `coreclr.dll` (for .NET 5+, formerly .NET Core).

The distinction matters for analysis because:

- When a process is said to "host the CLR," it means `clr.dll` (or `coreclr.dll`) has been loaded into its address space and initialized.
- `powershell.exe` is a native executable — its `main()` is native C++ — but it hosts the CLR to execute PowerShell scripts (which are compiled to .NET IL at runtime).
- `notepad.exe` is a native executable and does **not** normally host the CLR. If `clr.dll` appears in `notepad.exe`'s loaded modules, something has deliberately injected .NET execution into it.

### 1.1 The Two .NET Families
Since 2020, two CLR families coexist on modern Windows:

| Family | Runtime DLL | Hosting processes | Notes |
| :--- | :--- | :--- | :--- |
| **.NET Framework** (1.0 – 4.8.x) | `clr.dll` | `powershell.exe` (Windows PowerShell 5.1), most legacy enterprise apps | Still shipped with Windows; not going away |
| **.NET 5+** (formerly .NET Core) | `coreclr.dll` | `pwsh.exe` (PowerShell 7+), modern cross-platform apps | Sits side-by-side with Framework |

Malware analysis in 2024–2026 encounters both. `powershell.exe` (the default on every Windows installation) still uses `.NET Framework` / `clr.dll` — which is why most detection content focuses on `clr.dll`. Targeted campaigns and modern red-team tooling increasingly use `coreclr.dll` for cross-platform payloads.

### 1.2 CLR Hosting API
Any native process can host the CLR by calling the CLR hosting API (primarily `ICLRMetaHost` and `ICLRRuntimeHost`). This is a documented Microsoft interface used by legitimate applications (SQL Server, IIS, Office) to embed .NET execution. The same API is used by malicious loaders that want to execute .NET payloads from a non-.NET process.

The important architectural point: hosting the CLR is a **one-way door**. Once `clr.dll` is loaded into a process, the process can execute arbitrary .NET code for the remainder of its lifetime. There is no unload path in practice.

## 2. The Assembly Load Paths

A .NET assembly (`.exe` or `.dll` containing .NET IL) can enter the CLR through several paths, each with different telemetry consequences.

### 2.1 Standard Load Paths (Visible)

| Load Path | API | Telemetry |
| :--- | :--- | :--- |
| **From file path** | `Assembly.LoadFrom(string)`, `Assembly.LoadFile(string)` | Sysmon EID 7 (Image Load); `ImageLoaded` field shows the .NET assembly file |
| **By assembly name from GAC** | `Assembly.Load(AssemblyName)` | Sysmon EID 7 for the GAC'd DLL |
| **Standard .NET application startup** | OS loader + CLR startup | Sysmon EID 7 for the main `.exe` |

In all three cases, there is a file on disk, and the standard loader path executes. Defender telemetry looks identical to native binary loading.

### 2.2 The Fileless Path: `Assembly.Load(byte[])`

The critical API for malware analysis is `System.Reflection.Assembly.Load(byte[] rawAssembly)`. It takes a byte array containing a full PE-formatted .NET assembly and loads it directly into the CLR.

```csharp
byte[] payload = /* obtained from anywhere: network, decoded blob, embedded resource */;
Assembly asm = Assembly.Load(payload);
Type entry = asm.GetType("Payload.Main");
MethodInfo m = entry.GetMethod("Run");
m.Invoke(null, new object[] { args });
```

What makes this path forensically significant:

- **No `CreateFile` on the payload.** The bytes come from memory; the OS file system is never involved.
- **No Sysmon Event 7 for the payload.** The standard loader path is bypassed; `LoadLibrary` is never called on the in-memory assembly.
- **No on-disk Amcache or ShimCache entry.** Application compatibility tracking (see [8.1.19](./8.1.19_Application_Compatibility_Subsystem.md)) relies on file-system writes; fileless assemblies leave none.
- **No Authenticode check.** The CLR does not verify signatures on byte-array assemblies — there is no file to attach a signature to.

The assembly is loaded, verified against the CLR's type-safety rules, JIT-compiled to native code, and executed — all within the hosting process's memory space.

### 2.3 Variant: `Assembly.Load` via Reflection from PowerShell
PowerShell can invoke this API directly because it has full CLR access:

```powershell
$bytes = [System.IO.File]::ReadAllBytes("C:\temp\payload.dll")  # or from a network stream
$asm = [System.Reflection.Assembly]::Load($bytes)
$asm.GetType("Payload.Main").GetMethod("Run").Invoke($null, @($args))
```

This is the canonical pattern for "reflective loading" of .NET payloads from PowerShell. From the OS perspective, `powershell.exe` simply continues running — no new process, no new module load for the payload.

## 3. The CLR's Internal Load Sequence

When `Assembly.Load(byte[])` is called, the CLR performs these steps internally:

1. **PE header parsing.** The byte array is validated as a PE file, and the CLR header (the `IMAGE_COR20_HEADER` in data directory 14) is located. See [8.1.15 Portable Executable Architecture](./8.1.15_Portable_Executable_Architecture.md) for PE structure.
2. **Metadata table parsing.** The assembly's type definitions, method signatures, and references are decoded from the metadata streams.
3. **Assembly identity resolution.** The assembly's strong name (if any) and version are extracted. Duplicate-load checks are performed against already-loaded assemblies.
4. **AMSI scan (Windows 10 1709+, .NET 4.8+).** This is the critical defensive checkpoint — see §4.
5. **Type verification.** The CLR verifies that the assembly's IL is type-safe (unless verification is explicitly skipped via SkipVerification permissions).
6. **Method bodies registered.** Method bodies are not JIT-compiled yet; they are registered as lazy-compile stubs.
7. **First method invocation.** When a method is called, the JIT compiler converts its IL to native code on the fly. The native code is stored in a CLR-managed memory region within the hosting process's VAS (see [8.1.16 Virtual Address Space Architecture](./8.1.16_Virtual_Address_Space_Architecture.md)).

Steps 4 and 7 are the primary detection opportunities.

## 4. AMSI Integration with the CLR

Since .NET Framework 4.8 (shipped with Windows 10 1709), the CLR's assembly load path submits the byte array to AMSI for scanning before loading proceeds. This is the single most important defensive control for `Assembly.Load(byte[])` activity.

### 4.1 Where the Scan Happens
The AMSI call is located in `clr.dll`'s assembly load code, immediately after PE header validation but before type verification. The full byte content of the assembly is passed to `AmsiScanBuffer` via the standard AMSI interface described in [8.1.28 AMSI and Script Scanning Architecture](./8.1.28_AMSI_and_Script_Scanning_Architecture.md).

If the AMSI provider (typically Defender's `MpOav.dll`) returns `AMSI_RESULT_DETECTED` (≥ 0x8000), the CLR throws an exception and the assembly is not loaded. If the provider returns clean, loading proceeds normally.

### 4.2 Scope Limits
The CLR AMSI integration only applies to:

- **`Assembly.Load(byte[])`** — byte-array loads
- **`Assembly.LoadFile` / `LoadFrom`** in certain contexts where the assembly is deemed "user-loaded" rather than resolved through standard framework paths
- **PowerShell's `Add-Type`** when used with `-TypeDefinition` (which compiles and loads a new assembly)

It does **not** scan:

- Assemblies loaded from the GAC (trusted by definition)
- Already-loaded framework assemblies
- Assemblies loaded by .NET's internal startup path

### 4.3 The CLR-Specific Bypass Patterns
Because AMSI is invoked from user-mode `clr.dll`, the same class of bypass techniques applicable to PowerShell AMSI (see [8.1.28 §4](./8.1.28_AMSI_and_Script_Scanning_Architecture.md)) applies here:

- **Memory patching of `AmsiScanBuffer`**: neutralizes all AMSI scans in the process, including CLR-originated scans.
- **Hardware breakpoint + VEH bypass**: same primitive, same effect.
- **`amsi.dll` unload or non-loading**: if the attacker can prevent `amsi.dll` from loading into the process, no scan can occur. Some loaders achieve this by patching the AMSI initialization call inside `clr.dll` itself to skip the scan path.
- **Pre-existing .NET processes without 4.8**: if the target process is running .NET Framework 4.7.2 or earlier (rare in modern Windows but possible on server installations), no CLR AMSI integration exists.

### 4.4 Relationship to ETW
Independent of AMSI, the `Microsoft-Windows-DotNETRuntime` ETW provider emits events for assembly loads (see [8.1.04 ETW Architecture](./8.1.04_ETW_Architecture_and_Telemetry_Orchestration.md)). The relevant keyword is `AssemblyLoader` (`0x00000004`). This provider captures every assembly load — including byte-array loads — with fields indicating the assembly's identity and the load context. Unlike AMSI, ETW telemetry cannot be bypassed by patching `amsi.dll`; it requires tampering with the ETW subsystem itself (patching `EtwEventWrite` in `ntdll.dll`).

AMSI and ETW thus form complementary defensive layers: AMSI is higher-fidelity (content inspection) but easier to bypass; ETW is lower-fidelity (metadata only) but harder to suppress.

## 5. Detection Layers and Their Telemetry

For a `.NET`-based payload loaded via `Assembly.Load(byte[])`, four detection layers are available, each with different visibility.

### 5.1 Layer 1: CLR Hosting in Unusual Processes (Sysmon EID 7)
**What it sees**: `clr.dll` or `coreclr.dll` being loaded into a process that has no legitimate reason to host .NET.

**What it catches**: Native-process CLR hijacking. An attacker injects into `notepad.exe` and initializes the CLR to run .NET payloads.

**Blindness**: This layer sees the *hosting* of the CLR, not the execution of specific assemblies. If the attacker targets a process that already hosts the CLR (e.g., `powershell.exe`), this layer produces no signal.

Detection rules for this layer belong in `01_Hunting_Cheatsheets/1.1_Master_Hunting_Matrix.csv` (there is already an entry for `clr.dll` loading into native binaries — see the existing "Unmanaged PowerShell" row).

### 5.2 Layer 2: AMSI Scan Results (Defender / AMSI ETW provider)
**What it sees**: Every byte-array assembly passed to `Assembly.Load` (assuming .NET 4.8+ and AMSI integration active).

**What it catches**: Malicious assembly content matching AMSI provider signatures — including obfuscated Cobalt Strike beacons, Seatbelt, SharpHound, Rubeus, and most public .NET offensive tooling.

**Blindness**: AMSI bypasses (§4.3). Also blind to assemblies that load *before* AMSI initialization (rare in practice but possible in carefully-staged loaders).

Telemetry sources:
- `Microsoft-Antimalware-Scan-Interface` ETW provider — every scan submission
- Defender Event ID 1116 / 1117 — detections
- Defender Event ID 5007 — AMSI provider state changes

### 5.3 Layer 3: DotNETRuntime ETW (Assembly Load Events)
**What it sees**: Every assembly load — byte-array, file-path, or GAC — with metadata including the assembly's display name and load context.

**What it catches**:
- Anomalous assembly names (random GUIDs, `Unknown`, or names matching known offensive tooling patterns)
- Load context `LoadFromByteArray` — the specific context used by `Assembly.Load(byte[])`
- Assembly loads into unusual processes

**Blindness**: ETW can be tampered with from user mode (patching `EtwEventWrite` in `ntdll.dll`). Advanced malware does this; commodity malware typically does not.

The key keyword is `0x00000004` (AssemblyLoader) with event `AssemblyLoad`. `SilkETW` and similar tools enable this provider and log the events.

### 5.4 Layer 4: Behavioral (Post-Execution)
**What it sees**: The *consequences* of the assembly's execution — API calls, network connections, file writes, process creation.

**What it catches**: Everything the payload actually does, assuming the payload's behavior produces telemetry (syscalls, hooks, etc.).

**Blindness**: This layer doesn't identify the payload itself as a .NET assembly — it just sees the post-exploitation behavior. Useful for confirming impact; poor for attribution to .NET execution specifically.

## 6. The Common Attack Patterns

Three patterns dominate real-world `Assembly.Load(byte[])` abuse. Understanding them clarifies what detection layers actually matter.

### 6.1 PowerShell Reflective Loading
PowerShell reads bytes (from disk, network, or registry) and calls `[Reflection.Assembly]::Load($bytes)`. This is the pattern used by:

- Custom PowerShell loaders built by red teams
- Empire and similar C2 frameworks' PowerShell stagers
- Living-off-the-land tooling that wraps .NET payloads in PowerShell

**Primary detection**: AMSI (Layer 2) catches the payload content. PowerShell 4104 (Layer 2 adjacent) logs the `[Reflection.Assembly]::Load` invocation in the deobfuscated script block. Both fire reliably when the attacker has not bypassed AMSI.

### 6.2 Cobalt Strike `execute-assembly`
Cobalt Strike's `execute-assembly` command:

1. Spawns a sacrificial process (default: `rundll32.exe`, configurable via the malleable C2 profile).
2. Injects a custom .NET hosting loader into the sacrificial process.
3. The loader initializes the CLR, reads the .NET assembly from the beacon's command buffer, and calls `Assembly.Load(byte[])`.
4. The assembly's entry point executes; output is captured and returned via the beacon channel.
5. The sacrificial process may be terminated or reused.

**Primary detection**:
- Layer 1 (CLR hosting): `clr.dll` loading into `rundll32.exe` — the default `execute-assembly` sacrificial process normally has no reason to host the CLR.
- Layer 3 (ETW): Assembly load events in a short-lived `rundll32.exe` process, often with randomized or suspicious assembly names.
- Layer 2 (AMSI): Effective unless the beacon has already patched `amsi.dll` in the target process (common in mature Cobalt Strike usage).

### 6.3 PowerShell `Add-Type`
`Add-Type -TypeDefinition` compiles C# source code on the fly (using the CSC compiler in the temp directory) and loads the resulting assembly. This is used in PowerShell offensive tooling to embed C# code that can't easily be expressed in pure PowerShell — for example, calling Win32 APIs via `DllImport` or performing low-level memory operations.

**Primary detection**:
- Layer 2 (AMSI): scans the compiled assembly. Also, PowerShell 4104 captures the `Add-Type -TypeDefinition` source code pre-compilation, which AMSI also scans.
- Sysmon Event 1: `csc.exe` and `cvtres.exe` spawning from `powershell.exe` — the CSC compilation leaves distinctive process-creation artifacts.
- Layer 1/3: The compiled assembly is written to `%TEMP%` as a `.dll`, so file-write telemetry (Sysmon EID 11) and subsequent image load (Sysmon EID 7) both fire.

`Add-Type` is actually the *most visible* of the three patterns because it briefly touches disk. It is the reflective load path's noisy cousin.

## 7. Why Native Manual Mapping Evades This Entirely

For completeness: the techniques in this document cover **.NET assembly** loading via the CLR. Native PE loaders — Cobalt Strike's reflective DLL injection, manual-mapped C++ payloads, Hell's Gate-family direct-syscall loaders — do not touch the CLR at all. They operate at the native Windows loader level, covered in [8.1.10 Manual Mapping and IAT Reconstruction](./8.1.10_Manual_Mapping_and_IAT_Reconstruction.md).

This is architecturally significant: .NET in-memory loading has a specific defensive story (AMSI-for-CLR + DotNETRuntime ETW), while native manual mapping has a different one (memory integrity signals + ETW-TI). An attacker choosing between the two is in part choosing which defensive layer to bypass. Mature campaigns often combine both — a native loader manually-mapped into a target, which then hosts the CLR to execute a higher-level .NET payload.

---

## 8. Summary: The Four Invariants

Regardless of how a .NET payload is staged, these architectural facts cannot be hidden:

1. **Executing .NET code requires the CLR to be loaded.** `clr.dll` or `coreclr.dll` must be present in the process's module list.
2. **The CLR must JIT-compile IL to native code before execution.** The JIT output lives in a process-private, CLR-managed memory region — inspectable via memory forensics even when the source assembly is not on disk.
3. **`Assembly.Load(byte[])` invokes AMSI on modern systems.** Bypassing this requires explicit action (memory patching, provider tampering, or exploiting pre-4.8 runtimes).
4. **The `DotNETRuntime` ETW provider sees every assembly load.** Suppressing it requires tampering with `EtwEventWrite` in `ntdll.dll`.

These invariants mean that truly invisible .NET execution requires an attacker to successfully compromise *both* AMSI and ETW in the target process. Commodity malware does not achieve this; mature offensive tooling sometimes does.
