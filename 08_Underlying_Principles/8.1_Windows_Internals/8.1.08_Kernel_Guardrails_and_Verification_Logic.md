# Kernel Guardrails: The Final Audit (SSDT & Probing)

> **Core Principle**: The Kernel does not "blindly execute" Syscalls. It operates through a strict sequence of routing, memory validation, and access control before any physical execution occurs.

## 1. SSDT Routing & Bounds Checking (The Navigation Board)
When a Syscall enters the Kernel (via the `syscall` instruction), it carries a Syscall Number (SSN) in the `EAX` register. 
* **The Validation**: The Kernel uses the **SSDT (System Service Descriptor Table)** to map this SSN to a physical kernel function address. The *only* check here is a **Bounds Check**. If the SSN is out-of-range (e.g., higher than the maximum number of services), the Kernel rejects it (`STATUS_INVALID_SYSTEM_SERVICE`). 
* **Note**: SSDT does **NOT** check permissions. It simply routes the request to the corresponding kernel function (e.g., `NtReadVirtualMemory`).

## 2. Memory Probing (The Safety Barrier)
The Kernel never trusts user-provided memory pointers.
* **Probing**: It uses `ProbeForRead` and `ProbeForWrite` to ensure the application isn't tricking the Kernel into modifying **Kernel Space** memory.
* **Capturing**: Parameters are copied (Captured) from User Space into a Kernel-owned buffer to prevent **Time-of-Check to Time-of-Use (TOCTOU)** attacks.

## 3. Final Access Check (The Security Guard: Token vs. ACL)
Once the SSDT routes the execution flow inside the specific kernel function, this ultimate hurdle takes place.
1. **The Subject**: The Security Reference Monitor (SRM) identifies the calling process's **Access Token**.
2. **The Object**: The SRM checks the target object's **Security Descriptor (SACL/DACL)**.
3. **The Decision**: If the SID or Privileges in the Token do not satisfy the DACL's explicit requirements (e.g., lacking `PROCESS_VM_READ`), the Kernel returns `STATUS_ACCESS_DENIED` (0xC0000022).
