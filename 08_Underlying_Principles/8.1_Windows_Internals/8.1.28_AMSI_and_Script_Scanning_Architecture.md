# AMSI (Antimalware Scan Interface) and Script Scanning Architecture

> **Core Concept**: AMSI is a Microsoft-defined interface (`amsi.dll`) that allows scripting engines, applications, and OS components to submit in-memory buffers to a registered antimalware provider (most commonly Defender / `MsMpEng.exe`) for inspection **after** deobfuscation but **before** execution. It is the OS-level hook that closes the gap left by static file scanning when payloads are decoded, decompressed, or generated at runtime.
> **Blue Team Impact**: AMSI is the single most important user-mode defense against script-based and fileless malware (PowerShell, JScript, VBScript, .NET reflection, Excel 4.0 macros, WMI). Understanding its architecture is prerequisite to both trusting its verdicts and recognizing the precise mechanical patterns used to bypass it.

---

## 1. Technical Architecture

AMSI is not a scanner itself; it is a standardized broker. The actual scanning is performed by an Antimalware Product (AMP) registered as an AMSI Provider. This separation is deliberate: Microsoft publishes the interface, third-party AV/EDR vendors implement it, and scripting hosts consume it without needing to know which product is installed.

### 1.1 Component Layout

| Component | Role | Location |
| :--- | :--- | :--- |
| **`amsi.dll`** | The broker DLL loaded into the host process. Exposes the `AmsiScan*` API surface. | `C:\Windows\System32\amsi.dll` |
| **AMSI Host** | Any process that calls `AmsiInitialize` to request scanning (e.g., `powershell.exe`, `wscript.exe`, `mshta.exe`, Office applications). | Varies |
| **AMSI Provider** | COM in-process server implementing the `IAntimalwareProvider` interface. For Defender, this is `MpOav.dll`. | `C:\ProgramData\Microsoft\Windows Defender\Platform\...\MpOav.dll` |
| **AM Engine** | The actual scanning engine (`MpEngine.dll`) running inside the `MsMpEng.exe` service, which the provider forwards buffers to via RPC. | `MsMpEng.exe` |

### 1.2 Provider Registration
AMSI providers register themselves in the registry under:
`HKLM\SOFTWARE\Microsoft\AMSI\Providers\{GUID}`
The GUID maps via `HKLM\SOFTWARE\Classes\CLSID\{GUID}` to the provider DLL path. When a host calls `AmsiInitialize`, `amsi.dll` enumerates these entries and loads the registered provider DLL in-process. This is a standard COM `InprocServer32` activation — see [8.1.06 COM Architecture and Registry Ledger](./8.1.06_COM_Architecture_and_Registry_Ledger.md) for the underlying mechanism.

## 2. The Core API Surface

A compliant AMSI host follows a strict four-stage lifecycle. Each stage corresponds to an exported function in `amsi.dll`:

| API | Purpose |
| :--- | :--- |
| **`AmsiInitialize`** | Called once per host. Loads the registered provider via COM and returns an `HAMSICONTEXT`. |
| **`AmsiOpenSession`** | Creates a session-scoped context (`HAMSISESSION`) that allows the provider to correlate multiple chunked scans from the same logical operation (e.g., a single script read line-by-line). |
| **`AmsiScanBuffer` / `AmsiScanString`** | The actual scan call. Submits a byte buffer (or wide-string) to the provider. Returns an `AMSI_RESULT` value indicating clean, detected, or blocked. |
| **`AmsiCloseSession` / `AmsiUninitialize`** | Teardown. |

### 2.1 AMSI_RESULT Semantics
The return value is not a boolean. It is a graded enum:
* `AMSI_RESULT_CLEAN` (0)
* `AMSI_RESULT_NOT_DETECTED` (1)
* `AMSI_RESULT_DETECTED` (>= 32768) — any value at or above this threshold is considered a detection by the host. The host is expected to abort execution of the scanned content.

This threshold semantic is architecturally important: a bypass does not need to return a specific "clean" constant. It only needs to ensure the returned value is **below** `0x8000`. Any patch that forces the return register to a small number succeeds.

## 3. Host Integration Patterns

Different AMSI hosts submit buffers at different points in their execution pipeline. Knowing *when* scanning occurs determines *what* telemetry a defender can expect.

### 3.1 PowerShell (`System.Management.Automation.dll`)
PowerShell submits buffers to AMSI **after** each script block is fully parsed and deobfuscated, but **before** it is compiled to IL and executed. This is why AMSI catches payloads that are decoded at runtime — the scan sees the cleartext script, not the `FromBase64String` wrapper. The integration point is the `AmsiUtils` class inside SMA, specifically the method that feeds every ScriptBlock into `AmsiScanBuffer`.

The consequence for detection: AMSI's verdict corresponds 1:1 with the content later logged by **Event ID 4104** (PowerShell Script Block Logging). If AMSI is bypassed silently, 4104 still fires — but the reverse is also true, and this is the critical forensic anchor. See [8.1.04 ETW Architecture and Telemetry Orchestration](./8.1.04_ETW_Architecture_and_Telemetry_Orchestration.md) for the `Microsoft-Windows-PowerShell` provider.

### 3.2 Windows Script Host (WSH) and MSHTA
`wscript.exe`, `cscript.exe`, and `mshta.exe` submit buffers before each VBScript/JScript block is passed to the scripting engine. The host integration is thinner than PowerShell's — less visibility into intermediate variables, but the full script body is still seen.

### 3.3 .NET Framework (CLR) and .NET Assembly Loading
Since .NET Framework 4.8, the CLR scans assemblies loaded via `Assembly.Load(byte[])` — the primary technique used by tools like Cobalt Strike's `execute-assembly`. The scan occurs inside `clr.dll` before the assembly metadata is parsed. This closes a long-standing gap where reflectively loaded .NET payloads executed entirely in memory without AV visibility.

### 3.4 Office VBA and Excel 4.0 Macros
Office applications integrate AMSI at the macro interpreter level. For VBA, every procedure body is scanned before execution. For Excel 4.0 (XLM) macros, each formula cell is scanned when evaluated.

### 3.5 WMI Scripting
`WmiPrvSE.exe` submits the text of WQL and CIM method invocations to AMSI. This is why modern WMI abuse has shifted away from direct `Invoke-WmiMethod` payload embedding and toward staged or externally-fetched payloads.

## 4. Bypass Mechanics

Because AMSI is a user-mode library loaded into the *same process* as the potentially malicious script, the process can modify `amsi.dll` in its own memory space. AMSI integrity is therefore trust-based within the host process, not enforced by the kernel. This design choice — acceptable at the time for performance and scripting-engine integration — is the root cause of every AMSI bypass technique.

Bypass techniques fall into four structural categories:

### 4.1 Memory Patching of `AmsiScanBuffer`
The most common and most durable bypass. The attacker locates the `AmsiScanBuffer` export in the process's mapped copy of `amsi.dll` and overwrites the prologue with instructions that return a benign value without performing a scan. A typical patch is three or four bytes:
```
mov eax, 0x80070057   ; E_INVALIDARG — a non-detection HRESULT
ret
```

The scan call returns immediately; `AmsiResult` is written as 0; the host treats the buffer as clean.

* **Required privilege:** None beyond what the host already has. The memory region must first be flipped from `PAGE_EXECUTE_READ` to writable via `VirtualProtect` — see [8.1.16 Virtual Address Space Architecture](./8.1.16_Virtual_Address_Space_Architecture.md) on the W^X principle.
* **Forensic signal:** Modification of the `.text` section of `amsi.dll` inside a script host process. Visible via memory scanning tools that compare in-memory pages against the on-disk image.

### 4.2 Forcing `amsiInitFailed = true`
PowerShell's `AmsiUtils` class caches a boolean field named `amsiInitFailed`. If this is `true`, subsequent scan calls are short-circuited. The attacker uses reflection to locate and flip the field:
```powershell
[Ref].Assembly.GetType('System.Management.Automation.AmsiUtils').GetField('amsiInitFailed','NonPublic,Static').SetValue($null,$true)
```

This is the oldest documented bypass and is now aggressively signatured. Its forensic value for defenders is high: any obfuscated variant of the `amsiInitFailed` string appearing in a script block is a near-certain indicator of a bypass attempt.

### 4.3 Hardware Breakpoint (HWBP) Abuse
A more evasive variant that avoids modifying `.text` entirely. The attacker sets a DR0-DR3 hardware breakpoint on the entry of `AmsiScanBuffer`, registers a Vectored Exception Handler, and in the handler modifies the thread's `CONTEXT` (specifically `RAX` and `RIP`) to simulate a clean return. Because no memory is modified, memory-integrity scans see no anomaly. Detection must rely on ETW-TI or observing the thread's DR registers. Exception handling internals are covered in [8.1.27 Exception Handling and SEH/VEH Mechanics](./8.1.27_Exception_Handling_and_SEH_VEH_Mechanics.md).

### 4.4 Provider DLL Hijacking / Unregistration
An attacker with local administrator privilege can tamper with the provider registration in `HKLM\SOFTWARE\Microsoft\AMSI\Providers` — either pointing the CLSID to a null provider or removing the entry entirely. This bypass is loud (it requires admin, touches autoruns-visible registry keys, and breaks Defender telemetry) but is occasionally seen in ransomware staging phases.

### 4.5 Avoiding AMSI Entirely (Manual Mapping)
Unmanaged payloads (native C/C++/Rust) that never invoke a scripting host never trigger AMSI. This is the structural reason reflective DLL loading and manual mapping remain effective — they operate below the AMSI integration layer. See [8.1.10 Manual Mapping and IAT Reconstruction](./8.1.10_Manual_Mapping_and_IAT_Reconstruction.md).

## 5. Detection Engineering

AMSI's own telemetry lives in two places: the AMSI ETW provider and the Defender operational log.

### 5.1 ETW Provider
`Microsoft-Antimalware-Scan-Interface` (`{2A576B87-09A7-520E-C21A-4942F0271D67}`) emits an event for every scan submission. The event carries the session ID, content name (often a script block hash), scan result, and a truncated content hash. This is the most reliable source for post-hoc reconstruction of what was submitted to AMSI and what verdict was returned.

### 5.2 Windows Defender Operational Log
`Microsoft-Windows-Windows Defender/Operational`:
* **Event ID 1116** — Malware detected (includes the detection source; when source is AMSI, this confirms the payload was caught at the script layer).
* **Event ID 1117** — Action taken on detection.
* **Event ID 5007** — Configuration change (including AMSI provider disablement).

### 5.3 Bypass Detection Heuristics

| Heuristic | Signal |
| :--- | :--- |
| **PowerShell 4104 content referencing `amsiInitFailed`, `AmsiUtils`, `AmsiScanBuffer`** (even heavily obfuscated) | High-fidelity indicator of bypass attempt. |
| **`VirtualProtect` called against an address range inside `amsi.dll`** | Sysmon does not capture this directly; ETW-TI `Microsoft-Windows-Threat-Intelligence` `ProtectVirtualMemory` event does. |
| **`amsi.dll` `.text` section hash mismatch in memory vs. disk** | Memory forensics / live response. Requires either EDR memory integrity scanning or manual comparison via Volatility. |
| **Registry modification of `HKLM\SOFTWARE\Microsoft\AMSI\Providers`** | Sysmon Event 13 / Security 4657. Extremely high fidelity — legitimate modifications are rare outside AV updates. |
| **Defender Event 5007 reporting AMSI provider disabled** | Direct evidence of tampering. |
| **Script host process loading `amsi.dll` but never invoking `AmsiScanBuffer`** | Requires ETW-TI. Indicates the host was patched before the first scan could occur. |

## 6. Architectural Limits

Two structural properties of AMSI bound what it can and cannot do, and both matter for defenders setting realistic expectations.

First, AMSI operates in the same address space as the content it scans. There is no kernel-enforced boundary between the scanner and the scanned. Any bypass that successfully executes code before the first scan has won unconditionally. This is why AMSI is necessary but not sufficient — it must be paired with kernel-side telemetry (ETW-TI, Sysmon, EDR kernel callbacks) to close the window.

Second, AMSI scans content, not intent. A script that passes AMSI is not safe; it is merely not recognized by the provider's current signatures. High-entropy obfuscation that survives deobfuscation (rare but possible) or entirely novel payloads will receive `AMSI_RESULT_CLEAN` and proceed to execute.

These constraints position AMSI as the last well-lit room before the execution cliff — valuable, but not the final line of defense.
