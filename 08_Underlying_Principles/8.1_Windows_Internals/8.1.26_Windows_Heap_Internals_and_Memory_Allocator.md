# Windows Heap Internals and Memory Allocator Mechanics

> **Core Concept**: The heap is the user-mode region of a process's Virtual Address Space reserved for dynamic memory allocation of variable size. Unlike the stack (LIFO, fixed per-thread) or private `VirtualAlloc` regions (page-granular), heap allocations are managed by a user-mode allocator that sub-divides large memory blocks into small arbitrary-sized chunks on demand.
> **Blue Team Impact**: The heap is where most malware stores its *working data* after unpacking — decrypted configuration structures, decoded C2 payloads, reconstructed shellcode buffers, and cleartext credential material. Memory forensics that treats the heap as an opaque blob misses the majority of extractable IOCs. Understanding the allocator's structure is what makes carving decrypted strings and reconstructing in-memory objects feasible.

---

## 1. Technical Architecture: What "The Heap" Actually Is

A process does not have one heap. It has a **default process heap** (created at process start, retrievable via `GetProcessHeap()`) and zero or more **private heaps** that code creates on demand via `HeapCreate`. The CRT (C Runtime) of each loaded module often creates its own private heap, so a single process commonly has five to fifteen distinct heaps at any time.

Each heap is ultimately backed by one or more large `VirtualAlloc`-ed memory regions called **heap segments**. When the allocator runs out of space, it reserves a new segment from the VAS. This is the bridge between this document and [8.1.16 Virtual Address Space Architecture](./8.1.16_Virtual_Address_Space_Architecture.md): every byte the heap manages is physically backed by `VadPrivate` nodes in the process's VAD tree.

### 1.1 The Two Allocator Generations

Windows has shipped two fundamentally different heap implementations:

| Allocator | Introduced | Used In | Key Structure |
| :--- | :--- | :--- | :--- |
| **NT Heap** | Windows NT 3.1 | All processes pre-Windows 10; still the default for Win32 processes unless opted out | `_HEAP` structure, lookaside lists, Low Fragmentation Heap (LFH) |
| **Segment Heap** | Windows 10 (1703+) | UWP apps by default; selected Win32 processes (`csrss.exe`, `lsass.exe`, some Edge/Chromium components) | `_SEGMENT_HEAP` structure, backend heap, LFH, variable-size (VS) subsystem |

Both allocators share the same public API surface (`HeapAlloc`, `HeapFree`, `HeapReAlloc`), but their internal chunk layouts, metadata, and fragmentation mitigations differ substantially. For DFIR work, knowing which allocator a process uses determines which Volatility plugin and which chunk signature to apply.

### 1.2 Opt-In via Registry (Segment Heap)
A process can be promoted to Segment Heap by creating a value under:
`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options\<exe_name>\FrontEndHeapDebugOptions`
This IFEO-based mechanism is worth knowing because it uses the same registry subsystem as IFEO Debugger persistence (T1546.012) — modifications here are unusual outside of Microsoft-shipped configurations.

## 2. The NT Heap Structure

The NT Heap is what malware analysts encounter most often, because the overwhelming majority of Win32 malware runs in processes still using it.

### 2.1 The `_HEAP` Structure
Every NT Heap begins with a `_HEAP` header at the start of its first segment. The header contains:
* **`Signature`** — `0xEEFFEEFF`. Primary scanning signature for heap discovery in memory dumps.
* **`Encoding` / `EncodeFlagMask`** — an XOR key applied to chunk headers to catch corruption. Must be reversed before parsing chunks in Windows 7+.
* **`Segment` list** — doubly-linked list of `_HEAP_SEGMENT` structures covering all VAS regions owned by this heap.
* **`FreeLists`** — arrays tracking unallocated chunks by size class.
* **`FrontEndHeap`** — pointer to the Low Fragmentation Heap, if enabled.

### 2.2 Chunk Layout (Backend Heap)
A backend heap allocation consists of an 8-byte (x86) or 16-byte (x64) chunk header followed by the user's data:
```
+------------------+
| Size             |  (encoded: XOR with Heap->Encoding)
| PreviousSize     |
| SegmentOffset    |
| Flags            |  (BUSY=0x01, EXTRA_PRESENT=0x02, FILL_PATTERN=0x04, VIRTUAL_ALLOC=0x08, LAST_ENTRY=0x10)
| UnusedBytes      |
| SmallTagIndex    |
+------------------+
| User Data        |  <-- pointer returned by HeapAlloc points here
|    ...           |
+------------------+
```

For DFIR, the `BUSY` flag is the first filter: busy chunks hold live data, free chunks hold residual data that may still be forensically relevant but reflects the *previous* occupant.

### 2.3 The Low Fragmentation Heap (LFH)
The LFH is a front-end allocator that activates for a given size class after the backend heap has serviced 16 or more allocations of that size. It manages small allocations (<= 16 KB) in fixed-size buckets organized into **UserBlocks**. LFH chunks use a different, smaller header layout and are XOR-encoded with a per-UserBlock key.

The practical consequence: small, frequently-allocated structures — including most C2 command-and-control command buffers, encoded network beacons, and short decrypted strings — live in LFH UserBlocks, not in the backend heap. Volatility plugins that only walk the backend free/busy lists will miss them.

## 3. The Segment Heap Structure

The Segment Heap redesigns the allocator around four subsystems selected by allocation size:

| Subsystem | Size Range | Notes |
| :--- | :--- | :--- |
| **LFH** | ≤ 16 KB (after promotion) | Same concept as NT Heap LFH; different implementation. |
| **VS (Variable Size)** | ≤ 128 KB | Replaces the NT backend heap for mid-sized allocations. Uses a rb-tree of free blocks. |
| **Large Blocks** | > 128 KB | Direct `VirtualAlloc` backing; one VAD entry per allocation. |
| **Backend** | Reserved segments for VS and LFH metadata | Analogous to NT segments but organized differently. |

The Segment Heap is more resistant to classical heap-spray and heap-overflow exploitation techniques (which is why Microsoft moved security-critical processes like `lsass.exe` to it). For the defender, it means a memory dump of `lsass.exe` cannot be parsed with NT Heap structures — the wrong plugin produces silent garbage output, not a clear error.

## 4. Malware-Relevant Heap Behaviors

The heap is not just storage — it is the staging area for every runtime-assembled payload. Four patterns recur in malware analysis:

### 4.1 Decrypted Configuration and C2 Buffers
Malware that stores its configuration encrypted in the `.rdata` section (see [8.1.15 Portable Executable Architecture](./8.1.15_Portable_Executable_Architecture.md)) decrypts it at runtime into a heap-allocated buffer. The decrypted configuration — C2 URLs, campaign IDs, RC4 keys, mutex names — sits in the heap for the lifetime of the beacon.

For the analyst, this means a memory dump of the malicious process's heap, searched with standard string extraction followed by entropy filtering, is frequently the fastest path to IOC extraction. Volatility's `windows.heaps` and `windows.dumpheaps` plugins (when available for the target OS version) extract these buffers cleanly.

### 4.2 Decoded Network Payloads
Beacons that use HTTP or custom C2 protocols typically receive encrypted commands, decrypt them into a heap buffer, execute them, and free the buffer. Between decryption and free, the plaintext command resides in an LFH UserBlock. Because LFH memory is reused aggressively, the capture window is narrow — but freshly-freed LFH chunks retain their data until overwritten.

### 4.3 Heap Spraying (Exploitation Context)
In the exploit-development context, heap spraying is the technique of allocating large numbers of controlled-content heap chunks so that a later memory-corruption vulnerability has a high probability of redirecting execution into attacker-controlled data. Modern mitigations (LFH randomization, Segment Heap hardening, DEP, CFG) have reduced but not eliminated this technique. Relevant primarily to browser/Office exploit analysis rather than commodity malware.

### 4.4 Heap-Based Shellcode Staging
Some loaders (notably early-stage droppers embedded in Office documents) allocate an `HeapAlloc` buffer, copy shellcode into it, and then call `VirtualProtect` to promote that region to `PAGE_EXECUTE_READ`. This pattern leaves a distinctive artifact: an executable memory page whose backing VAD is `VadPrivate` but whose *contents* are physically inside the heap segment's VAD range. Volatility's `malfind` catches this when the region is still RWX; if `VirtualProtect` has downgraded it to RX (see [4.0 Common Malware Behaviors and TTPs](../../04_Malware_Analysis_Cheatsheets/4.0_Common_Malware_Behaviors_and_TTPs.md) Section 2 on "RW to RX Downgrade"), only heap-aware analysis catches it.

## 5. The Relationship Between Heap, VAD, and `_EPROCESS`

For forensic analysis, the chain from kernel object to user-space data is:

`_EPROCESS` → `VadRoot` → `VadPrivate` node → heap segment → `_HEAP` header → chunks → user data

This is why heap analysis is not separable from process analysis. A hidden process (see [8.1.17 EPROCESS and DKOM Mechanics](./8.1.17_EPROCESS_and_DKOM_Mechanics.md)) whose `_EPROCESS` has been unlinked is still discoverable by scanning for `0xEEFFEEFF` heap signatures and then back-referencing the containing VAD → `_EPROCESS`. This thread-backwards approach (scan for the heap, find the process) is occasionally the only path to recovering a rootkit's working data.

### 5.1 Pagefile Interaction
Heap pages, like all committed private memory, are eligible for paging to `pagefile.sys`. Long-running processes with idle heap regions (common in persistent beacons that sleep for hours) will have significant portions of their heap swapped out. See [8.1.24 Pagefile and Swapfile Mechanics](./8.1.24_Pagefile_and_Swapfile_Mechanics.md) — carving the pagefile for heap signatures occasionally recovers data that the live process no longer holds in RAM.

## 6. Detection Engineering and Forensic Workflow

Heap-level analysis is primarily a post-incident forensic activity rather than a real-time detection surface. The allocator does not emit telemetry, and there is no Sysmon event for `HeapAlloc`. The detection value sits in downstream ETW events and memory forensics artefacts.

### 6.1 Runtime Signals with Heap Implications

| Signal | Source | Heap Connection |
| :--- | :--- | :--- |
| `VirtualProtect` changing heap region to executable | ETW-TI `Microsoft-Windows-Threat-Intelligence` | Shellcode staging inside heap. |
| Large private-memory growth without corresponding file-backed image loads | Performance counters / EDR baseline | Unpacking or large payload decryption into heap. |
| High-entropy memory region inside a heap segment | Memory scanning | Encrypted/compressed payload staged but not yet decrypted, or decrypted shellcode. |

### 6.2 Post-Mortem Analysis Workflow

A structured approach to heap analysis during malware triage:

First, identify the target process and confirm which allocator it uses. Processes listed in the Segment Heap opt-in registry, plus all UWP apps, use Segment Heap; everything else typically uses NT Heap. Getting this wrong produces plausible-looking but meaningless output.

Second, acquire a full process memory dump or a full system memory image. `procdump -ma` and Volatility's `memdump` plugin cover the two common acquisition paths.

Third, enumerate heaps. For NT Heap, scan the dump for the `0xEEFFEEFF` signature and validate candidates by walking segment links. For Segment Heap, walk `_SEGMENT_HEAP` structures referenced from the PEB's `ProcessHeaps` array.

Fourth, extract busy chunks and apply content analysis: string extraction with length and entropy filters, YARA rules tuned for decrypted configuration formats of known malware families, and pattern matching against known C2 protocol headers.

Fifth, correlate findings with `VirtualProtect` events from ETW-TI to confirm which heap regions were ever marked executable — these are the highest-value targets for shellcode reconstruction.
