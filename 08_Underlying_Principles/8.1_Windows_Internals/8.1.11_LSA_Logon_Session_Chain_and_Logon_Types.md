# LSA Logon Session Chain and Logon Types

> **Core Concept:** A single user action (e.g., an RDP connection) does not produce a single 4624 event — it produces a deterministic *sequence* of logon sessions, each with its own LUID and LogonType. The LSA is the orchestrator of this sequence.
> **Blue Team Impact:** Hunting on a single LogonType in isolation (especially Type 10 for RDP) misses the source IP and true auth protocol. Correlating the full sequence via LogonId is the only reliable way to reconstruct remote access activity.

## 1. The LSA Logon Flow

When a user or process attempts to authenticate, the request moves through a specific architectural pipeline:

1.  **Winlogon.exe & LogonUI.exe:** For interactive logons, `Winlogon` handles the Secure Attention Sequence (SAS, e.g., Ctrl+Alt+Del) and spawns `LogonUI` to collect the actual credentials (PIN, password, biometrics).
2.  **LSASS.exe (Local Security Authority Subsystem Service):** The collected credentials are passed to LSASS. LSASS acts as the central routing hub for all authentication requests.
3.  **Authentication Packages (APs):** LSASS doesn't verify the credentials itself. It routes them to the appropriate AP. The primary packages are `Kerberos` (for domain authentication) and `MSV1_0` (for local authentication and NTLM fallback).

If the AP verifies the credentials successfully, LSASS generates an Access Token and creates a Logon Session.

## 2. The Essence of a Logon Session

A Logon Session is not just a log entry; it is a fundamental LSA-managed security structure, with its Access Token tracked as a kernel Executive Object.

* **LogonId (Locally Unique Identifier - LUID):** A 64-bit value guaranteed to be unique until the system reboots (e.g., `0x3E7` is always the SYSTEM account's logon session). This LUID is the primary key used to link authentication events to subsequent process creation (Event ID 4688) or object access (Event ID 4663) logs.
* **Access Token:** The primary security context attached to the session, detailing the user's SID, group memberships, and assigned privileges.
* **Credential Material:** Depending on the configuration (e.g., WDigest, Credential Guard), LSASS may cache plaintext passwords, NTLM hashes, or Kerberos TGT/TGS tickets associated with this session to facilitate single sign-on (SSO). This cached material is exactly what tools like Mimikatz target.

## 3. 4624 Event Sequence Fingerprints

Different tools and protocols interact with the LSA pipeline differently, resulting in distinct multi-event sequences rather than a single log entry.

### RDP with Network Level Authentication (NLA)
Modern RDP does not establish a UI session before authenticating. NLA forces authentication over CredSSP before the RDP connection is fully built.
* **Step 1:** The remote client authenticates at the network layer. This generates a **Logon Type 3 (Network)** event on the target.
* **Step 2:** After passing NLA, the Remote Desktop Services stack builds the interactive session, generating a **Logon Type 10 (RemoteInteractive)** event.
* *Note:* Disconnecting and reconnecting without logging off will generate a **Logon Type 7 (Unlock)**.

### `runas /netonly`
This command is heavily used by attackers to pass-the-hash or use alternate credentials without changing their local user context.
* **Fingerprint:** Generates a **Logon Type 9 (NewCredentials)**.
* **Under the hood:** It creates a "split" logon session. Locally, the process continues to run as the original user. However, when the process makes an outbound network request (e.g., accessing an SMB share), LSASS seamlessly substitutes the alternate credentials provided via the command.

### PsExec
PsExec chains three distinct logon sessions via SMB + SCM. For the full MSRPC/Named Pipe mechanics, see [8.1.13_Windows_Service_Control_Manager_Named_Pipes_Communication](./8.1.13_Windows_Service_Control_Manager_Named_Pipes_Communication.md).
* **Step 1 (Network):** SMB connection to `ADMIN$` → Logon Type 3 on target.
* **Step 2 (Service):** SCM spawns `PSEXESVC.exe` as SYSTEM → Logon Type 5.
* **Step 3 (Interactive, if `-i`):** Payload attached to `winsta0` → additional Logon Type 2.
### Local or RDP Session Restore
When a user locks their screen or disconnects an RDP session (leaving it active in the background), returning to it does not create a new Type 2 or Type 10 session.
* **Fingerprint:** Generates a **Logon Type 7 (Unlock)**. The existing LogonId is reused.

### WMI Remote Execution (wmic / Invoke-WmiMethod)
Unlike PsExec, WMI does NOT use SCM. The target process is spawned by `WmiPrvSE.exe` directly.
* **Fingerprint:** Logon Type 3 only. No Type 5 (no service created), no Type 2 (no interactive window).
* **Analytical Rule:** A Logon Type 3 from a remote host followed by `WmiPrvSE.exe` spawning `cmd.exe` / `powershell.exe` (Event 4688) is a cleaner signal than PsExec's SCM-heavy trail — which is precisely why adversaries prefer it.

## 4. The Correlation Imperative — Why Terminal Logon Types Are Always Downstream Evidence

A common structural pitfall in SOC operations is treating "terminal" logon events—such as Logon Type 10 (RemoteInteractive), Type 2 (Interactive), or Type 5 (Service)—as the starting point of an investigation. 

In the LSA architecture, terminal logon types merely represent the final execution state (e.g., rendering the desktop UI or launching a service binary). The actual network handshake, protocol negotiation, and source IP validation occur in the upstream pre-authentication phase, which is almost always logged as a preceding **Logon Type 3 (Network)** event.

**The Analytical Rule:** You cannot reliably extract true network origins (Source IP) or exact authentication protocols (NTLM vs. Kerberos) by looking at terminal logons alone. They are downstream evidence. You must hunt backwards.

### The RDP NLA Paradigm (Primary Example)
When Network Level Authentication (NLA) is enabled, the security negotiation happens before the RDP session is fully established. By the time the terminal **Type 10** event is generated, the `IpAddress` field is frequently masked with local loopback addresses (`127.0.0.1` or `::1`), or left blank. To find the attacker's real IP, you must query for the upstream **Type 3** event generated milliseconds prior for the same target user.

### Beyond RDP: PsExec and WMI
This correlation imperative applies across various lateral movement techniques:
* **PsExec:** The terminal **Type 5 (Service)** event for `PSEXESVC` will show `NT AUTHORITY\SYSTEM` starting a local service. To find the source of the lateral movement, you must correlate this back to the upstream **Type 3** event where the attacker authenticated to the `ADMIN$` or `IPC$` share via SMB.
* **WMI (WinRM):** Remote execution via WMI might manifest as process creation events or terminal logons under specific service accounts, but the true network source is tied to the upstream **Type 3** HTTP/RPC authentication.

### The Hunting Strategy
To operationalize this correlation:
1.  **User Context Linking (not LUID):** Upstream Type 3 and downstream Type 10/Type 5 events carry *different* LogonIds (they are distinct LSA sessions). Instead, correlate on matching `TargetUserName` + `TargetDomainName` + narrow time window. LUID is only useful for linking a session *forward* to its 4688/4663 children, not across the Type 3 → Type 10 boundary.
2.  **Time-Bounding:** Anchor on the terminal event (Type 10/Type 5) and search backwards within a 1-to-5 second window for a Type 3 event belonging to the same user context.
3.  **Protocol Extraction:** Rely *only* on the upstream Type 3 event to confirm if the attacker forced an NTLM downgrade (`NTLM V2`) or successfully used Kerberos (`Negotiate` resolving to Kerberos).
