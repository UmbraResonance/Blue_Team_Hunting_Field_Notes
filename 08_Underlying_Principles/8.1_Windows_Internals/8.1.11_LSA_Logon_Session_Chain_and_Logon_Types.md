# LSA Logon Session Chain and Logon Types

> **Core Concept:** A single user action (e.g., an RDP connection) does not produce a single 4624 event — it produces a deterministic *sequence* of logon sessions, each with its own LUID and LogonType. The LSA is the orchestrator of this sequence.
> **Blue Team Impact:** Hunting on a single LogonType in isolation (especially Type 10 for RDP) misses the source IP and true auth protocol. Correlating the full sequence via LogonId is the only reliable way to reconstruct remote access activity.

## 1. The LSA Logon Flow

When a user or process attempts to authenticate, the request moves through a specific architectural pipeline:

1.  **Winlogon.exe & LogonUI.exe:** For interactive logons, `Winlogon` handles the Secure Attention Sequence (SAS, e.g., Ctrl+Alt+Del) and spawns `LogonUI` to collect the actual credentials (PIN, password, biometrics).
2.  **LSASS.exe (Local Security Authority Subsystem Service):** The collected credentials are passed to LSASS. LSASS acts as the central routing hub for all authentication requests.
3.  **Authentication Packages (APs):** LSASS doesn't verify the credentials itself. It routes them to the appropriate AP. The primary packages are `Kerberos` (for domain authentication) and `MSV1_0` (for local authentication and NTLM fallback).

If the AP verifies the credentials successfully, LSASS generates an Access Token and creates a Logon Session.

## 2. The Essence of a Logon Session

A Logon Session is not just a log entry; it is a fundamental kernel-level security structure. Once LSASS validates the credentials, it establishes a session characterized by three critical components:

* **LogonId (Locally Unique Identifier - LUID):** A 64-bit value guaranteed to be unique until the system reboots (e.g., `0x3E7` is always the SYSTEM account's logon session). This LUID is the primary key used to link authentication events to subsequent process creation (Event ID 4688) or object access (Event ID 4663) logs.
* **Access Token:** The primary security context attached to the session, detailing the user's SID, group memberships, and assigned privileges.
* **Credential Material:** Depending on the configuration (e.g., WDigest, Credential Guard), LSASS may cache plaintext passwords, NTLM hashes, or Kerberos TGT/TGS tickets associated with this session to facilitate single sign-on (SSO). This cached material is exactly what tools like Mimikatz target.

## 3. 4624 Event Sequence Fingerprints

Different tools and protocols interact with the LSA pipeline differently, resulting in distinct multi-event sequences rather than a single log entry.

### RDP with Network Level Authentication (NLA)
Modern RDP does not establish a UI session before authenticating. NLA forces authentication over CredSSP before the RDP connection is fully built.
* **Step 1:** The remote client authenticates at the network layer. This generates a **Logon Type 3 (Network)** event on the target.
* **Step 2:** After passing NLA, the Remote Desktop Services stack builds the interactive session, generating a **Logon Type 10 (RemoteInteractive)** event.
* *Note:* Disconnecting and reconnecting without logging off will generate a **Logon Type 7 (Unlock)**.

### `runas /netonly`
This command is heavily used by attackers to pass-the-hash or use alternate credentials without changing their local user context.
* **Fingerprint:** Generates a **Logon Type 9 (NewCredentials)**.
* **Under the hood:** It creates a "split" logon session. Locally, the process continues to run as the original user. However, when the process makes an outbound network request (e.g., accessing an SMB share), LSASS seamlessly substitutes the alternate credentials provided via the command.

### PsExec
Standard execution of PsExec relies on SMB and the Service Control Manager (SCM), which leaves a very specific trail.
* **Step 1:** The attacker connects to the `ADMIN$` share via SMB. This creates a **Logon Type 3 (Network)** event.
* **Step 2:** PsExec pushes its binary (`PSEXESVC.exe`) and tells the SCM to start it. The SCM creates a session for the service, logging a **Logon Type 5 (Service)** event for `NT AUTHORITY\SYSTEM`.
* **Step 3 (Optional):** If the attacker uses the `-i` flag to interact with the user's desktop, PsExec forces the payload to run in the target user's interactive window station (`winsta0`), which can additionally generate a **Logon Type 2 (Interactive)** event depending on session state.

### Local or RDP Session Restore
When a user locks their screen or disconnects an RDP session (leaving it active in the background), returning to it does not create a new Type 2 or Type 10 session.
* **Fingerprint:** Generates a **Logon Type 7 (Unlock)**. The existing LogonId is reused.

## 4. The Threat Hunting Perspective: Why Type 10 is a Blind Spot

A common pitfall in SOC operations is building alerts or hunting exclusively around Logon Type 10 for RDP tracking. 

When NLA is enabled, the actual security negotiation (NTLM vs. Kerberos) and the initial network handshakes are handled during the pre-authentication phase. By the time the Logon Type 10 event is logged, the `IpAddress` field is frequently populated with local loopback addresses (like `127.0.0.1` or `::1`) or is left blank, and the authentication package might generically say `Negotiate`.

**The Analytical Rule:** You cannot accurately determine the source IP or the true authentication protocol of an RDP connection by looking at Type 10 alone. 

You must correlate the Logon Type 10 event backwards to its preceding Logon Type 3 event. This can be done by:
1.  **Time-bounding:** Looking for a Type 3 event for the same target user within milliseconds/seconds prior to the Type 10.
2.  **Network correlation:** Correlating the Type 3 event which reliably contains the external `IpAddress` and the specific Auth Package (e.g., identifying if an attacker forced an NTLM downgrade).
