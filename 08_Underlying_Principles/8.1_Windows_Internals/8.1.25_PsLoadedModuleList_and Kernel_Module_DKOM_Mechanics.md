# PsLoadedModuleList and Kernel Module DKOM Mechanics

> **Core Concept:** Just as the `EPROCESS` structure provides authoritative management for user-mode requests (as covered in 8.1.17), the OS requires a core structure in Ring 0 to track all loaded driver executables (`.sys` files). That structure is the `PsLoadedModuleList`. Attacking and manipulating this specific list allows advanced threats (Rootkits) to achieve perfect stealth at the highest system privilege level.

## 1. The PsLoadedModuleList Structure Overview (The Target of Ring 0)
In [8.1.17_EPROCESS_and_DKOM_Mechanics](./8.1.17_EPROCESS_and_DKOM_Mechanics.md), we established that active processes are tracked via `EPROCESS` blocks. However, for modules operating entirely within the kernel—handling low-level hardware interactions, network protocol filtering, or system-wide interceptions—their load status is centrally managed by the `PsLoadedModuleList`.

This list is the sole official ledger used by the kernel debugger to identify which `.sys` modules are currently loaded. Consequently, it is also the primary data source for AV/EDR solutions enumerating driver lists. For DFIR analysts, this structure is the absolute primary battleground when hunting for Ring 0 malicious behavior, such as rootkit persistence.

## 2. _KLDR_DATA_TABLE_ENTRY and Doubly-Linked Lists (The Driver Data Source)
Similar to how processes are not stored in a simple array, the Windows kernel utilizes a doubly-linked list to chain all loaded kernel modules together. `PsLoadedModuleList` serves as the head of this chain.

Every node on this list is a `_KLDR_DATA_TABLE_ENTRY` structure. This structure holds critical metadata regarding the module:
* **DllBase:** The base address where the driver is loaded within the kernel's virtual memory space.
* **SizeOfImage:** The exact byte size the driver occupies in memory.
* **FullDllName / BaseDllName:** The absolute path and base name of the driver (e.g., `\SystemRoot\System32\drivers\tcpip.sys`).

Mirroring the `ActiveProcessLinks` found in `EPROCESS`, this structure relies on the **FLINK (Forward Link)** and **BLINK (Backward Link)** pointers within the `InLoadOrderLinks` field to maintain the continuity of the list.

## 3. Direct Kernel Object Manipulation (DKOM) - Ring 0 Evasion
Once you understand how DKOM is used to hide an `EPROCESS` (Section 3 of 8.1.17), driver-level DKOM is logically identical. To evade detection by security software, rootkit developers execute a "module unlinking" attack directly within kernel memory:

1. The rootkit locates its own `_KLDR_DATA_TABLE_ENTRY` node in memory (Node B).
2. It modifies the `FLINK` of the preceding legitimate driver (Node A) to bypass Node B, pointing it directly to the succeeding legitimate driver (Node C).
3. It similarly modifies the `BLINK` of Node C to point directly back to Node A.

**The Result:** The malicious rootkit driver is entirely erased from the `PsLoadedModuleList`. While its code continues to execute inside the Non-Paged Pool with SYSTEM privileges, any security tool relying on standard Windows APIs (like `EnumDeviceDrivers`) or walking this specific linked list will be completely blind to its presence.

## 4. DFIR Detection Strategy: List Walking vs. Pool Tag Scanning
The memory forensics detection logic for this Ring 0 evasion directly mirrors the strategy used for finding hidden processes:

* **List Walking (The `modules` plugin):** Similar to `pslist`, this method sequentially follows the `FLINK` pointers starting from the `PsLoadedModuleList`. Consequently, it will **fail** to detect rootkit drivers hidden via DKOM.
* **Pool Tag Scanning (The `modscan` plugin):** Similar to `psscan`, this method entirely ignores the linked list structure. Instead, it brutally scans the entire kernel memory space (typically the Non-Paged Pool) looking for specific Pool Tags uniquely associated with the `_KLDR_DATA_TABLE_ENTRY` structure.

**Hunting Heuristic:** A classic Indicator of Compromise (IOC) for a kernel-level rootkit is a discrepancy between the outputs of `modules` and `modscan`. If a driver appears in `modscan` but is missing from the `modules` list, a driver-level DKOM unlinking attack is highly probable.

## 5. Memory Forensics: The Pathfinding Mechanism
Locating the head of the `PsLoadedModuleList` within a massive physical memory dump relies on the exact same underlying logic used to find the process list:

1. Locate the **KPCR** (Kernel Processor Control Region) as the physical core anchor.
2. Retrieve the pointer to the **KDBG** (Kernel Debugger Data Block) via the KPCR.
3. Within the KDBG—the "ultimate index map"—the OS stores not only the `PsActiveProcessHead` but also the exact memory address of the `PsLoadedModuleList`. Once this head is located, the forensic tool can begin walking the list.

## 6. Module Backing and Extraction
Just as the `_EPROCESS` block allows analysts to examine a process's virtual address space, the information gathered from `_KLDR_DATA_TABLE_ENTRY` is crucial for extracting and reverse-engineering malicious drivers:

* **The Tactical Value of DllBase:** By securing the `DllBase` and `SizeOfImage`, forensic analysts can use tools (such as Volatility's `moddump`) to carve the driver entirely out of memory.
* **Digital Signature Verification:** The extracted `.sys` file can then be fed into reverse engineering frameworks (like IDA Pro/Ghidra) or checked for valid digital signatures. An unlinked module that is unsigned or signed with a forged/leaked certificate constitutes definitive proof of compromise.

## 7. Kernel Connectors: How Hidden Drivers Expose Themselves
Even if a rootkit successfully vanishes from the `PsLoadedModuleList`, it must still interact with the OS to execute its payload. These interactions inevitably leave artifacts:

* **IRP Hooks (I/O Request Packet Hooks):** To intercept file reads or network traffic, hidden drivers often hijack the Dispatch Routines within the `DriverObject` of legitimate devices. Scanning with `devicetree` can expose IRP hooks pointing to unbacked or unknown memory regions.
* **SSDT Manipulation (System Service Dispatch Table):** Malicious drivers may alter the SSDT to redirect critical syscall pointers to their own malicious code segments. The `ssdt` plugin can reveal these pointer anomalies, proving that while the module's entry might be hidden, its behavioral hooks remain firmly anchored in the kernel's operational machinery.
