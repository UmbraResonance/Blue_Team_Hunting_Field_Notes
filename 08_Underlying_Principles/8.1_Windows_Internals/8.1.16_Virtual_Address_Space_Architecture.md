# Virtual Address Space (VAS) Architecture

## 1. The Concept of Isolation
In Windows, every process is provided with its own private Virtual Address Space (VAS). This creates an illusion for the process that it has exclusive access to the system's memory. In a 64-bit architecture, this space is massive and heavily partitioned to prevent a user-mode application from crashing the OS or reading another process's memory.

## 2. The Bridge: Virtual vs. Physical Memory & The MMU

> **Core Concept:** The Virtual Address Space is essentially a "logical ledger." A process believes it has access to a massive, contiguous block of memory, but the underlying physical reality is fragmented and strictly managed by the hardware and the OS.

### The Memory Management Unit (MMU) and Page Tables
When a thread within a process attempts to read or execute instructions from a virtual address (e.g., within its `.text` segment), the CPU does not—and cannot—go directly to the physical RAM. 
* **The Interception:** The hardware **Memory Management Unit (MMU)** built into the CPU intercepts every single memory access request.
* **The Translation:** The MMU consults a **Page Table** (a mapping structure maintained by the Windows kernel) to translate the process's illusory Virtual Address into a concrete Physical Address in the actual RAM chips.

### Demand Paging and Page Faults
Windows operates on a principle called "Demand Paging." When a process is created, the OS maps out the VAS but does not immediately load the entire executable file from the disk into the physical RAM.
* **The Page Fault:** If the MMU checks the Page Table and finds no valid physical mapping for the requested virtual address (because the data is still sitting on the disk or in `pagefile.sys`), it halts the CPU and issues a hardware interrupt known as a **Page Fault**.
* **The Kernel Response:** This fault forces an immediate context switch to Ring 0. The Windows Memory Manager takes over, locates the required 4KB chunk of data on the disk (a Hard Page Fault), loads it into a free space in the physical RAM, updates the Page Table, and tells the thread to resume execution.

### DFIR Relevance: The Security Implications
Understanding this hardware-to-OS translation is non-negotiable for advanced detection engineering:
1. **Artifact Generation:** The Hard Page Fault mechanism is exactly what the `SysMain` service monitors to track which files and DLLs are touched during application startup, enabling the creation of Prefetch (`.pf`) forensic artifacts.
2. **Fileless Malware Detection:** Adversaries using Reflective DLL Injection or Cobalt Strike allocate "Private Memory" that is strictly virtual and has no corresponding file on the disk. Identifying these **Unbacked** memory regions (which generate Page Faults pointing to the pagefile rather than a legitimate `.exe`) is the primary methodology for hunting fileless implants.

## 3. Microscopic Layout of VAS
When a process executes, its VAS is divided into distinct regions managed by the memory controller:

* **Code Segment (`.text`)**: 
    * Contains the executable machine instructions mapped from the disk image.
    * *Security Posture*: Generally set to `PAGE_EXECUTE_READ` (R-X). If this area becomes writable during runtime, it strongly indicates process hollowing, unpacking, or self-modifying code.
* **Data Segments (`.data` / `.rdata` / `.bss`)**: 
    * Houses initialized and uninitialized global/static variables, as well as read-only constants like the Import Address Table (IAT).
    * *Security Posture*: Typically `PAGE_READWRITE` (RW-) or `PAGE_READONLY` (R--). Attackers often target the `.rdata` section for IAT hooking.
* **The Heap**: 
    * Used for dynamic memory allocation during runtime (e.g., via `malloc` or `HeapAlloc`). It grows from lower to higher memory addresses. 
    * *DFIR Relevance*: Often abused for Heap Spraying to execute arbitrary payloads.
* **The Stack**: 
    * A LIFO (Last-In-First-Out) structure allocated for each individual thread within the process. It handles local variables, function parameters, and return addresses.
    * *Note*: Unlike the Heap, the Stack grows downwards (from higher to lower memory addresses). Overwriting the return address here is the foundation of classic buffer overflow attacks.

## 4. VAD (Virtual Address Descriptor) Tree: The Memory Ledger

* **Transition Concept:** While Section 3 describes what is inside the process space, the VAD Tree is the kernel's authoritative "ledger" that tracks the existence and boundaries of these segments.

* **The Architecture (The "How"):** - Structure: VADs are organized as an AVL (Balanced Binary) Tree rather than a flat list to ensure O(logn) search efficiency.

* **Kernel Link:** The _EPROCESS structure holds the VadRoot pointer to the top of this tree.

* **DFIR & Hunting Impact:**

  - VAD Walking (vadinfo): Walks the "official" AVL tree. It only sees what the kernel recognizes.

  - VAD Scanning (vads_scan): Scans raw memory for VAD pool tags.

  - The Mismatch Heuristic: If a segment is "unlinked" from the AVL tree (similar to DKOM), it becomes invisible to vadinfo but remains detectable via vads_scan.

## 5. Memory States and Protections (Stored within VAD Nodes)

* **Transition Concept:** Each node in the VAD Tree mentioned above stores specific flags that define the current status and access rights of that memory range.

* **Free**: The memory is unallocated and inaccessible.
* **Reserved**: A contiguous block of VAS is set aside for future use, but no physical memory or page file space is committed yet.
* **Committed**: Physical storage is actually allocated. 

### Key Memory Protection Constants (The W^X Principle)
Modern defenses enforce the "Write XOR Execute" (W^X) principle. A memory page should either be writable or executable, never both simultaneously. 
* Hunting for `PAGE_EXECUTE_READWRITE` (RWX) permissions in memory dumps or telemetry is a primary detection heuristic for injected shellcode or reflective loaders.

## 6. Exploit Mitigation Mechanisms
The VAS layout is not static. Windows employs randomizations to break hardcoded exploits:
* **ASLR (Address Space Layout Randomization)**: Randomizes the base addresses of the executable, DLLs, heap, and stack every time the system boots or the process spawns.
* **DEP (Data Execution Prevention)**: Marks memory regions like the Heap and Stack as strictly non-executable, forcing attackers to use complex techniques like ROP (Return-Oriented Programming) chains to execute code.
