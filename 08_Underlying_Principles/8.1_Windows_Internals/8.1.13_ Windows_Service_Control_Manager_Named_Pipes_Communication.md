# Windows Service Control Manager (SCM) and Named Pipes Communication

---

## 1. Overview
The **Service Control Manager (SCM)** and **Named Pipes** are fundamental Windows mechanisms that intersect during administrative tasks and lateral movement activities (e.g., PsExec). Understanding their underlying orchestration is critical for detecting service-based persistence and inter-process communication (IPC) anomalies.

---

## 2. Service Control Manager (SCM) Architecture
The SCM is a specialized Remote Procedure Call (RPC) server launched by `services.exe` during system boot. It acts as the "ledger" for all Windows services.

### Key Components:
* **The Database:** Maintained in the registry at `HKLM\SYSTEM\CurrentControlSet\Services`. Every service must have a subkey here.
* **Control Requests:** SCM handles requests to start, stop, and configure services via the Service Control API (e.g., `CreateService`, `StartService`).
* **Security Context:** Services typically run under `LocalSystem`, `NetworkService`, or `LocalService` accounts, making them high-value targets for privilege escalation.

---

## 3. Named Pipes: The Inter-Process Conduit
Named Pipes provide a method for one-way or duplex communication between a server process and one or more client processes. They allow processes to share data without the overhead of network sockets, even across a network using the SMB protocol (port 445).

### Communication Workflow:
1.  **Creation:** A server process creates a pipe using `CreateNamedPipe` with a specific name (e.g., `\\.\pipe\psexesvc`).
2.  **Connection:** A client process connects using `CreateFile` or `CallNamedPipe`.
3.  **Abuse Vector:** Because Named Pipes support impersonation, a malicious client can sometimes trick a privileged server into connecting to its pipe, leading to token theft.

---

## 4. Case Study: PsExec Orchestration
PsExec's effectiveness relies on the synergy between SCM and Named Pipes:

1. **MSRPC Handshake:** The client establishes an RPC session via SMB (\pipe\svcctl). The SCM process (services.exe) receives this request, impersonates the calling user, and verifies permissions before modifying the Services registry hive.
2. **Service Deployment:** The PsExec client uses the SCM API to remotely create and start a service named `PSEXESVC` on the target machine.
3.  **Binary Execution:** The SCM executes `C:\Windows\PSEXESVC.exe` under the `SYSTEM` context.
4.  **I/O Redirection via Pipes:** To provide an interactive shell, `PSEXESVC.exe` creates named pipes (e.g., `\psexesvc-stdin`, `\psexesvc-stdout`). The local PsExec client connects to these pipes via SMB to send commands and receive output.

## 5. Detection & Hunting Indicators

| Artifact | Event Source | Event ID | Logic |
| :--- | :--- | :--- | :--- |
| **Service Creation** | System Log | 7045 | New service installation with suspicious ImagePath (e.g., `\Temp\`). |
| **Registry Modification** | Sysmon | 13 | `services.exe` modifying `ImagePath` in `CurrentControlSet\Services`. |
| **Pipe Creation** | Sysmon | 17 | Unusual processes creating named pipes (e.g., `\psexesvc`). |
| **Pipe Connection** | Sysmon | 18 | Cross-process communication between an untrusted process and a system pipe. |

## 6. Case Study: Cobalt Strike PSExec vs. Legitimate PsExec

While Cobalt Strike's PSExec lateral movement module shares the same underlying SCM and Named Pipe mechanics as the legitimate Sysinternals PsExec utility, it introduces several deliberate behavioral modifications designed to evade signature-based detection. Understanding these differences is essential for constructing behavior-based detection logic that remains effective regardless of tooling.

### 6.1 Structural Comparison

| Dimension | Legitimate PsExec | Cobalt Strike PSExec |
| :--- | :--- | :--- |
| **Service Name** | Fixed: `PSEXESVC` | Randomized at runtime (e.g., `c3400ec`) |
| **Binary Name** | Fixed: `PSEXESVC.exe` | Randomized at runtime (e.g., `c3400ec.exe`) |
| **Drop Location** | `C:\Windows\PSEXESVC.exe` via `ADMIN$` | `C:\Windows\<random>.exe` via `ADMIN$` |
| **Service Lifetime** | Persists for the duration of the interactive session | Self-deletes immediately after beacon execution |
| **Named Pipes** | Creates stdin/stdout/stderr pipes for interactive I/O | No I/O pipes required; beacon establishes its own C2 channel |
| **API Version** | `CreateServiceW` (Unicode) | `CreateServiceA` (ANSI) -- deliberate obfuscation |
| **Objective** | Provide an interactive remote shell | Plant a beacon payload; no further reliance on SCM |

### 6.2 Two-Phase Delivery Workflow

Cobalt Strike PSExec operates in two distinct phases that map directly to the two hidden SMB shares:

**Phase 1 -- Payload Staging via `ADMIN$`**

The attacker (operating from an existing beacon on a compromised host) authenticates over SMB and writes the randomized beacon executable to the target's `C:\Windows\` directory by accessing the `ADMIN$` share. The binary is transferred in chunks (typically 65,536 bytes per write request) to avoid triggering size-based network signatures.

```
NTLM Authentication
Tree Connect --> \\Target\ADMIN$
Create File  --> <random>.exe
Write Request (chunk 1 of N, Len: 65536)
Write Request (chunk 2 of N, Len: 65536)
...
Close File
Tree Disconnect
```

**Phase 2 -- Remote Execution via `IPC$` and SCM**

A new SMB session is established to `IPC$`, which serves as the transport for DCE/RPC calls to the Service Control Manager. The sequence mirrors the legitimate PsExec SCM interaction, with the critical difference that the service is destroyed immediately after the beacon process is spawned.

```
Tree Connect --> \\Target\IPC$
Create File  --> svcctl         (open handle to SCM named pipe)
DCERPC Bind  --> svcctl interface
OpenSCManagerW
CreateServiceA --> ImagePath: C:\Windows\<random>.exe
StartServiceA  --> beacon executes, injects into host process
DeleteServiceA --> service record removed
Tree Disconnect
```

### 6.3 Post-Execution: Beacon Independence

Once `StartServiceA` triggers execution, the beacon payload operates entirely independently of the SCM infrastructure used to launch it. The beacon typically injects its shellcode into a legitimate host process (e.g., `svchost.exe`) to avoid detection as a standalone executable, then establishes its own C2 channel. At this point, `DeleteServiceA` removes the service record, leaving no persistent SCM artifact.

Depending on the operator's network architecture, the newly planted beacon may communicate in one of two modes:

* **Direct C2**: The beacon connects outbound to the external C2 server over HTTPS or DNS. This exposes the target host to outbound traffic monitoring.
* **SMB Beacon (Peer-to-Peer)**: The beacon communicates exclusively over a named pipe back to the originating beacon, which relays traffic to the external C2. The target host produces no external network connections, making perimeter-based detection ineffective. This topology is the operationally preferred mode in segmented or monitored environments.

### 6.4 Detection Engineering Implications

Because service name, binary name, and pipe names are all randomized, signature-based detection is ineffective against Cobalt Strike PSExec. Detection must be grounded in behavioral invariants -- the aspects of the attack that cannot be changed without abandoning the technique entirely. The table in Section 5 covers the shared detection surface; the invariants below are specific to the CS PSExec pattern.

| Invariant Behavior | Why It Cannot Be Evaded | Detection Signal |
| :--- | :--- | :--- |
| Executable written to `ADMIN$` | Payload must reach the target filesystem via SMB -- there is no alternative path | Sysmon Event 11 for `.exe` in `C:\Windows\` root from a remote session |
| SCM RPC sequence | SCM is the only mechanism to remotely execute a binary as SYSTEM without an existing session | `dce_rpc.log`: `OpenSCManagerW` -> `CreateService` -> `StartService` |
| Service created and deleted within seconds | Self-deletion is the cleanup step -- skipping it leaves a detectable artifact | EventID 7045 followed immediately by EventID 7036 |
| No stdin/stdout named pipes post-execution | Beacon does not need interactive I/O; absence of `\psexesvc-*` pipes distinguishes this from legitimate PsExec | Sysmon Event 17 absence pattern |


## Conclusion
The SCM provides the **Execution** capability, while Named Pipes provide the **Communication** channel. Modern attackers often rename service binaries and pipe names to evade signature-based detection, making behavioral monitoring of `services.exe` and pipe-related Sysmon events essential for robust defense.

Beyond PsExec, SCM is the ultimate gatekeeper for high-privilege operations. Whether it's the exploitation of Unquoted Service Paths for elevation, or the tampering of EDR services for evasion, SCM telemetry (Event 7045/7036/13) remains the most reliable signal for identifying post-exploitation activities in a Windows environment.
