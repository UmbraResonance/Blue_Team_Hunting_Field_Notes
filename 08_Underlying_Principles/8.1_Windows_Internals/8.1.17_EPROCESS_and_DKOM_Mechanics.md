# 8.1.17 EPROCESS and DKOM (Direct Kernel Object Manipulation) Mechanics

> **Core Concept:** Building on the User-Mode concepts from 8.1.05, once an API request crosses the Syscall boundary into Ring 0, the kernel needs an authoritative structure to manage the process making the request. That structure is `EPROCESS`, and attacking it directly allows adversaries to achieve Ring 0 evasion, akin to how Direct Syscalls provide Ring 3 evasion.

## 1. The EPROCESS Structure Overview (The Target of the Syscall)
In [8.1.05_The_User_Mode_Ecosystem_and_Call_Stack](./8.1.05_The_User_Mode_Ecosystem_and_Call_Stack.md), we established that every user-mode request for system resources converges at the System Call (Syscall) to enter Kernel Mode. In the Windows kernel, every active process initiating these calls is represented by an `EPROCESS` (Executive Process) structure. 

This data structure resides exclusively in kernel memory and acts as the master operational object for a process. It contains critical metadata, including the Process ID (PID), parent PID, security tokens, access rights, and memory directory tables.

For forensic analysts, the `EPROCESS` block is the source of truth for determining what was actively running on a system at the time of a memory capture.

## 2. ActiveProcessLinks and Doubly-Linked Lists (The API Data Source)
When standard user-mode components like `kernel32.dll` or `advapi32.dll` (discussed in 8.1.05) process an API call like `EnumProcesses`, the OS must retrieve this information from the kernel. 

The Windows kernel does not store processes in a simple array. Instead, it links `EPROCESS` structures together using a doubly-linked list via the `ActiveProcessLinks` field.

This list utilizes two critical pointers:
* **FLINK (Forward Link):** Points to the `ActiveProcessLinks` entry of the *next* `EPROCESS` structure.
* **BLINK (Backward Link):** Points to the `ActiveProcessLinks` entry of the *previous* `EPROCESS` structure.

When standard monitoring tools (like Task Manager) request a list of running processes, the OS iterates through this chain by following the `FLINK` pointers.

## 3. Direct Kernel Object Manipulation (DKOM) - The Ring 0 Evasion
While [8.1.05_The_User_Mode_Ecosystem_and_Call_Stack](./8.1.05_The_User_Mode_Ecosystem_and_Call_Stack.md) covered how malware uses *Direct Syscalls* to bypass user-land EDR hooks, DKOM is the kernel-land equivalent: manipulating the absolute source of truth to bypass monitoring altogether. 

DKOM is a stealth technique utilized by rootkits and advanced malware to manipulate kernel structures directly, effectively bypassing user-land monitoring. 

To hide a malicious process, a rootkit executes a "process unlinking" attack:
1.  The rootkit identifies the `EPROCESS` block of the malicious process (Process B).
2.  It modifies the `FLINK` of the preceding process (Process A) to point directly to the succeeding process (Process C).
3.  It modifies the `BLINK` of the succeeding process (Process C) to point directly to the preceding process (Process A).

**The Result:** The malicious Process B is entirely removed from the `ActiveProcessLinks` chain. It continues to execute on the CPU and consume memory, but any tool relying on the standard linked list will not see it.

## 4. DFIR Detection Strategy: List Walking vs. Pool Tag Scanning
Understanding DKOM, much like understanding Direct Syscalls, dictates how we approach forensics:

* **List Walking (`pslist`):** Follows the `ActiveProcessLinks` doubly-linked list. Because it relies on the same pointers standard APIs use, it will **fail** to display processes hidden via DKOM.
* **Pool Tag Scanning (`psscan`):** Ignores the linked list entirely. Instead, it scans the raw memory space for specific pool tags associated with `EPROCESS` structures (e.g., `Proc` or `Proce` tags). 

**Hunting Heuristic:** A classic Indicator of Compromise (IOC) for a rootkit is a discrepancy between list-walking and pool-scanning outputs. If a process appears in `psscan` but is absent in `pslist`, DKOM unlinking is highly probable.

## 5. Memory Forensics: The Pathfinding Mechanism
While DKOM explains how malware manipulates the OS internally, memory forensics tools (like Volatility) face a different challenge: locating the start of the `ActiveProcessLinks` chain within a massive, unstructured raw memory dump.

To bridge this gap, forensic tools rely on specific hardware and kernel structures used as anchor points:
* **KPCR (Kernel Processor Control Region):** Windows maintains one KPCR structure for each logical processor (CPU core) to store state data. Memory analysis tools often scan for the KPCR signature first because it serves as the foundational stepping stone.
* **KDBG (Kernel Debugger Data Block):** The KPCR contains a pointer to the KDBG. Originally designed to assist kernel debugging, this structure acts as the ultimate index map for memory forensics, holding the addresses of critical kernel variables.
* **PsActiveProcessHead:** This is the specific "hook" required for process enumeration. The KDBG contains the `PsActiveProcessHead` pointer, which points directly to the very first `_EPROCESS` block in the doubly-linked list. Once located, tools can walk the `FLINK` pointers to enumerate the unhidden processes (e.g., via the `pslist` plugin).

## 6. Directory Table Base (DTB) and Memory Translation
Finding an `_EPROCESS` block is only half the battle. To extract or analyze the data inside a process (like dumping an injected DLL or reading strings), the forensic tool must read the process's private Virtual Address Space (VAS). 

* **DTB (Directory Table Base):** Each `_EPROCESS` block contains its own DTB value. The DTB represents the physical base address of the Page Directory for that specific process. 
* **Forensic Relevance:** Without the correct DTB, it is impossible to translate the virtual memory addresses back into physical offsets within the memory dump. The DTB is essentially the translation key that allows tools to reconstruct fragmented physical memory pages into a coherent, contiguous virtual view of the process.

## 7. The Kernel Connectors: How EPROCESS Links Everything
While `ActiveProcessLinks` is the most famous list for enumeration, the `EPROCESS` block contains other critical pointers that define the process's operational "truth":

* **VadRoot (The Memory Connector):** * **Mechanism:** Instead of a simple list, the kernel manages a process's memory layout via an **AVL (Balanced Binary) Tree**. The `_EPROCESS` structure holds the `VadRoot` pointer to the top of this tree.
    * **Forensic Impact:** Volatility’s `vadinfo` walks this tree. If a rootkit "prunes" a branch from the AVL tree, standard memory queries fail, but `vads_scan` (pool tag scanning) can still find the orphaned memory segments.

* **ObjectTable (The Asset Connector):** * **Mechanism:** As established in [8.1.07], the Kernel acts as a "Central Bank". The `_EPROCESS` structure contains the `ObjectTable` pointer, which leads to the process's private **Handle Table**.
    * **Forensic Impact:** Even if an attacker uses Direct Syscalls to hide their API calls, the **Handle Table** remains the immutable record of what the process "owns" (files, LSASS handles, etc.).

* **ThreadListHead (The Execution Connector):** * **Mechanism:** `_EPROCESS` manages its threads through a doubly-linked list called `ThreadListHead`.
    * **Forensic Impact:** Every `_ETHREAD` structure in this list contains a pointer back to its parent `_EPROCESS`. This is the foundation of **Thread Backtracking**—finding a hidden process by first finding its running threads.
