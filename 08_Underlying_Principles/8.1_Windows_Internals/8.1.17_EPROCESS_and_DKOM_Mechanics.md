# 8.1.17 EPROCESS and DKOM (Direct Kernel Object Manipulation) Mechanics

> **Core Concept:** Building on the User-Mode concepts from 8.1.05, once an API request crosses the Syscall boundary into Ring 0, the kernel needs an authoritative structure to manage the process making the request. That structure is `EPROCESS`, and attacking it directly allows adversaries to achieve Ring 0 evasion, akin to how Direct Syscalls provide Ring 3 evasion.

## 1. The EPROCESS Structure Overview (The Target of the Syscall)
In [8.1.05_The_User_Mode_Ecosystem_and_Call_Stack](./8.1.05_The_User_Mode_Ecosystem_and_Call_Stack.md), we established that every user-mode request for system resources converges at the System Call (Syscall) to enter Kernel Mode. In the Windows kernel, every active process initiating these calls is represented by an `EPROCESS` (Executive Process) structure. 

This data structure resides exclusively in kernel memory and acts as the master operational object for a process. It contains critical metadata, including the Process ID (PID), parent PID, security tokens, access rights, and memory directory tables.

For forensic analysts, the `EPROCESS` block is the source of truth for determining what was actively running on a system at the time of a memory capture.

## 2. ActiveProcessLinks and Doubly-Linked Lists (The API Data Source)
When standard user-mode components like `kernel32.dll` or `advapi32.dll` (discussed in 8.1.05) process an API call like `EnumProcesses`, the OS must retrieve this information from the kernel. 

The Windows kernel does not store processes in a simple array. Instead, it links `EPROCESS` structures together using a doubly-linked list via the `ActiveProcessLinks` field.

This list utilizes two critical pointers:
* **FLINK (Forward Link):** Points to the `ActiveProcessLinks` entry of the *next* `EPROCESS` structure.
* **BLINK (Backward Link):** Points to the `ActiveProcessLinks` entry of the *previous* `EPROCESS` structure.

When standard monitoring tools (like Task Manager) request a list of running processes, the OS iterates through this chain by following the `FLINK` pointers.

## 3. Direct Kernel Object Manipulation (DKOM) - The Ring 0 Evasion
While [8.1.05_The_User_Mode_Ecosystem_and_Call_Stack](./8.1.05_The_User_Mode_Ecosystem_and_Call_Stack.md) covered how malware uses *Direct Syscalls* to bypass user-land EDR hooks, DKOM is the kernel-land equivalent: manipulating the absolute source of truth to bypass monitoring altogether. 

DKOM is a stealth technique utilized by rootkits and advanced malware to manipulate kernel structures directly, effectively bypassing user-land monitoring. 

To hide a malicious process, a rootkit executes a "process unlinking" attack:
1.  The rootkit identifies the `EPROCESS` block of the malicious process (Process B).
2.  It modifies the `FLINK` of the preceding process (Process A) to point directly to the succeeding process (Process C).
3.  It modifies the `BLINK` of the succeeding process (Process C) to point directly to the preceding process (Process A).

**The Result:** The malicious Process B is entirely removed from the `ActiveProcessLinks` chain. It continues to execute on the CPU and consume memory, but any tool relying on the standard linked list will not see it.

## 4. DFIR Detection Strategy: List Walking vs. Pool Tag Scanning
Understanding DKOM, much like understanding Direct Syscalls, dictates how we approach forensics:

* **List Walking (`pslist`):** Follows the `ActiveProcessLinks` doubly-linked list. Because it relies on the same pointers standard APIs use, it will **fail** to display processes hidden via DKOM.
* **Pool Tag Scanning (`psscan`):** Ignores the linked list entirely. Instead, it scans the raw memory space for specific pool tags associated with `EPROCESS` structures (e.g., `Proc` or `Proce` tags). 

**Hunting Heuristic:** A classic Indicator of Compromise (IOC) for a rootkit is a discrepancy between list-walking and pool-scanning outputs. If a process appears in `psscan` but is absent in `pslist`, DKOM unlinking is highly probable.

## 5. Memory Forensics: The Pathfinding Mechanism
While DKOM explains how malware manipulates the OS internally, memory forensics tools (like Volatility) face a different challenge: locating the start of the `ActiveProcessLinks` chain within a massive, unstructured raw memory dump.

To bridge this gap, forensic tools rely on specific hardware and kernel structures used as anchor points:
* **KPCR (Kernel Processor Control Region):** Windows maintains one KPCR structure for each logical processor (CPU core) to store state data. Memory analysis tools often scan for the KPCR signature first because it serves as the foundational stepping stone.
* **KDBG (Kernel Debugger Data Block):** The KPCR contains a pointer to the KDBG. Originally designed to assist kernel debugging, this structure acts as the ultimate index map for memory forensics, holding the addresses of critical kernel variables.
* **PsActiveProcessHead:** This is the specific "hook" required for process enumeration. The KDBG contains the `PsActiveProcessHead` pointer, which points directly to the very first `_EPROCESS` block in the doubly-linked list. Once located, tools can walk the `FLINK` pointers to enumerate the unhidden processes (e.g., via the `pslist` plugin).

## 6. Directory Table Base (DTB) and Memory Translation
Finding an `_EPROCESS` block is only half the battle. To extract or analyze the data inside a process (like dumping an injected DLL or reading strings), the forensic tool must read the process's private Virtual Address Space (VAS). 

* **DTB (Directory Table Base):** Each `_EPROCESS` block contains its own DTB value. The DTB represents the physical base address of the Page Directory for that specific process. 
* **Forensic Relevance:** Without the correct DTB, it is impossible to translate the virtual memory addresses back into physical offsets within the memory dump. The DTB is essentially the translation key that allows tools to reconstruct fragmented physical memory pages into a coherent, contiguous virtual view of the process.

## 7. The Kernel Connectors: How EPROCESS Links Everything
While `ActiveProcessLinks` is the most famous list for enumeration, the `EPROCESS` block contains other critical pointers that define the process's operational "truth":

* **VadRoot (The Memory Connector):** * **Mechanism:** Instead of a simple list, the kernel manages a process's memory layout via an **AVL (Balanced Binary) Tree**. The `_EPROCESS` structure holds the `VadRoot` pointer to the top of this tree.
    * **Forensic Impact:** Volatility’s `vadinfo` walks this tree. If a rootkit "prunes" a branch from the AVL tree, standard memory queries fail, but `vads_scan` (pool tag scanning) can still find the orphaned memory segments.

* **ObjectTable (The Asset Connector):** * **Mechanism:** As established in [8.1.07], the Kernel acts as a "Central Bank". The `_EPROCESS` structure contains the `ObjectTable` pointer, which leads to the process's private **Handle Table**.
    * **Forensic Impact:** Even if an attacker uses Direct Syscalls to hide their API calls, the **Handle Table** remains the immutable record of what the process "owns" (files, LSASS handles, etc.).

* **ThreadListHead (The Execution Connector):** * **Mechanism:** `_EPROCESS` manages its threads through a doubly-linked list called `ThreadListHead`.
    * **Forensic Impact:** Every `_ETHREAD` structure in this list contains a pointer back to its parent `_EPROCESS`. This is the foundation of **Thread Backtracking**—finding a hidden process by first finding its running threads.

## 8. APC Queue Mechanics (Per-Thread Execution Routing)
 
While `_EPROCESS` is the container and `_ETHREAD` is the executor, each thread owns a pair of **Asynchronous Procedure Call (APC) queues** — kernel-managed linked lists of function pointers that the OS delivers to the thread at specific, well-defined points in its execution. Understanding APC queues is essential for reasoning about both legitimate asynchronous I/O completion and one of the most stealthy classes of process injection.
 
### 8.1 The Dual Queue Structure
 
Each `_ETHREAD` contains two logically distinct APC queues:
 
* **Kernel-mode APC queue** — Used by the I/O manager to deliver completion routines when asynchronous I/O (`ReadFile` / `WriteFile` with OVERLAPPED structures) finishes. These APCs execute in kernel mode, have priority over user-mode APCs, and are part of normal OS operation.
* **User-mode APC queue** — Used to deliver callbacks into the thread's user-mode context. This is the queue that matters for security analysis, because it is the queue exploitable via `QueueUserAPC`.
### 8.2 The Delivery Trigger: Alertable Wait State
 
The defining constraint on user-mode APC delivery is that the target thread must enter an **alertable wait state** before queued APCs will execute. A thread enters alertable wait by calling one of a specific set of APIs:
 
| API | Typical Use |
| :--- | :--- |
| `SleepEx(<ms>, TRUE)` | Timed wait with alertable flag. |
| `WaitForSingleObjectEx(..., TRUE)` | Wait on a single kernel object with alertable flag. |
| `WaitForMultipleObjectsEx(..., TRUE)` | Wait on multiple objects with alertable flag. |
| `MsgWaitForMultipleObjectsEx(..., MWMO_ALERTABLE)` | GUI thread wait with alertable flag. |
| `NtTestAlert` | Explicit alertable-state entry, typically only seen in offensive tooling. |
 
If a thread is executing non-alertable code — a busy loop, a standard `Sleep` without the `Ex` variant, a wait without the `TRUE` flag — queued APCs sit in the queue indefinitely and never execute. This is the architectural property that makes APC injection viable against specific targets (threads that routinely enter alertable waits, like those servicing GUI message loops or network I/O) and unreliable against others.
 
When the thread does enter alertable wait, the kernel drains the user-mode APC queue and executes each queued function pointer in FIFO order, in the thread's own user-mode context. After the queue is drained, the original wait operation completes (typically returning `WAIT_IO_COMPLETION` to signal that an APC interrupted the wait).
 
### 8.3 APC Injection: The TTP
 
APC injection (ATT&CK T1055.004) exploits this mechanism by queuing a malicious function pointer into a legitimate remote thread's user-mode APC queue. The standard sequence:
 
1. `OpenProcess` to obtain a handle to the target process with appropriate rights.
2. `VirtualAllocEx` + `WriteProcessMemory` to stage the payload in the target process's address space.
3. `OpenThread` on a target thread inside the victim process.
4. `QueueUserAPC(payload_address, thread_handle, ...)` to queue the payload.
5. Wait for the target thread to enter alertable state — or force it.
The "force it" variant is **Early Bird Injection**: the attacker creates the target process in suspended state (see the Process Hollowing mechanics in [4.0 Common Malware Behaviors and TTPs](../../04_Malware_Analysis_Cheatsheets/4.0_Common_Malware_Behaviors_and_TTPs.md) Section 3), queues the APC to its primary thread before resuming, and then calls `ResumeThread`. Because the primary thread passes through an alertable wait very early in its initialization (inside `ntdll`'s thread initialization code), the APC fires before the process's own `main` function ever runs.
 
### 8.4 Why APC Injection Is Preferred Over `CreateRemoteThread`
 
Three structural advantages drive adversary selection of APC injection over the classic `CreateRemoteThread` approach:
 
First, `CreateRemoteThread` is heavily monitored. Kernel callbacks (`PsSetCreateThreadNotifyRoutine`) and ETW-TI both emit events when a thread is created in a remote process. `QueueUserAPC` against an existing thread triggers no thread-creation event — no new thread was created.
 
Second, APC injection does not require the `THREAD_CREATE` access right on the target process. `QueueUserAPC` only needs `THREAD_SET_CONTEXT` on the thread handle, which in practice is easier to obtain and less audited.
 
Third, the injected code executes in the context of an already-running, already-legitimate thread. From a behavioral analytics perspective, the thread's history — its loaded module context, its previous API call pattern — is all "normal" right up to the moment the APC fires. Behavioral anomaly detection that baselines per-thread behavior has limited purchase against this technique.
 
### 8.5 Detection Primitives
 
APC injection produces a thin but distinctive telemetry signature when the full detection stack is in place:
 
| Source | Signal |
| :--- | :--- |
| **ETW-TI `Microsoft-Windows-Threat-Intelligence`** | The `KiUserApcDispatcher` event (provider-specific; exposed to PPL consumers) fires when a user-mode APC is dispatched. Correlating this with cross-process memory writes from a non-parent process identifies the injection chain. |
| **Sysmon Event 8 (CreateRemoteThread)** | Does **not** fire for APC injection — absence of this event despite observable cross-process memory manipulation is itself a heuristic signal. |
| **Thread call stack inspection** | The first user-mode frame of an APC-dispatched thread will be inside unbacked memory (the payload) with the subsequent frame inside `ntdll!KiUserApcDispatcher`. This signature is visible via EDR stack-walking or live WinDbg analysis. |
| **Handle-access telemetry** | `OpenThread` calls from a non-related process requesting `THREAD_SET_CONTEXT` on threads in sensitive targets (LSASS, security products) are high-fidelity signals. Event 4656/4663 with appropriate SACLs on these processes captures this. |
 
The practical reality is that APC injection sits in a detection gap for organizations that rely primarily on Sysmon + Security Event Log without ETW-TI or a commercial EDR. This is exactly the gap the technique was designed for, and it is a reason APC injection remains common in modern commodity loaders despite being a technique that has been public knowledge for over a decade.
 
### 8.6 Cross-Reference to EPROCESS Structure
 
The APC queues live on `_ETHREAD`, not `_EPROCESS`. However, enumeration during memory forensics always starts from `_EPROCESS`: the analyst walks `ThreadListHead` (discussed in Section 7 of this document) to reach each `_ETHREAD`, then inspects the APC state flags (`_ETHREAD.ApcState`) to see whether user-mode APCs are pending. Volatility's `threads` plugin surfaces this — threads with pending APCs and a call stack originating outside the expected module set are the forensic indicator.

## 9. Parent Process ID Spoofing (PPID Spoofing)
 
Every `_EPROCESS` structure contains an `InheritedFromUniqueProcessId` field that records the Process ID of its creating process. This is the field that tools like Task Manager, Process Explorer, and Sysmon consume to construct process-lineage trees. The design assumption is that this field faithfully reflects reality: if process A calls `CreateProcess` to spawn process B, then B's `InheritedFromUniqueProcessId` equals A's PID.
 
This assumption is exploitable. Since Windows Vista, the `CreateProcess` API family has supported an **attribute list** that lets the caller specify, among other things, an arbitrary parent process — overriding the default behavior of using the calling process as the parent.
 
### 9.1 The Mechanism
 
The technique uses three APIs in sequence:
 
```c
SIZE_T size = 0;
InitializeProcThreadAttributeList(NULL, 1, 0, &size);
LPPROC_THREAD_ATTRIBUTE_LIST attrList = HeapAlloc(GetProcessHeap(), 0, size);
InitializeProcThreadAttributeList(attrList, 1, 0, &size);
 
HANDLE hParent = OpenProcess(PROCESS_CREATE_PROCESS, FALSE, <target_pid>);
 
UpdateProcThreadAttribute(
    attrList,
    0,
    PROC_THREAD_ATTRIBUTE_PARENT_PROCESS,
    &hParent,
    sizeof(HANDLE),
    NULL, NULL
);
 
STARTUPINFOEX si = { 0 };
si.StartupInfo.cb = sizeof(STARTUPINFOEX);
si.lpAttributeList = attrList;
 
CreateProcessW(
    L"C:\\Windows\\System32\\cmd.exe",
    NULL, NULL, NULL, FALSE,
    EXTENDED_STARTUPINFO_PRESENT,
    NULL, NULL,
    &si.StartupInfo,
    &pi
);
```
 
After this sequence, the newly created `cmd.exe` process has its `_EPROCESS.InheritedFromUniqueProcessId` set to the PID of whichever process the handle `hParent` pointed to — typically `explorer.exe`, `services.exe`, or another legitimate long-running system process.
 
The critical permission requirement is `PROCESS_CREATE_PROCESS` on the spoofed-parent process handle. This is not a trivial right; it effectively requires SYSTEM privilege or explicit DACL permission on the target. The technique is therefore typically seen post-escalation, not as an initial-compromise primitive.
 
### 9.2 What Gets Spoofed and What Does Not
 
The spoofing affects only the `InheritedFromUniqueProcessId` field and the user-mode tools that derive parent-lineage from it:
 
| Observable | Affected by PPID Spoofing? |
| :--- | :--- |
| Task Manager parent tree | Yes — shows spoofed parent. |
| `wmic process` output | Yes — `ParentProcessId` field reflects spoofed value. |
| Sysmon Event 1 `ParentImage` / `ParentProcessId` | Yes — the user-mode classifier in Sysmon reads this field and is deceived. |
| Security Event 4688 `Creator Process ID` | Yes — same underlying data source. |
| ETW `Microsoft-Windows-Kernel-Process` provider | **No** — the kernel-level provider records the *actual* calling process via its internal trace, not the spoofed field. |
| `_EPROCESS.ParentProcessId` (as retrieved by Volatility via raw memory) | Yes — the spoofed value is what was written. |
| Volatility with `pstree` vs. cross-correlation against thread creator | Partial — `pstree` is deceived; deeper analysis of the process's initial thread and its stack can reveal the true creator. |
 
The asymmetry between user-mode telemetry (deceived) and kernel-mode ETW (truthful) is the architectural basis for detection.
 
### 9.3 Adversary Use Cases
 
PPID spoofing is rarely a standalone goal. It is almost always a component of a larger evasion chain, serving one of three functions:
 
* **Blending with expected process lineage**: A loader creates `cmd.exe` with a spoofed parent of `explorer.exe` to match the pattern of a user manually opening a command prompt. Detection rules that alert on "`cmd.exe` spawned by non-shell process" fail to fire.
* **Hiding post-exploitation execution**: After initial access via a macro in `winword.exe`, the payload spawns follow-on processes with spoofed parents to break the `winword.exe → cmd.exe → powershell.exe` lineage that would otherwise be a high-fidelity alert chain.
* **Confusing forensic timeline reconstruction**: During IR, analysts reconstruct attacker activity by walking process ancestry. Spoofed parents introduce deliberate false branches that must be disentangled before the true sequence is recoverable.
### 9.4 Detection via Kernel ETW Correlation
 
The definitive detection pattern leverages the asymmetry described in Section 9.2. Two observations of the same process-creation event are available:
 
* The **user-mode observation** (Sysmon Event 1, Security Event 4688) records the spoofed parent.
* The **kernel-mode observation** (`Microsoft-Windows-Kernel-Process` provider, event ID 1 "Process Start") records the true calling thread's process.
When these disagree, PPID spoofing has occurred. This is documented behavior — Mark Russinovich's Sysinternals tooling and Microsoft's own threat research have relied on this correlation for years. The detection rule is structurally simple; the operational challenge is ensuring both telemetry sources are collected and correlated.
 
For organizations without kernel ETW ingestion, a secondary heuristic is viable: monitor for any process that invokes `UpdateProcThreadAttribute` with `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`. This API call pattern is rare in legitimate software outside of specific Microsoft tools (some installer frameworks, the Service Control Manager's child process logic). Sysmon does not directly capture API calls, but API Monitor and commercial EDR do.
 
### 9.5 Relationship to DKOM
 
PPID spoofing and DKOM (described earlier in this document) solve different problems via different mechanisms. DKOM hides a process from enumeration entirely by unlinking its `_EPROCESS` from `ActiveProcessLinks`. PPID spoofing keeps the process enumerable but falsifies its origin. An advanced adversary may combine both: a primary malicious process is DKOM-hidden, and its child processes use PPID spoofing to appear to descend from legitimate system processes rather than from the hidden parent. Each technique addresses a different layer of the detection stack, and each has a distinct detection primitive.
