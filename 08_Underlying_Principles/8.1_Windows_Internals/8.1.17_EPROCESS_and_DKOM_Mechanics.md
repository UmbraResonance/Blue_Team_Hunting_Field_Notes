# EPROCESS and DKOM (Direct Kernel Object Manipulation) Mechanics

## 1. The EPROCESS Structure Overview
In the Windows kernel, every active process is represented by an `EPROCESS` (Executive Process) structure. This data structure resides exclusively in kernel memory and acts as the master operational object for a process. It contains critical metadata, including the Process ID (PID), parent PID, security tokens, access rights, and memory directory tables.

For forensic analysts, the `EPROCESS` block is the source of truth for determining what was actively running on a system at the time of a memory capture.

## 2. ActiveProcessLinks and Doubly-Linked Lists
The Windows kernel does not store processes in a simple array. Instead, it links `EPROCESS` structures together using a doubly-linked list via the `ActiveProcessLinks` field.

This list utilizes two critical pointers:
* **FLINK (Forward Link):** Points to the `ActiveProcessLinks` entry of the *next* `EPROCESS` structure.
* **BLINK (Backward Link):** Points to the `ActiveProcessLinks` entry of the *previous* `EPROCESS` structure.

When standard monitoring tools (like Task Manager) or standard API calls (like `EnumProcesses`) request a list of running processes, the OS iterates through this chain by following the `FLINK` pointers.

## 3. Direct Kernel Object Manipulation (DKOM) - The Unlinking Attack
DKOM is a stealth technique utilized by rootkits and advanced malware to manipulate kernel structures directly, effectively bypassing user-land monitoring. 

To hide a malicious process, a rootkit executes a "process unlinking" attack:
1.  The rootkit identifies the `EPROCESS` block of the malicious process (Process B).
2.  It modifies the `FLINK` of the preceding process (Process A) to point directly to the succeeding process (Process C).
3.  It modifies the `BLINK` of the succeeding process (Process C) to point directly to the preceding process (Process A).

**The Result:** The malicious Process B is entirely removed from the `ActiveProcessLinks` chain. It continues to execute on the CPU and consume memory, but any tool relying on the standard linked list will not see it.

## 4. DFIR Detection Strategy: List Walking vs. Pool Tag Scanning
Understanding DKOM dictates how we approach memory forensics:

* **List Walking (`pslist`):** Follows the `ActiveProcessLinks` doubly-linked list. It will **fail** to display processes hidden via DKOM.
* **Pool Tag Scanning (`psscan`):** Ignores the linked list entirely. Instead, it scans the raw memory space for specific pool tags associated with `EPROCESS` structures (e.g., `Proc` or `Proce` tags). 

**Hunting Heuristic:** A classic Indicator of Compromise (IOC) for a rootkit is a discrepancy between list-walking and pool-scanning outputs. If a process appears in `psscan` but is absent in `pslist`, DKOM unlinking is highly probable.
