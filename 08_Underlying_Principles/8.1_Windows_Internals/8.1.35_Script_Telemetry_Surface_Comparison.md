# 8.1.35 Script Telemetry Surface Comparison

> **Core Principle**: Different script languages produce different telemetry because their execution hosts integrate differently with Windows defensive infrastructure. PowerShell has deep AMSI integration and produces Event 4104 with fully deobfuscated script content. Batch/CMD has **no AMSI integration at all**. VBA has AMSI integration only in Office 365 / Microsoft 365, not in legacy Office. WMI scripting is scanned, but through a different provider path than standalone VBS. These differences are not accidents — they reflect which execution paths Microsoft has instrumented and which remain architectural blind spots.
>
> **Blue Team Impact**: Detection strategy depends on what telemetry actually exists for each language. Hunting rules that assume "we can see the deobfuscated content" are correct for PowerShell, partially correct for VBS/JScript on modern Windows, and **architecturally wrong for batch/cmd**. This document provides the reference matrix for which telemetry source catches which language, and where the documented blind spots are. The goal is not a list of event IDs — it is a mental model that tells you, for any given script-based incident, which log to read first and which not to bother with.

## 2. Why PowerShell Has the Richest Telemetry

PowerShell's telemetry is not accidentally richer than other scripting languages' — it is the result of deliberate, multi-year investment in defender-side visibility. Three architectural factors contribute:

### 2.1 AMSI Integration at the ScriptBlock Boundary
PowerShell's parser produces a ScriptBlock object for every piece of code, whether from a file, the command line, or a dynamically-constructed string. The AMSI integration is embedded in `AmsiUtils` class inside `System.Management.Automation.dll` — meaning every ScriptBlock is scanned before compilation to IL.

This placement is optimal for defenders: deobfuscated content is guaranteed (see [8.1.34 §3.1](./8.1.34_Interpreter_Architecture_and_Deobfuscation_Primitives.md)), and the scan happens before any execution side-effects.

### 2.2 Event 4104 Content Fidelity
Event 4104 logs the full ScriptBlock **as seen by the parser**. Because the parser only operates on deobfuscated source (the same architectural necessity that makes sink substitution work), Event 4104 content is post-deobfuscation by definition.

The practical implication: even if AMSI is bypassed, Event 4104 still captures the attempted content. Bypassing AMSI doesn't suppress 4104; it only prevents the pre-execution block.

### 2.3 CLR Integration
PowerShell scripts compile to .NET IL and execute under the CLR. This means PowerShell execution also benefits from the CLR-level telemetry described in [8.1.31 §4](./8.1.31_CLR_and_In_Memory_Assembly_Loading.md) — AMSI-for-CLR scans assembly loads that PowerShell performs via `Add-Type` or `[Reflection.Assembly]::Load`.

Cumulatively, PowerShell attacks face three independent content-inspection layers (AMSI on ScriptBlock, 4104 script logging, AMSI on CLR assembly loads) — an unusual density of telemetry for any scripting language.

## 3. The VBS/JScript Situation

VBS and JScript have AMSI integration since Windows 10 1709 (October 2017), but the integration is less comprehensive than PowerShell's.

### 3.1 The Integration Point
Windows Script Host (`wscript.exe`, `cscript.exe`) and MSHTA (`mshta.exe`) invoke AMSI through a pre-execution scan of each script block before passing it to the script engine (VBScript.dll or JScript.dll). The scan receives the script source in plaintext — after host-level unwrapping (HTA inner scripts, encoded VBE/JSE files) but before the engine tokenizes it.

### 3.2 The Coverage Gaps
Compared to PowerShell:

- **No ScriptBlock-level granularity**: VBS/JS AMSI scans the whole script, not individual blocks. Dynamically-constructed content submitted via `Execute` or `eval` may or may not be rescanned depending on the host and Windows version.
- **No 4104 equivalent in all cases**: While a `Microsoft-Windows-VBScript` ETW provider exists, it is not universally collected or as content-rich as PowerShell 4104. Its presence varies across Windows builds.
- **Encoded scripts (VBE, JSE)**: Microsoft's screnc.exe-encoded scripts used to be a routine evasion; modern hosts decode them before AMSI scans, closing this gap. However, some custom "encoding" schemes that pre-decode via a tiny launcher script may evade.

### 3.3 Detection Implications
For VBS/JScript analysis, AMSI catches unobfuscated or lightly-obfuscated malicious content effectively. Heavily-obfuscated samples that rely on `Execute`/`eval` patterns may evade AMSI but produce telemetry elsewhere — specifically, the COM Automation layer (see [8.1.30 §7](./8.1.30_COM_Automation_and_IDispatch_Interface.md)) provides DLL-load fingerprinting that survives script obfuscation.

The practical hunting approach: combine AMSI events (when available) with COM-layer signals (DLL loads into script hosts). Neither alone provides full coverage; their union does.

## 4. The Batch/CMD Architectural Blind Spot

Batch files and CMD.EXE scripts occupy a unique position: **Microsoft never built AMSI integration into CMD.EXE**. This is not an oversight scheduled for future fixes — it is an architectural reality based on CMD.EXE's legacy and technical constraints.

### 4.1 Why No AMSI Exists for CMD
CMD.EXE dates to DOS. Its architecture predates AMSI, predates ETW script telemetry, predates the concept of content scanning. Adding AMSI integration would require:

- Modifying `cmd.exe` to invoke `amsi.dll` before executing each command
- Defining what "content" to scan — CMD has no clear ScriptBlock equivalent
- Handling the performance impact on batch processing, which is often called from high-throughput contexts

Microsoft has prioritized AMSI integration for languages where the cost-benefit favored investment: PowerShell (high-value attack surface), VBS/JS (common malware), VBA (email-delivered malware). CMD has been left where it always was — a command processor without content inspection.

### 4.2 What This Means Practically
For batch-based malware:

- **No free deobfuscation**: There is no event equivalent to PowerShell 4104. The batch file's source is exactly what gets executed; analysts must read the obfuscated form directly or trace execution manually.
- **No AMSI detection**: Signature-based detection cannot rely on content matching at runtime. Detection must happen elsewhere — at file write (Sysmon EID 11), at command-line logging (Security 4688 or Sysmon EID 1), or at the downstream action (DNS queries, network connections, process creation).
- **Heavy reliance on sub-shell invocations**: Batch frequently calls PowerShell or WSH for actual payload execution. Those invocations *do* fire AMSI for the child process. The batch layer itself is invisible; the payload layer is not.

### 4.3 Detection Approach for Batch
Given the blind spot, detection strategy for batch-based threats centers on:

- **Command-line logging**: Security EID 4688 with command-line arguments enabled, or Sysmon EID 1. This captures the fully-expanded command line after batch variable substitution, which is the closest equivalent to "deobfuscated content" available.
- **Process tree anomalies**: `cmd.exe` spawning `powershell.exe` with encoded commands, or `cmd.exe` spawning `wscript.exe` with suspicious scripts, are high-fidelity signals because batch is rarely the legitimate parent for these patterns in interactive use.
- **Behavioral signals on the payload**: Since batch typically delegates actual payload execution to PowerShell/WSH/PE binaries, detection at that downstream layer works regardless of batch obfuscation.

The implication: batch obfuscation is effective at evading content-inspection tools, but it doesn't evade behavioral detection. For detection engineering, this means batch-based threats require **command-line-centric hunting rules**, not content-matching rules.

## 5. The VBA Version Split

VBA telemetry differs dramatically between Office 365 (current Microsoft 365 builds) and legacy Office (pre-365 or perpetual-license installations).

### 5.1 Office 365 VBA AMSI
Starting with Office 365 Semi-Annual Channel 2004 (April 2020), Office integrates VBA with AMSI. Every VBA procedure is scanned before execution; additionally, macro calls and certain runtime behaviors are tracked.

This brings VBA into parity with PowerShell for content visibility — obfuscated macros are scanned in their runtime-expanded form, and AMSI providers can block or log detections.

### 5.2 Legacy Office: Structural Analysis Only
For Office versions without AMSI integration (Office 2016 perpetual license, Office 2019, and other non-M365 installations), VBA has **no runtime content inspection**. Analysts must recover macro intent through:

- **Document structural parsing** (CFBF / VBA project structure — see [8.1.32](./8.1.32_OLE_Compound_File_and_VBA_Project_Structure.md))
- **olevba / oledump workflow**
- **VBA stomping detection** via `PerformanceCache` vs `CompressedSource` comparison

The macro executes entirely within `winword.exe` / `excel.exe`, and those processes produce no content-level events for macro execution. Sysmon EID 1 captures any child processes the macro spawns, but the macro itself is invisible to content inspection.

### 5.3 The Enterprise Reality
Most enterprises have a mixed fleet — some users on M365, some on perpetual Office. Attackers targeting broad populations must assume the lowest common denominator: no AMSI. This is why modern phishing campaigns delivering malicious documents still work despite AMSI having existed for years.

For detection engineering, this means VBA-based threats require a two-track approach:
- **Content-based detection** (AMSI-derived) for M365 environments
- **Structural detection** (document parsing, child-process anomalies) for all environments

## 6. Multi-Layer Chains and Telemetry Gaps

Real-world malware rarely uses a single language. A typical kill chain involves multiple language transitions, each potentially crossing telemetry boundaries.

### 6.1 A Representative Chain

```
┌──────────────┐
│ Email (.docm) │
└──────┬───────┘
       │  opens in winword.exe → VBA executes
       ▼
┌──────────────┐
│ VBA macro    │  ← Office 365: scanned by AMSI | Legacy: invisible
└──────┬───────┘
       │  Shell() launches cmd.exe
       ▼
┌──────────────┐
│ cmd.exe batch│  ← No AMSI, batch substitution happens here
└──────┬───────┘
       │  cmd.exe runs: powershell -enc <base64>
       ▼
┌──────────────┐
│ PowerShell   │  ← AMSI scans, Event 4104 logs
└──────┬───────┘
       │  [Reflection.Assembly]::Load($bytes)
       ▼
┌──────────────┐
│ .NET payload │  ← AMSI-for-CLR scans the byte[] assembly (if .NET 4.8+)
└──────────────┘
```

### 6.2 Where Telemetry Fires
For the chain above, defender visibility manifests as:

1. **Email layer**: Email security gateway (typically out-of-band from the Windows event log)
2. **VBA layer**: Office AMSI events (if M365); otherwise, only the fact that Word opened the document (no event for macro execution itself)
3. **Batch layer**: Command-line logging (EID 4688 / Sysmon EID 1) for the `cmd.exe` spawn; content of the batch itself invisible
4. **PowerShell layer**: Event 4104 with the deobfuscated `-EncodedCommand` content; AMSI scan event for the content
5. **.NET payload layer**: AMSI-for-CLR scan event; DotNETRuntime ETW assembly load event

### 6.3 The Weakest Link
The chain's observability is limited by its weakest link. If any single stage is uninstrumented or evades telemetry, subsequent stages must be detected independently — you cannot trace forward from an invisible stage.

For the chain above, the **batch layer is the weakest link** in any environment. Even in a fully-instrumented modern environment, the batch substitution and flow control are only visible through the resulting command lines, not through the batch's own logic.

### 6.4 The Detection Engineering Principle
This leads to a practical principle: **never design detection around a single stage assuming the adjacent stages are also visible**. Build detection at each stage independently, because adversaries specifically select stages to hide behind the most opaque telemetry layer in the chain.

Hunting rules should target:
- The PowerShell layer (rich telemetry, high content fidelity)
- The process-creation layer (universal coverage, lower content fidelity)
- The behavioral outcomes (network, file, registry — universal, post-facto)

Not:
- The batch layer (architecturally limited)
- The VBA layer on uninstrumented Office (architecturally limited)

## 7. Summary: The Four Structural Realities

1. **Telemetry surface is language-specific.** There is no universal "script execution log"; there are per-host, per-language integrations at varying depths.
2. **Deobfuscation-for-free is a PowerShell privilege.** Only PowerShell guarantees the defender sees deobfuscated content via logged events. Other languages require AMSI (which can be bypassed) or structural analysis (which cannot see runtime behavior).
3. **Batch/CMD is an architectural blind spot, not an oversight.** Detection for batch-based threats must be command-line-centric and behavioral, not content-based.
4. **Multi-layer chains require per-stage detection.** Attackers deliberately structure kill chains to hide behind the most opaque layer; defenders must detect at every stage independently.

For the detection engineer, the practical takeaway is a ranking of effort-vs-payoff:

- **Highest ROI**: PowerShell 4104 + AMSI content rules. Cheap to implement, high-fidelity, survives most obfuscation.
- **High ROI**: Command-line logging (EID 4688 / Sysmon EID 1) with rich hunting rules. Covers the gap left by batch/CMD.
- **Medium ROI**: COM Automation layer rules (Sysmon EID 7 for script-host DLL loads — see [8.1.30 §7](./8.1.30_COM_Automation_and_IDispatch_Interface.md)).
- **Medium ROI**: Office VBA content rules (valuable in M365 environments, useless on legacy Office).
- **Lower ROI**: Attempting content-inspection rules for batch. The architecture doesn't support it.
