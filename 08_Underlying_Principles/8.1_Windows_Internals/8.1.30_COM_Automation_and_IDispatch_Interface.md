# 8.1.30 COM Automation and the IDispatch Interface

> **Core Principle**: Scripting languages like VBScript, JScript, and PowerShell do not call Windows APIs directly. They reach the OS through **COM Automation** — a late-binding dispatch mechanism built on the `IDispatch` interface that lets an interpreter invoke arbitrary methods on arbitrary objects without compile-time knowledge of either. Every line of the form `CreateObject("Scripting.FileSystemObject")` or `New-Object -ComObject WScript.Shell` is a COM Automation call, and every script-based malware sample you will analyze depends on this mechanism.
>
> **Blue Team Impact**: Script obfuscation rarely targets the language itself — it targets the **COM object names** the script needs to invoke. Understanding the ProgID → CLSID → DLL resolution chain, the `IDispatch::Invoke` path, and the VARIANT type system tells you (a) why `Set` exists in VBScript, (b) why `ADODB.Stream` appearing in a script is a near-definitive indicator of binary payload dropping, and (c) where detection surfaces sit that survive arbitrary script-level obfuscation.

---

## 1. What Problem COM Automation Solves

Windows has two kinds of code consumers:

- **Compiled code** (C, C++, Rust): knows at compile time what functions it will call, what their signatures are, and which DLL exports them. Uses the standard Import Address Table mechanism described in [8.1.15 Portable Executable Architecture](./8.1.15_Portable_Executable_Architecture.md).
- **Interpreted code** (VBScript, JScript, PowerShell, VBA): discovers at runtime what objects exist, what methods they have, and what arguments those methods take. Has no IAT. Has no link step. Cannot know ahead of time that `Scripting.FileSystemObject` will ever be referenced.

COM Automation is Microsoft's solution to the second case. It provides a **universal runtime-discovery interface** that any interpreter can use to invoke any registered COM object, without either side knowing anything about the other at compile time.

The relationship to [8.1.06 COM Architecture and Registry Ledger](./8.1.06_COM_Architecture_and_Registry_Ledger.md) is a layering distinction:

| Layer | Concern | Primary Document |
| :--- | :--- | :--- |
| **OS activation** | RPCSS, `InprocServer32` vs `LocalServer32`, `dllhost.exe` surrogate, registry hive priority (HKCU over HKLM) | 8.1.06 |
| **Automation / script use** | ProgID parsing, `CoCreateInstance` from script, `IDispatch::Invoke`, VARIANT marshaling | **This document** |

Both documents describe the same underlying COM infrastructure, but from different entry points. 8.1.06 answers "how does `dllhost.exe` end up running"; this document answers "how does `CreateObject("...")` end up calling a method."

## 2. The Two Binding Models: Early vs Late

Before describing `IDispatch`, it helps to contrast it with the alternative. COM supports two ways for a client to call a method on an object:

### 2.1 Early Binding (vtable-based)

The client knows at compile time which interface it is calling. Example: a C++ program calls `pFileSystem->CreateTextFile(...)` by dereferencing a **virtual function table (vtable)** — a fixed array of function pointers at the start of the object. Offset 7 in the vtable is always `CreateTextFile`; the compiler encodes this offset directly into the generated machine code.

- **Pros**: Fast (one indirect call), compile-time type checking.
- **Cons**: Requires header files and a type library at build time.
- **Who uses it**: C/C++ clients, high-performance applications, MFC, ATL.

### 2.2 Late Binding (IDispatch-based)

The client does not know at compile time which interface exists or what methods it provides. Instead, it calls a single well-known method — `IDispatch::Invoke` — passing the method name (or a precomputed numeric ID) and an array of arguments. The COM object decodes the method name internally, looks up the correct vtable entry, and dispatches the call.

- **Pros**: Works from any runtime-resolved environment, including scripts.
- **Cons**: Slower (name lookup + argument marshaling per call), no compile-time type checking.
- **Who uses it**: VBScript, JScript, PowerShell, VBA, Excel formulas, any automation client.

**Key insight**: The reason VBScript can call arbitrary COM objects is that **every Automation-compatible object implements `IDispatch`**. The interpreter needs to know how to talk to `IDispatch` and nothing else. The object on the other end translates the generic `IDispatch` call into the specific method the caller named.

## 3. The IDispatch Interface in Detail

`IDispatch` has exactly four methods. Understanding the two that matter explains 90% of what a script interpreter does when executing COM code.

| Method | Purpose |
| :--- | :--- |
| `GetIDsOfNames` | Translate a method name (string) into a numeric DISPID (dispatch ID) |
| `Invoke` | Execute the method identified by a DISPID |
| `GetTypeInfoCount` | Reports whether the object supports type-library introspection |
| `GetTypeInfo` | Returns the type library (enables tools like Object Browser) |

### 3.1 The Two-Phase Call

When an interpreter executes this line:

```vbscript
RX = KH.CreateTextFile(Qa, 1, 0)
```

Internally, it performs two COM calls:

**Phase 1 — Name resolution**:
```
KH->GetIDsOfNames("CreateTextFile") → DISPID 0x60030000  (for example)
```

**Phase 2 — Method invocation**:
```
KH->Invoke(
    dispIdMember = 0x60030000,
    pDispParams  = { Qa, 1, 0 },    // arguments as VARIANTs
    pVarResult   = &returnValue,     // receives the TextStream object
    ...
)
```

The object's implementation of `Invoke` is what turns this generic dispatch call into the actual `CreateTextFile` logic. From the script's perspective, the complexity is invisible — but from the detection perspective, it matters a great deal where each phase happens.

### 3.2 Why This Matters for Analysis

The string `"CreateTextFile"` travels through the interpreter in plaintext, even if the **variable name** holding the object (`KH` above) is heavily obfuscated. This is an architectural fact the obfuscator cannot change: the method name is an argument to `GetIDsOfNames`, not a variable reference.

This leads to a practical analysis heuristic: when reading obfuscated script, **treat method names as ground truth** even when surrounding identifiers are scrambled. `KH.CreateTextFile(...)` tells you unambiguously that `KH` is an object supporting `CreateTextFile` — which narrows the candidate object types to a small set (FSO, a few others). The method name is the anchor; the variable name is noise.

## 4. ProgID, CLSID, and the Resolution Chain

A script never calls `CoCreateInstance` directly. It calls `CreateObject("ProgID")`. Tracing what happens between those two is the key to understanding many COM-related detection signals.

### 4.1 Definitions

- **CLSID (Class Identifier)**: A 128-bit GUID that uniquely identifies a COM class. Example: `{0D43FE01-F093-11CF-8940-00A0C9054228}` is the CLSID for `Scripting.FileSystemObject`.
- **ProgID (Programmatic Identifier)**: A human-readable string that maps to a CLSID. Example: `"Scripting.FileSystemObject"`. Intentionally not globally unique — multiple ProgIDs can map to the same CLSID.

### 4.2 The Resolution Walk

When VBScript executes `CreateObject("Scripting.FileSystemObject")`, the following registry lookups occur in sequence:

```
Step 1: Resolve ProgID → CLSID
    HKCU\Software\Classes\Scripting.FileSystemObject\CLSID  (checked first)
    HKLM\Software\Classes\Scripting.FileSystemObject\CLSID  (fallback)
    → returns {0D43FE01-F093-11CF-8940-00A0C9054228}

Step 2: Resolve CLSID → server binary
    HKCU\Software\Classes\CLSID\{0D43FE01-...}\InprocServer32  (checked first)
    HKLM\Software\Classes\CLSID\{0D43FE01-...}\InprocServer32  (fallback)
    → returns "C:\Windows\System32\scrrun.dll"

Step 3: Load the server
    LoadLibrary("scrrun.dll")
    Call scrrun.dll's DllGetClassObject export
    Request the IDispatch interface on the new object
    Return the IDispatch pointer to the script
```

### 4.3 The HKCU-First Rule Enables Hijacking

The HKCU-before-HKLM priority is the same OS design property described in [8.1.06 §2](./8.1.06_COM_Architecture_and_Registry_Ledger.md). It has two immediate consequences for scripting:

1. **A standard user can redirect any ProgID.** Writing `HKCU\Software\Classes\Scripting.FileSystemObject\CLSID` with a different GUID redirects every `CreateObject("Scripting.FileSystemObject")` call for that user to an attacker-controlled class.
2. **A standard user can redirect any CLSID's InprocServer32.** Writing `HKCU\Software\Classes\CLSID\{0D43FE01-...}\InprocServer32` with a path to a malicious DLL causes that DLL to be loaded into every script process that uses FSO.

These are the registry-level TTPs listed in [4.0 Common Malware Behaviors §8 (COM Hijacking)](../../04_Malware_Analysis_Cheatsheets/4.0_Common_Malware_Behaviors_and_TTPs.md). From the script-analysis perspective, they explain why registry-tampering detection and script-analysis detection are two halves of the same problem.

### 4.4 Monikers: The Other Entry Point

Some COM objects are not reached via `CreateObject`. They are reached via `GetObject` with a **moniker string** — a URI-like syntax that the COM runtime parses to locate an existing object (rather than creating a new one).

Common monikers seen in malicious scripts:

| Moniker | Purpose |
| :--- | :--- |
| `winmgmts:\\.\root\cimv2` | Bind to the local WMI namespace |
| `winmgmts:\\target\root\cimv2` | Bind to remote WMI (lateral movement) |
| `LDAP://CN=Users,DC=corp,DC=local` | Bind to an Active Directory container via ADSI |
| `WinNT://./Administrator` | Legacy local account binding |
| `script:http://attacker.com/payload.sct` | Scriptlet — loads remote XML containing a COM class definition |

The last entry is the notorious **scriptlet moniker** exploited in several public techniques (e.g., `regsvr32 /i:http://...`). It demonstrates that moniker parsing is itself an attack surface — the string is not just a reference, it is an instruction the COM runtime follows.

## 5. The VARIANT Type and Why `Set` Exists

This section answers the question that every analyst coming from Python or JScript asks: **"Why does VBScript require `Set` for some assignments and forbid it for others?"**

### 5.1 The VARIANT Structure

COM Automation must carry arguments between interpreters and objects without knowing their types in advance. To solve this, Microsoft defined the **VARIANT** — a tagged union that can hold any Automation-compatible value.

Simplified structure:

```c
struct VARIANT {
    VARTYPE vt;     // a 16-bit type tag: VT_I4, VT_BSTR, VT_DISPATCH, etc.
    union {
        LONG       lVal;       // if vt == VT_I4
        BSTR       bstrVal;    // if vt == VT_BSTR
        IDispatch* pdispVal;   // if vt == VT_DISPATCH  ← object reference
        // ... many other types ...
    };
};
```

The critical distinction for VBScript: some VARTYPE values represent **values** (numbers, strings, booleans, dates), and one in particular — `VT_DISPATCH` — represents a **pointer to an IDispatch interface**, i.e., an object reference.

### 5.2 Why VBScript Needs Two Assignment Syntaxes

VBScript allows assignment operators to behave differently depending on whether the right-hand side is a value-type VARIANT or a VT_DISPATCH VARIANT:

- **Value assignment** (`x = expr`): the VARIANT is **copied** into the variable. If the source is `VT_I4` (integer), the integer is copied. If the source happens to be `VT_DISPATCH`, VBScript **invokes the object's default property** and copies that value instead.
- **Reference assignment** (`Set x = expr`): the VARIANT is **copied by reference**. If the source is `VT_DISPATCH`, the object pointer is aliased (with reference counting). Using `Set` with a non-object source is a runtime error.

The reason VBScript requires this explicit distinction rather than inferring it: many COM objects have a **default property** that returns a value. Consider:

```vbscript
Dim x
Set x = CreateObject("Scripting.FileSystemObject")  ' x is the FSO object
Dim y
y = CreateObject("Scripting.FileSystemObject")      ' y is... the default property of FSO? runtime error?
```

For `FileSystemObject` specifically, there is no default property, so the second line raises "Object required." But for objects that *do* have default properties (like `TextStream.ReadAll`), the second line would silently assign the string contents. To avoid this ambiguity being implicit, VBScript requires the programmer to declare intent via `Set`.

> **Note**: The "default-property disambiguation" explanation is the widely-accepted community interpretation (discussed in multiple Microsoft-era blog posts by Eric Lippert and others). Microsoft never published a formal language-design rationale; this should be understood as historical consensus rather than an official specification statement.

### 5.3 Why JScript and PowerShell Don't Need `Set`

- **JScript**: All JScript variables are reference types by default (like standard JavaScript). `var x = new ActiveXObject("...")` always holds a reference — there is no "copy the default property" behavior to disambiguate. The VARIANT indirection still exists under the hood, but the language binding hides it.
- **PowerShell**: Similarly reference-by-default. `$fso = New-Object -ComObject Scripting.FileSystemObject` always holds the object reference. PowerShell accesses default properties only through explicit syntax (`$obj.psbase`, etc.).

### 5.4 Analysis Consequence

The `Set` keyword is a reliable **parseable signal** in static VBScript analysis. Every `Set X = Y.Method(...)` line is a guarantee that `Y.Method` returns an object, which in turn constrains the set of possible methods `Y` could be. When reverse-engineering obfuscated VBScript, walking backwards from `Set` assignments is the fastest way to map the object graph without running the script.

This is the parsing habit formalized in [4.3.03 JScript/VBS/HTA Analysis §3.4 Reading Tip](../../04_Malware_Analysis_Cheatsheets/4.3_Script_Deobfuscation/4.3.03_JScript_VBS_HTA_Analysis.md).

## 6. Automation Interfaces Malware Uses Most

This is a reference, not an exhaustive list. Each entry describes why malware reaches for it and what its presence implies.

### 6.1 Filesystem and Binary Dropping

| ProgID | Interface Purpose | Malicious Use Signal |
| :--- | :--- | :--- |
| `Scripting.FileSystemObject` | Text-mode file I/O, directory enumeration | Standard; appears in nearly all scripts |
| `ADODB.Stream` | **Binary** file I/O — read/write arbitrary bytes | **High-fidelity signal**. Text-only scripts have no reason to use this. Appearance almost always indicates dropping an `.exe`, `.dll`, or encrypted payload. |
| `Shell.Application` | Folder operations via Explorer namespace | Used for zip extraction, UAC bypass patterns, verb invocation |

### 6.2 Process Execution and Shell Access

| ProgID | Interface Purpose | Malicious Use Signal |
| :--- | :--- | :--- |
| `WScript.Shell` | Process launch (`.Run`, `.Exec`), registry, environment | The script's primary **sink** — see [4.3.03 §6.1](../../04_Malware_Analysis_Cheatsheets/4.3_Script_Deobfuscation/4.3.03_JScript_VBS_HTA_Analysis.md) |
| `Shell.Application` (`.ShellExecute`) | Launch via Explorer shell — can invoke verbs like "runas" | Used for UAC prompts, file-type-based execution |

### 6.3 Network Transport

| ProgID | Interface Purpose | Distinguishing Behavior |
| :--- | :--- | :--- |
| `MSXML2.XMLHTTP` / `Microsoft.XMLHTTP` | Synchronous HTTP | Most common; first attempt |
| `WinHttp.WinHttpRequest.5.1` | Alternative HTTP | Common fallback if MSXML2 fails |
| `MSXML2.ServerXMLHTTP` | Server-context HTTP | Less commonly chosen; sometimes selected for proxy behavior differences |

Malware routinely tries all three in sequence, because corporate environments sometimes block one but not the others.

### 6.4 Management and Identity

| ProgID / Moniker | Interface Purpose | Detection Relevance |
| :--- | :--- | :--- |
| `winmgmts:\\.\root\cimv2` (via `GetObject`) | WMI namespace access | Enumeration (sandbox check), process creation, lateral movement |
| `LDAP://...` (via `GetObject`) | Active Directory queries via ADSI | Reconnaissance — account enumeration, group membership |
| `WinNT://...` (via `GetObject`) | Legacy SAM database access | Older local-account enumeration, occasionally seen in privilege checks |

### 6.5 Rare but Telling

| ProgID | Signal |
| :--- | :--- |
| `Wbemscripting.SWbemLocator` | Alternative WMI access path — sometimes chosen to evade `winmgmts:` moniker string matching |
| `Schedule.Service` (Task Scheduler) | Scheduled task creation — common persistence |
| `Outlook.Application` | Email enumeration or sending — occasionally seen in exfiltration scripts |
| `Excel.Application` with `.RegisterXLL` | XLL sideloading — loads attacker DLL via Excel's COM automation |

## 7. Why COM-Level Telemetry Survives Script Obfuscation

This section explains **why** COM telemetry is obfuscation-resistant. Concrete detection rules and SPL queries live in folder `01_Hunting_Cheatsheets/` — see the pointer list at the end of this section.

### 7.1 The Architectural Invariant

No matter how a script obfuscates its variable names, string literals, or control flow, three things must happen for a COM object to be used:

1. **A `CoCreateInstance` call with a CLSID** must reach the COM runtime. The CLSID cannot be hidden — it is a 128-bit value the runtime matches against registry entries.
2. **The server DLL must be loaded** via the standard loader path. `LoadLibrary` is called on a concrete disk path resolved from `InprocServer32`. Sysmon Event ID 7 captures this.
3. **Method names pass through `IDispatch::GetIDsOfNames` as literal strings** (see §3.1). If AMSI is scanning the deobfuscated script buffer (see [8.1.28 AMSI](./8.1.28_AMSI_and_Script_Scanning_Architecture.md)), those strings are visible.

Each of these is a choke point below the script-language layer. Obfuscation that concatenates `"ADOD" & "B.Stream"` still ends up calling `CoCreateInstance` with the same CLSID and loading the same DLL as a script that used the cleartext ProgID.

### 7.2 The Two Detection Planes

From these invariants, two obfuscation-resistant detection planes emerge:

**Plane A — DLL load fingerprinting** (Sysmon EID 7):
Every COM object has exactly one `InprocServer32` DLL. Presence of specific DLLs loading into `wscript.exe` / `cscript.exe` / `mshta.exe` is equivalent to presence of specific ProgIDs, without requiring any visibility into script content. This plane is immune to script-level obfuscation because it observes the consequence, not the cause.

**Plane B — Registry tampering detection** (Sysmon EID 13 / Security EID 4657):
COM hijacking requires registry writes to `HKCU\Software\Classes\CLSID\*\InprocServer32` or ProgID keys. These writes are universally logged and the target paths are enumerable.

### 7.3 Where to Implement These Detections

Detection rules belong in the hunting cheatsheets, not in this document. Specifically:

- **Sysmon EID 7 patterns** (DLL-load fingerprinting for script-host processes) → **`01_Hunting_Cheatsheets/1.3_Windows_Event_Core.md`**, under the existing Sysmon Event 7 section. A "Script-Host DLL Load Fingerprint" subsection is a natural fit, listing the ProgID ↔ DLL correspondences.
- **Sysmon EID 13 / Security EID 4657 rules** (CLSID/ProgID hijacking detection) → **`01_Hunting_Cheatsheets/1.1_Master_Hunting_Matrix.csv`**, as new rows under the Persistence/Defense Evasion tactic.
- **AMSI correlation rules** (post-deobfuscation ProgID matching in PowerShell 4104) → already covered generically in `1.3_Windows_Event_Core.md`; specific ProgID match patterns belong there.

> **Verification note**: ProgID ↔ DLL correspondences (e.g., `Scripting.FileSystemObject` → `scrrun.dll`, `ADODB.Stream` → `msado15.dll`, WMI scripting → `wbemdisp.dll`, `MSXML2.XMLHTTP` → `msxml3.dll`/`msxml6.dll` depending on version) should be verified on your target Windows build via Process Monitor before committing to a detection rule. Some ProgIDs have multiple version-specific DLLs, and minimal Windows installations may lack certain components.

### 7.4 The AMSI Intersection

For PowerShell specifically, AMSI (see [8.1.28](./8.1.28_AMSI_and_Script_Scanning_Architecture.md) §3.1) scans the deobfuscated script block, which includes post-concatenation ProgID strings. A script that dynamically builds `"ADOD" & "B.Stream"` is scanned with both parts concatenated, and signature rules applied to Event 4104 content remain effective even against heavy obfuscation. This is complementary to the DLL-load plane: AMSI catches the intent, DLL-load catches the consequence.

## 8. Summary: The Five Invariants

Regardless of how a script is obfuscated, these architectural facts cannot be hidden:

1. **Every `CreateObject` / `GetObject` eventually reaches `CoCreateInstance` or `CoGetObject`** with a CLSID that must exist in a readable registry hive.
2. **Every in-process COM object causes the corresponding DLL to load** via the standard `LoadLibrary` path — visible to Sysmon EID 7 and to any user-mode EDR hook.
3. **Every method call passes through `IDispatch::Invoke`**, which takes the method name or DISPID as an argument the obfuscator cannot remove.
4. **Every VARIANT-typed argument carries its type tag**, enabling runtime introspection that Automation clients (including defender tools) can exploit.
5. **HKCU-level redirection of ProgID or CLSID requires registry writes**, which are universally logged by Sysmon EID 13 or Security EID 4657.

These invariants are why **ProgID-based and DLL-load-based detection rules outperform string-pattern-based detection** of script content. The script can be rewritten arbitrarily; the COM invariants cannot.
