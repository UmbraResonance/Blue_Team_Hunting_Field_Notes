# Windows Execution Ecosystems & The Call Stack

> **Core Principle**: Windows is a layered architecture strictly divided into User Mode and Kernel Mode. Regardless of the high-level language used, every request for system resources must eventually converge at the System Call (Syscall) to cross the boundary into the Kernel.

## 1. Windows Architecture Components (Static View)
Before analyzing execution flows, it's essential to understand the static components of the OS. These components often serve as injection targets, execution proxies, or privilege escalation paths.

### User-Mode Components (Ring 3)
- **System Support Processes**: Crucial components that provide core functionalities but are not standard Windows services (e.g., `winlogon.exe`, `smss.exe`). Advanced malware frequently targets these for process injection due to their high privilege and expected presence.
- **Service Processes**: Background processes hosting Windows services (e.g., Task Scheduler, Windows Update Service).
- **Environment Subsystems**: Components that provide execution environments for specific application types, primarily the **Win32 Subsystem**.
- **Subsystem DLLs**: The "front desk" of the OS. They translate documented functions into internal native system calls.
    - *kernel32.dll*: Handles base infrastructure (memory management, process/thread creation, basic I/O).
    - *advapi32.dll*: Handles security and administration (Access Tokens, Registry, Service Control Manager).
    - *user32.dll*: Manages the Windows GUI and user input processing. 
        - **Hunting Focus**: High-frequency imports here often indicate **Keyloggers** (e.g., using `SetWindowsHookEx`) or screen-capturing spyware.
    - *wininet.dll* (and *winhttp.dll*): High-level Internet communication APIs. 
        - **Hunting Focus**: Strong indicator of network capabilities. Commonly seen in **Droppers** fetching next-stage payloads or malware establishing **C2 Beaconing**.
    - *kernelbase.dll*: The underlying core engine for `kernel32` and `advapi32` in modern Windows architectures. 
        - **Hunting Focus**: Advanced EDRs often place their user-land hooks here. Advanced malware may target it directly for unhooking or API manipulation.

### Kernel-Mode Components (Ring 0)
- **Executive**: The upper layer accessed via `ntdll.dll`. It manages I/O, object management, and houses the Security Reference Monitor (SRM) for access control checks.
- **Kernel**: Manages low-level OS operations like thread scheduling, hardware interrupts, and exception dispatching.
- **Device Drivers**: Software acting as intermediaries, allowing the OS to interact directly with hardware.
- **Hardware Abstraction Layer (HAL)**: An abstraction layer (`hal.dll`) that hides low-level hardware differences from the OS.
- **Windowing and Graphics System (win32k.sys)**: The kernel-mode subsystem responsible for managing the GUI and rendering visual elements (GDI).
    - *Security Context*: Because it parses highly complex data structures (like fonts and bitmaps) directly in Ring 0 for performance reasons, `win32k.sys` is historically one of the most heavily exploited components for **Local Privilege Escalation (LPE)**.

## 2. User-Mode Application Ecosystems
Windows categorizes user-space applications into three primary execution environments, each with distinct auditing characteristics:

| Ecosystem | Technology | Execution Logic | Security & Auditing |
| :--- | :--- | :--- | :--- |
| **Native** | C++, Rust | **Direct Command**. Interacts directly with Win32 APIs and memory pointers. | Opaque, high performance, bypasses AMSI, difficult to reverse-engineer. |
| **Managed** | .NET (C#) | **Supervised**. Runs on the CLR (Common Language Runtime) which manages memory. | Transparent, heavily monitored by AMSI and ETW. |
| **Web-Wrapped**| Electron | **Bridge-based**. Uses a browser engine (Chromium) to call native APIs via a bridge. | Audit focus is on the "Bridge" layer between JS and the OS. |

## 3. The Execution Chain: API Call Flow
When an application requests a privileged operation, the request follows a strict linear lifecycle. 
*Example: A malware process attempting to read credentials from another process's memory using `ReadProcessMemory`.*

1. **Application Layer**: Initiates the request (e.g., malware calls `ReadProcessMemory`, passing the target process handle and memory address).
2. **Runtime Layer (Managed Only)**: If written in C#, `clr.dll` intercepts and translates the request via **P/Invoke**.
3. **Subsystem Layer (Win32 API)**: `kernel32.dll` receives the request. It performs basic parameter validation and acts as the user-mode interface.
4. **Native API Layer (ntdll.dll)**: `kernel32.dll` internally passes the request to `ntdll.dll`. The function is translated to the undocumented Native API counterpart, `NtReadVirtualMemory`. This is the final stop in User Mode.
5. **The Border (Syscall)**: `ntdll.dll` prepares the CPU registers with the specific **Syscall ID** (e.g., `mov eax, 3Fh`) and executes the `syscall` assembly instruction. This triggers a context switch, transitioning the thread to Kernel Mode.
6. **Kernel Execution (ntoskrnl.exe)**: 
    - The Kernel consults the **SSDT (System Service Descriptor Table)** to map the Syscall ID (`3Fh`) to the actual kernel function pointer (`Nt!NtReadVirtualMemory`).
    - The Executive performs the final security validation (checking if the calling process has rights to read the target). Once authorized, it retrieves the physical memory data, copies it to the user buffer, and transitions the thread back to User Mode.

## 4. Detection Strategy: The "Direct Syscall"
* **The Evasion**: Advanced adversaries execute Step 5 directly within their malware code, completely skipping the documented hooks in `kernel32.dll` and `ntdll.dll` to blind User-Land EDR "cameras".
* **Hunting Logic**: Analyze the **Thread Call Stack**. If a Syscall is initiated from a memory region not backed by a legitimate `ntdll.dll` module on disk, it is a high-fidelity indicator of evasion.

## 5. User-to-Kernel Driver Communication (IOCTL & IRP Flow)

> **Core Concept:** While standard APIs (like `ReadProcessMemory`) use predefined Syscalls to talk to the core OS routines, user-mode applications must use a different mechanism to communicate with specific third-party or custom kernel drivers. This is achieved through the I/O subsystem using Device Objects, IOCTLs, and IRPs.

### 5.1 Driver Objects vs. Device Objects
When the Service Control Manager (SCM) loads a `.sys` file into Ring 0, the Windows Object Manager creates a **DriverObject**. This represents the loaded code and its internal state. 

However, user-mode applications cannot talk to a `DriverObject` directly. To expose its functionality to Ring 3, the driver must create at least one **DeviceObject** (e.g., `\Device\MySecurityScanner`) and typically maps it to a symbolic link (e.g., `\\.\MyScanner`) that user-mode applications can open via `CreateFile`.

### 5.2 The Bridge: DeviceIoControl and IOCTLs
To send custom instructions to a driver, a user-mode application uses the `DeviceIoControl` Win32 API. 
* **IOCTL (I/O Control Code):** Instead of calling a specific function name within the driver, the application passes a 32-bit IOCTL code. This code acts as a command router, telling the driver exactly which internal operation to execute (e.g., "Start packet capture" or "Hide this PID").

### 5.3 The Courier: I/O Request Packets (IRP)
When `DeviceIoControl` (or any I/O API like `ReadFile`) is called, the transition to Ring 0 occurs. The Kernel I/O Manager packages the request parameters (the IOCTL code, input buffers, and output buffers) into an **IRP (I/O Request Packet)**.

* **The Dispatch Table (MajorFunctions):** The IRP is sent to the target driver's `DriverObject`. Inside this object is an array of function pointers known as the MajorFunction table (or Dispatch Table). 
* The I/O Manager inspects the type of request (e.g., `IRP_MJ_DEVICE_CONTROL` for IOCTLs, or `IRP_MJ_CREATE` when opening a handle) and routes the IRP to the corresponding function pointer in that table for processing.

### 5.4 DFIR Relevance: IRP Hooking
Understanding this flow is critical for analyzing kernel-mode rootkits, acting as the foundation for the DKOM concepts discussed in [8.1.25]. 

* **The Attack:** A rootkit doesn't always need to hide its own module from the `PsLoadedModuleList`. Instead, it can overwrite the function pointers in the `MajorFunction` table of a *legitimate* driver (such as the NTFS file system driver `ntfs.sys` or the network driver `tcpip.sys`).
* **The Result:** When a user-mode tool asks the legitimate driver to list files or network connections, the IRP is hijacked and routed to the rootkit's malicious code first. The rootkit filters out its own artifacts before passing the request back to the legitimate driver, achieving stealth without touching the linked lists.
