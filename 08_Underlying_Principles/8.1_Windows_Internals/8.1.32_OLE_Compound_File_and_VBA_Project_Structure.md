# 8.1.32 OLE Compound File and VBA Project Structure

> **Core Principle**: Legacy Office documents (`.doc`, `.xls`, `.ppt`) and embedded macro containers are stored in the **OLE Compound File Binary Format (CFBF)** — a hierarchical, FAT-like filesystem-in-a-file that organizes content into "streams" and "storages." Macro code is not stored as plaintext but as a combination of a tokenized compressed stream (`CompressedSource`) and a performance-cache precompiled representation (`PerformanceCache`). The two can disagree. This disagreement is the architectural basis for **VBA stomping** — an evasion technique where the plaintext the analyst sees does not match the code the interpreter executes.
>
> **Blue Team Impact**: Understanding CFBF structure explains (a) why `oledump.py` lists "streams" instead of files, (b) why `olevba` sometimes extracts code that does not match what Word shows, (c) why VBA stomping is undetectable by static content analysis alone, and (d) where in the document structure detection signals actually live. Without this foundation, VBA macro analysis is a cargo-cult exercise of running tools and trusting their output — which breaks down against modern stomped samples.

---

## 1. Why OLE Compound Files Exist

Before 2007, Microsoft Office used a **single binary file** to hold everything a document needed — text, formatting, embedded images, OLE-linked objects, and macros. The design challenge: how to store a hierarchical, growing collection of heterogeneous data inside a flat file while supporting incremental updates without rewriting the entire file every time.

Microsoft's solution, inherited from COM's "Structured Storage" specification, was the **Compound File Binary Format** — a filesystem implemented inside a single file. A CFBF file can hold:

- Named "streams" (equivalent to files — hold arbitrary binary data)
- Named "storages" (equivalent to directories — hold other streams and storages)
- A hierarchical structure with a root storage at the top

This design persisted because it solved a real problem. Modern `.docx` / `.xlsx` / `.pptx` files (Office 2007+) switched to ZIP archives of XML files — but **macro-enabled modern formats** (`.docm`, `.xlsm`, `.pptm`) still contain a legacy CFBF file inside the ZIP archive (as `word/vbaProject.bin`), because the VBA runtime expects CFBF structure. VBA stomping therefore applies to `.docm` files as well as legacy `.doc` files.

## 2. CFBF Physical Structure

A CFBF file is logically a FAT filesystem. The physical layout:

```
+---------------------------------+
| Header (512 bytes)              |  Magic: D0 CF 11 E0 A1 B1 1A E1
+---------------------------------+
| Sector 0 (FAT or Directory)     |  Each sector is 512 or 4096 bytes
+---------------------------------+
| Sector 1                        |
+---------------------------------+
| Sector 2                        |
+---------------------------------+
| ...                             |
+---------------------------------+
```

### 2.1 The Header
The first 512 bytes contain:
- **Magic bytes** (`D0 CF 11 E0 A1 B1 1A E1`) — the CFBF file identifier. Any file beginning with these 8 bytes is a CFBF file regardless of extension.
- **Minor version**, **Major version** — typically 0x003E 0x0003 (version 3) or 0x003E 0x0004 (version 4).
- **Byte order** — always little-endian on modern systems (`FE FF`).
- **Sector size** — 512 bytes (version 3) or 4096 bytes (version 4).
- **Directory sector location** — points to the first sector of the directory structure.
- **FAT sector locations** — pointers to sectors containing the sector allocation table.

### 2.2 The FAT
The File Allocation Table works identically to the FAT in a DOS/Windows filesystem:
- Each entry corresponds to one sector.
- The entry value indicates the next sector in the chain, or special values for end-of-chain (`0xFFFFFFFE`), free (`0xFFFFFFFF`), or FAT sector (`0xFFFFFFFD`).
- A stream's contents are read by following the FAT chain starting from the stream's first sector.

### 2.3 The Directory
The directory is itself a stream (the "Root Entry") containing an array of 128-byte directory entries. Each entry describes one storage or stream:
- **Name** (up to 32 Unicode characters)
- **Type** (storage, stream, or root)
- **Left sibling / right sibling / child pointers** (forms a red-black tree for fast lookup)
- **Start sector** (where the stream's data begins)
- **Stream size**

The directory entries form a tree rooted at the "Root Entry," which represents the top-level storage.

### 2.4 Mini-Streams
For space efficiency, small streams (below a configurable threshold, typically 4096 bytes) are stored in a **Mini-FAT** with 64-byte mini-sectors, backed by a regular stream called the "Mini-Stream." This is transparent at the API level but matters for forensic reconstruction: recovering small streams from a corrupted CFBF file requires understanding the Mini-FAT indirection.

### 2.5 Implications for Analysis
The CFBF structure means that:
- A `.doc` file is not a single blob; it is a collection of dozens of named streams.
- Each macro module, the VBA project metadata, and the dir stream are separate, independently-addressable streams.
- Tools like `oledump.py` enumerate these streams; they do not parse the document content.
- Modifying one stream does not require rewriting others — which is what makes VBA stomping technically feasible.

## 3. The VBA Project Within CFBF

Macro code lives inside a specific storage hierarchy within the document's CFBF. The relevant paths:

```
Root Storage
└── Macros (or _VBA_PROJECT_CUR)          <- VBA project storage
    ├── VBA (storage)
    │   ├── dir                            <- project metadata (compressed)
    │   ├── _VBA_PROJECT                   <- performance cache (precompiled)
    │   ├── Module1                        <- individual module streams
    │   ├── Module2
    │   └── ThisDocument
    ├── PROJECT                            <- text-format project description
    └── PROJECTwm                          <- project workspace metadata
```

The three streams that matter for macro analysis:

### 3.1 The Module Streams (e.g., `Module1`)
Each code module the user wrote corresponds to one stream. The stream contains **two parts** concatenated:

| Offset | Content |
| :--- | :--- |
| `0` to `PerformanceCache.Size` | **PerformanceCache** — precompiled / tokenized VBA, used by the runtime for fast execution |
| `PerformanceCache.Size` onward | **CompressedSource** — the original VBA source code, compressed with VBA's custom RLE-variant algorithm |

The offset between the two parts is stored in the `dir` stream (§3.3).

The critical fact: **the runtime executes the PerformanceCache**, not the CompressedSource. The CompressedSource exists only so that the VBA IDE can show source code to the user and re-compile when the user edits it.

### 3.2 The `_VBA_PROJECT` Stream
A performance cache at the project level, containing cross-module compiled references. Typically binary-only with no source. Less commonly targeted for tampering.

### 3.3 The `dir` Stream
Compressed binary metadata describing:
- Project-level settings (name, version, language ID)
- Module-level settings (each module's name, stream offset, and — critically — the **PerformanceCache offset within its module stream**)
- References to external type libraries

The `dir` stream is compressed using the same VBA compression algorithm as CompressedSource. When `olevba` says "parsing dir stream," this is what it's decompressing to find each module's structure.

### 3.4 The `PROJECT` Stream (Text)
A plaintext INI-style description of the project:
```
ID="{GUID}"
Module=Module1
Module=ThisDocument
HelpFile=""
Name="VBAProject"
```
This stream is not executed; it is project metadata. But it's useful for triage because it's plaintext.

## 4. VBA Compression: The RLE Variant

The VBA compression algorithm used for `CompressedSource` and the `dir` stream is **not** standard gzip/zlib. It is a proprietary run-length-encoding variant defined in `[MS-OVBA]` (the VBA File Format Structure specification).

The algorithm works on 4096-byte "decompression chunks," each preceded by a 2-byte chunk header indicating compression mode (compressed or raw) and chunk length. Within compressed chunks, bytes are emitted either as literal bytes or as `(copy_offset, copy_length)` references to previously-emitted content.

For the analyst, three practical consequences:

1. **Standard decompression tools do not work.** gunzip, zlib, lz77 implementations all fail. You need VBA-aware decompressors (`olevba`, `oledump` with the `-p plugin_vba` option, or the Python `oletools` library's `vbacompression` module).
2. **Custom parsing is feasible but not trivial.** The MS-OVBA specification is public; implementations exist in Python, Go, and C. Most analysts use `oletools` rather than reimplementing.
3. **The algorithm is deterministic and reversible.** There is no encryption. Anyone with the compressed bytes can obtain the source — malicious actors cannot hide source code by "encrypting" it at this layer; they can only obfuscate the source itself.

## 5. VBA Stomping: The Architectural Evasion

VBA stomping exploits the fact that the runtime executes `PerformanceCache` (precompiled tokens) while analysts and editors read `CompressedSource` (source text). If an attacker modifies the `CompressedSource` to be **different from what the `PerformanceCache` actually encodes**, the runtime runs one thing while the analyst sees another.

### 5.1 The Attack
1. The attacker writes malicious VBA code and runs the document on the target version of Office.
2. Office compiles the source and populates `PerformanceCache`.
3. The attacker then replaces `CompressedSource` with benign VBA code (or empty, or decoy content).
4. The document is distributed.

When the victim opens the document:
- The VBA runtime sees the `PerformanceCache` is present and matches the expected Office version.
- It executes `PerformanceCache` directly, bypassing source recompilation.
- The malicious code runs.

When an analyst opens the document:
- `olevba` and similar tools decompress `CompressedSource` and show the benign content.
- The analyst concludes the document is harmless or that the malicious content was already removed.

### 5.2 Why Stomping Is Version-Fragile
`PerformanceCache` format is tied to the specific Office major version and build that compiled it. If the victim's Office version differs from the attacker's compilation version, the cache is rejected and the runtime falls back to recompiling `CompressedSource` — which now contains the benign decoy, defeating the attack.

This version dependence is why stomped documents often target specific Office versions explicitly, and why their effectiveness is a campaign-level concern rather than a universal technique. Modern threat actors maintain fleets of build machines with multiple Office versions to produce version-specific stomped payloads.

### 5.3 Detection Requires Parsing, Not Reading
Detecting stomping cannot be done by reading the VBA source. It requires:

- **Comparing `PerformanceCache` size/hash against `CompressedSource`.** If `CompressedSource` is trivially small or empty while `PerformanceCache` is substantial, the document is suspicious.
- **Attempting to recompile `CompressedSource` and comparing the resulting tokens to `PerformanceCache`.** Identical documents should produce matching caches. `oletools` includes a `pcodedmp`-based check for this.
- **Examining the `dir` stream** for structural inconsistencies between advertised module sizes and actual stream contents.

Tools that surface stomping:

| Tool | Capability |
| :--- | :--- |
| **`pcodedmp.py`** | Decompiles `PerformanceCache` back to VBA pseudocode, allowing comparison against `CompressedSource` |
| **`olevba --decode`** | Shows both source and flags obvious stomping patterns |
| **`oletools.olevba` (Python API)** | Programmatic access to both streams for custom comparison |

## 6. AutoExec and the Macro Execution Trigger

A separate but related concept: **what causes a malicious macro to run in the first place**. Office documents do not auto-execute macros unless explicit triggers are present.

### 6.1 The AutoExec Sub Names
VBA recognizes specific procedure names as automatic execution points:

| Name | Trigger |
| :--- | :--- |
| `AutoOpen` / `Document_Open` (Word) | Document opened |
| `Auto_Open` / `Workbook_Open` (Excel) | Workbook opened |
| `AutoClose` / `Document_Close` | Document closed |
| `AutoExec` (legacy) | Word started (runs before any document loads) |
| `AutoNew` / `Document_New` | New document created from template |

The presence of any of these procedure names in a macro is a strong signal that the macro is designed to run without user interaction (beyond enabling macros).

### 6.2 ActiveX-Triggered Execution
Office forms and ActiveX controls have their own event handlers (`UserForm_Initialize`, `CommandButton1_Click`, etc.). Some malicious documents use these in combination with hidden forms to trigger execution.

### 6.3 Property Accessor Execution
A more subtle technique: certain VBA property accessors execute on object creation. If a malicious class is instantiated during document load (as part of legitimate-appearing initialization), its `Class_Initialize` method runs.

From the detection perspective, the procedure name itself is the cheapest signal — `olevba` flags these automatically. Stomped documents, however, may hide the AutoExec name in the `CompressedSource` while the `PerformanceCache` retains it — another reason source-only analysis is insufficient.

## 7. The Broader Analysis Workflow Context

VBA macro analysis is usually a multi-step pipeline. Understanding where this document fits:

1. **Document triage**: Is this file actually a CFBF file? (Check magic bytes `D0 CF 11 E0 A1 B1 1A E1`.)
2. **Stream enumeration**: What streams exist? Which ones contain VBA? (`oledump.py` at this stage.)
3. **Source extraction**: Decompress `CompressedSource`; this gives the analyst-visible code. (`olevba` here.)
4. **Stomping check**: Compare `CompressedSource` against `PerformanceCache`. (`pcodedmp` here.)
5. **Deobfuscation**: Apply the sink-substitution framework from [4.3.00](../../04_Malware_Analysis_Cheatsheets/4.3_Script_Deobfuscation/4.3.00_Deobfuscation_Methodology.md) to whichever source is the real execution target.
6. **IoC extraction**: From the deobfuscated content, extract URLs, file paths, commands.
7. **Pivot**: If the macro drops a PE, continue with [4.1.01 Static Analysis Triage and Architecture Gate](../../04_Malware_Analysis_Cheatsheets/4.1_Static_Analysis/4.1.01_Static_Analysis_Triage_and_Architecture_Gate.md).

This document is the architectural foundation for steps 1–4. The planned 4.3.02 will operationalize the full pipeline.

### 7.1 The COM Automation Connection
VBA macros reach the OS via the same COM Automation mechanism as VBScript — `CreateObject("WScript.Shell")`, `CreateObject("ADODB.Stream")`, `CreateObject("MSXML2.XMLHTTP")`. Everything in [8.1.30 COM Automation and the IDispatch Interface](./8.1.30_COM_Automation_and_IDispatch_Interface.md) applies directly to VBA analysis: the same ProgIDs, the same DLL-load fingerprints, the same detection-at-the-COM-layer opportunity.

The VBA-specific additions are:
- **Office-embedded execution context** — macros run inside the Office process (`winword.exe`, `excel.exe`), so COM activations are inherited by the Office process's module list rather than appearing in a script host.
- **Office AMSI integration** (Office 365) — VBA procedures are scanned individually by AMSI before execution, providing an additional defensive layer analogous to PowerShell 4104.

## 8. Summary: The Five Structural Facts

Regardless of document obfuscation or tampering technique:

1. **Every macro-containing legacy Office document is a CFBF file.** Magic-byte check is definitive.
2. **VBA source is split into two parts per module** — `PerformanceCache` (executed) and `CompressedSource` (read by tools).
3. **The VBA runtime executes `PerformanceCache` when its version matches the Office build.** This is the architectural basis for stomping.
4. **VBA compression is the proprietary `[MS-OVBA]` algorithm** — not gzip, not zlib. Requires specialized tooling.
5. **COM Automation is the bridge to the OS.** Every malicious macro's interesting behavior eventually invokes a COM object, making the telemetry from [8.1.30](./8.1.30_COM_Automation_and_IDispatch_Interface.md) applicable.

These facts mean a complete VBA macro analysis requires parsing both the structural container (CFBF) and the semantic content (both source representations), not just reading source text.
