# Cross-Protocol Authentication Visibility Matrix

> **Core Concept:** Windows Security Event Log (specifically Event 4624) is not a universal 
> record of "who authenticated where." It is a record of what the **Local Security Authority 
> (LSA)** processed. Protocols that bypass the LSA — or that authenticate outside Windows 
> entirely — leave no trace in 4624, regardless of how critical they are to the business.
> 
> **Blue Team Impact:** Building a detection strategy around "watch 4624" assumes all 
> authentication flows through LSA. This assumption fails for SQL Server logins, OAuth 
> tokens, anonymous RPC calls, Forms-auth web apps, and any Modern Auth scenario. The 
> result is a silent visibility gap that attackers routinely exploit. This document maps 
> every major Windows-adjacent authentication protocol to its actual telemetry surface, 
> so you know *which log to look at* before the incident, not after.

---

## 1. The Three Authentication Architecture Patterns

Before enumerating protocols, it helps to recognize that every authentication flow falls 
into one of three architectural patterns. Once you can classify a protocol, you can predict 
its telemetry behavior without memorizing each case.

### 1.1 Pre-Authentication (Credentials Verified Before Session Established)
Credentials are validated at the network/transport layer **before** the application-level 
session is built. The LSA is invoked upfront.

* **4624 Behavior:** Produces a **Type 3 (Network)** event carrying the real `SourceNetworkAddress`. Any downstream terminal logon (Type 10 / 5 / 2) is a *later* event referencing the same user context but with potentially degraded IP fidelity.
* **Examples:** RDP with NLA, SMB, WinRM, DCOM/WMI, LDAP with SASL bind, Windows Authentication to MSSQL.
* **Hunting Anchor:** Always pivot on the **upstream Type 3** for source attribution.

### 1.2 In-Session Authentication (Credentials Verified After Session Established)
The application session is built first, then credentials are submitted inside that session. 
Only a terminal logon event is produced.

* **4624 Behavior:** Produces only a **terminal logon event** (e.g., Type 10 for legacy RDP). No preceding Type 3.
* **Examples:** RDP without NLA, some legacy terminal protocols, interactive local logon.
* **Hunting Anchor:** The terminal event itself carries the real IP. **An isolated terminal logon in an environment that should enforce pre-auth is itself a configuration-drift signal.**

### 1.3 Out-of-LSA Authentication (Credentials Never Touch LSA)
Authentication is handled entirely by the application or a cloud identity provider. LSA is 
never invoked.

* **4624 Behavior:** **No 4624 generated at all.**
* **Examples:** SQL Server native authentication, Forms/JWT/OAuth web apps, Modern Auth to Entra ID, anonymous protocol bindings.
* **Hunting Anchor:** You must query the application-specific or cloud-specific log. Treating the absence of 4624 as "nothing happened" is the single most common detection gap in modern environments.

## 2. Protocol-by-Protocol Breakdown

### 2.1 SMB (File Sharing / IPC$ / ADMIN$)
SMB has been pre-auth by design since SMBv2. Credentials are exchanged during the 
`SESSION_SETUP` command before any file or pipe operations.

* **Pattern:** Pre-Auth
* **4624 Type:** 3 (Network)
* **`SourceNetworkAddress`:** Reliable
* **Key Variables:**
    * **NTLM vs Kerberos:** Revealed by `AuthenticationPackageName`. NTLM on a domain account = potential relay or downgrade attack.
    * **SMB Signing:** Not a telemetry variable, but its absence enables relay attacks that produce *valid-looking* Type 3 events from unexpected hosts.
    * **SMB over QUIC (Server 2022+):** 4624 unchanged; network-layer visibility shifts from TCP/445 to UDP/443.
* **Detection Notes:** Always cross-reference with Event 4776 (NTLM credential validation on DC) to detect protocol downgrade patterns.

### 2.2 RDP

RDP is the canonical example of a protocol whose 4624 behavior changes based on a security 
setting. See **[8.1.11_LSA_Logon_Session_Chain_and_Logon_Types](../8.1_Windows_Internals/8.1.11_LSA_Logon_Session_Chain_and_Logon_Types.md)** for the full session-chain analysis.

#### 2.2.1 RDP with NLA (Modern Default)
* **Pattern:** Pre-Auth
* **4624 Sequence:** Type 3 (upstream) → Type 10 (downstream)
* **`SourceNetworkAddress`:** Real IP **only in Type 3**. Type 10 often shows `::1` / `127.0.0.1` / empty.
* **Hunting Rule:** Any Type 10 investigation must pivot backwards to its paired Type 3.

#### 2.2.2 RDP without NLA (Legacy / Misconfigured)
* **Pattern:** In-Session
* **4624 Sequence:** Isolated Type 10
* **`SourceNetworkAddress`:** Real IP in Type 10 itself
* **Hunting Rule:** In an environment where NLA should be enforced, an isolated Type 10 with no preceding Type 3 is a configuration-drift or tampering indicator. Correlate with Sysmon Event 13 monitoring:  
  `HKLM\SYSTEM\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp\UserAuthentication`  
  (value `0` = NLA disabled, `1` = NLA enforced).

### 2.3 WinRM / PowerShell Remoting
WinRM runs over HTTP(S) via WS-Management. It supports several authentication mechanisms, 
each with distinct telemetry and risk profiles.

| WinRM Auth Mode | 4624 Behavior | Risk Profile |
|---|---|---|
| **Kerberos / Negotiate (default)** | Type 3 upstream, then process creation under `WmiPrvSE.exe` or `wsmprovhost.exe` | Standard; safest mode |
| **CredSSP** | Type 3 upstream, but credentials are **forwarded** into remote LSASS | High — remote host now holds usable credentials; Mimikatz target |
| **Basic Authentication** | Type 3 with anomalous/empty `AuthenticationPackageName` | Very high — credentials transmitted in clear (HTTP) or TLS-only (HTTPS); rare in production |
| **Digest** | Same as Basic but with digest hashing | Legacy; avoid |

* **Key Variable:** CredSSP enablement is the WinRM analogue of "NLA disabled" — it trades credential confidentiality for double-hop convenience. Check:  
  `HKLM\SYSTEM\CurrentControlSet\Control\Lsa\CredSSP\*`  
  and the GPO path `Computer Config → Admin Templates → System → Credentials Delegation`.

### 2.4 WMI / DCOM (Classic Remote WMI)
Classic remote WMI (`wmic /node:`, `Invoke-WmiMethod -ComputerName`, `Get-WmiObject -ComputerName`) runs over DCOM/RPC on port 135 plus a dynamic high port.

* **Pattern:** Pre-Auth
* **4624 Sequence:** Type 3 only — **no Type 5**, because WMI does not use SCM. The target process is spawned directly by `WmiPrvSE.exe`.
* **`SourceNetworkAddress`:** Reliable
* **Why Attackers Prefer It Over PsExec:** PsExec leaves a loud SCM trail (service creation, service start, service deletion — Events 7045 / 7036). WMI leaves only a Type 3 plus process creation under `WmiPrvSE.exe`. Cleaner signal, harder to fingerprint.
* **Reference:** See [8.1.23_WMI_and_CIM_Repository_Architecture](../8.1_Windows_Internals/8.1.23_WMI_and_CIM_Repository_Architecture.md)

### 2.5 MS-RPC (Generic Remote Procedure Call)
RPC is the substrate under SCM, Task Scheduler, Remote Registry, Event Log, EFSRPC, DFS, 
and many other services. Its telemetry behavior depends on the **Authentication Level** 
configured on each specific RPC interface.

| RPC Auth Level | 4624 Produced? | Significance |
|---|---|---|
| `RPC_C_AUTHN_LEVEL_NONE` | **No** | Anonymous call — exploited by PetitPotam, PrinterBug, DFSCoerce, ShadowCoerce |
| `RPC_C_AUTHN_LEVEL_CONNECT` | Yes (Type 3) | Standard authenticated RPC |
| `RPC_C_AUTHN_LEVEL_PKT_INTEGRITY` | Yes (Type 3) | Signed calls |
| `RPC_C_AUTHN_LEVEL_PKT_PRIVACY` | Yes (Type 3) | Signed + encrypted |

* **Critical Hunting Insight:** Coercion attacks (PetitPotam et al.) work precisely because certain RPC interfaces accept `RPC_C_AUTHN_LEVEL_NONE`. The coercion call itself does **not** produce a 4624 on the target. The detection pivot is the *outbound* authentication the target is tricked into making — which *does* produce a 4624 at the relay destination.
* **Transport Variants:** Named Pipe (over SMB) → inherits SMB telemetry. TCP (`ncacn_ip_tcp`) → independent Type 3. LRPC (local) → no 4624.

### 2.6 LDAP / LDAPS
LDAP has three binding modes, each mapping cleanly to one of the three architectural 
patterns.

| LDAP Bind | Pattern | 4624 Produced? | Notes |
|---|---|---|---|
| **Anonymous Bind** | Out-of-LSA | No | Reconnaissance vector; may expose directory info without any auth log |
| **Simple Bind (plaintext)** | Pre-Auth | Yes (Type 3) | Credentials transmitted in clear unless wrapped in TLS; relay target |
| **SASL/GSSAPI (Kerberos)** | Pre-Auth | Yes (Type 3) | Standard secure mode |
| **SASL + Sign & Seal** | Pre-Auth | Yes (Type 3) | Signing prevents tampering and relay |

* **Key Variable:** LDAP Signing enforcement is the LDAP analogue of NLA. If signing is not enforced, Simple Bind over LDAP (389) becomes a target for NTLM Relay — the attacker captures an NTLM response elsewhere and replays it against the DC's LDAP endpoint to take over an account (see CVE-2019-1040, "Drop the MIC").
* **Detection Supplement:** Enable Event 2889 on DCs (Directory Services event log) to log unsigned LDAP binds. This event has no 4624 equivalent — if you only watch Security Log, you miss the entire LDAP Signing visibility layer.

### 2.7 Microsoft SQL Server
SQL Server supports two authentication models. Which one is in use determines whether the 
login appears in Windows Security Log at all.

| SQL Auth Mode | Pattern | 4624 Produced? | Where to Find the Login Record |
|---|---|---|---|
| **Windows Authentication** | Pre-Auth | Yes (Type 3, `LogonProcessName=Advapi`, `AuthenticationPackageName=NTLM` or `Kerberos`) | Windows Security Log + SQL Server Audit |
| **SQL Authentication (SA + database users)** | Out-of-LSA | **No** | SQL Server Error Log + SQL Server Audit (if enabled) |

* **Critical Gap:** An attacker brute-forcing `sa` over TCP/1433 produces **zero events in Windows Security Log**. The only records are in SQL Server's own logs, which are frequently not forwarded to the SIEM.
* **Mandatory Supplements:** Enable SQL Server Audit (`CREATE SERVER AUDIT`) and configure it to capture `FAILED_LOGIN_GROUP` and `SUCCESSFUL_LOGIN_GROUP`. Forward the audit log to the SIEM.

### 2.8 IIS / Web Application Authentication
IIS's telemetry behavior depends entirely on the authentication method configured per site 
or per virtual directory. This is the single most fragmented area of Windows authentication 
visibility.

| IIS Auth Method | Pattern | 4624 Produced? | Notes |
|---|---|---|---|
| **Anonymous** | Out-of-LSA | No (uses IUSR or App Pool Identity) | Standard for public web content |
| **Basic** | Pre-Auth | Yes (Type 3 per request) | High volume; low signal-to-noise |
| **Windows Integrated (NTLM/Negotiate)** | Pre-Auth | Yes (Type 3 on first request; may cache) | Standard for intranet apps |
| **Client Certificate** | Pre-Auth | Yes (Type 3, Kerberos or custom package) | Smart card / PKI authentication |
| **Forms Authentication** | Out-of-LSA | **No** | ASP.NET managed; credentials in app DB |
| **OAuth / JWT / OpenID Connect** | Out-of-LSA | **No** | Modern pattern; token-based |

* **Critical Gap:** Any web application using Forms, JWT, or OAuth is invisible to Windows Security Log. Compromise via these paths requires application-layer logging (IIS logs, application logs, WAF logs).

### 2.9 Exchange Server (On-Premises)
Exchange is the most authentication-complex first-party Microsoft product. It inherits IIS's 
fragmentation and adds its own audit infrastructure.

| Exchange Interface | Auth Mechanism | 4624 Produced? | Dedicated Log |
|---|---|---|---|
| **OWA** | Basic / Forms / Modern Auth (varies) | Conditional | IIS logs + Exchange audit |
| **ECP (Admin Center)** | Integrated Windows | Yes (Type 3) | Exchange Admin Audit Log |
| **EWS (Exchange Web Services)** | Basic / NTLM / OAuth | Conditional | IIS logs |
| **ActiveSync** | Basic (historically) / OAuth (modern) | Conditional | IIS logs |
| **MAPI over HTTP** | NTLM / Kerberos / OAuth | Conditional | IIS logs |
| **PowerShell (Remote Exchange Management Shell)** | WinRM pattern | Yes (Type 3) | WinRM logs + Exchange cmdlet log |

* **Mailbox-Level Actions:** Reading emails, forwarding, delegation changes, and inbox rule creation are **not** logged in 4624 — they are logged in the **Mailbox Audit Log** (`Search-MailboxAuditLog`) or **Unified Audit Log** in hybrid/cloud deployments. An attacker with valid credentials reading mailboxes produces one Type 3 at login, then nothing in Security Log for the rest of the session.
* **Hybrid Consideration:** On-prem Exchange fronting Exchange Online (classic hybrid) may produce 4624 on-prem for authentication that ultimately traverses to the cloud. Trace direction matters.

### 2.10 Modern Auth (Entra ID / Azure AD)
Modern Auth replaces the LSA-centric model entirely. Cloud identity providers issue OAuth 2.0 
access tokens and refresh tokens. Token validation happens at the resource (Graph API, 
SharePoint Online, etc.), not via LSA.

* **Pattern:** Out-of-LSA (from the on-premises perspective)
* **4624 Produced?** Only when a **Hybrid-Joined** device's user signs in locally — a side effect, not a record of the cloud authentication itself.
* **Authoritative Log:** **Entra ID Sign-in Logs**, accessible via Azure Portal, Microsoft Graph (`auditLogs/signIns` endpoint), or Microsoft Sentinel.
* **Critical Detection Gap:**
    * Token replay attacks produce **no** 4624 and often no Sign-in Log either (if the token is valid).
    * Illicit Consent Grants (malicious OAuth apps) produce no 4624 on any endpoint.
    * AiTM phishing (Adversary-in-the-Middle, e.g., Evilginx) captures tokens that work without further authentication; detection requires risk-based signals in Entra ID Protection, not traditional logon events.

### 2.11 Network Device and Third-Party Integrations
For completeness: VPN concentrators (RADIUS), wireless authentication (802.1X/EAP), 
identity-brokered SaaS logins (SAML federation), and jump boxes with their own auth layers 
all fall outside LSA unless specifically configured to delegate to AD.

* **Implication:** A single user action ("log into the corporate VPN") may produce a RADIUS accounting log, an AD Kerberos AS-REQ (Event 4768), a firewall session log, and no 4624 at all, depending on topology. Mapping your organization's identity flow is a prerequisite to building complete detection.

## 3. Three Detection Principles

Once the matrix above is internalized, three horizontal detection principles emerge. These 
are the heuristics that separate surface-level 4624 monitoring from actual authentication 
hunting.

### Principle 1: "Should-have-4624-but-doesn't" Is Itself a Signal
Certain attack techniques are identifiable precisely by their *absence* from Security Log.

* **Anonymous RPC coercion** (PetitPotam class) — no 4624 at the target of coercion, but a chain of outbound authentications at the relay destination.
* **SQL Authentication login bypass** — bypasses Windows logon entirely.
* **Anonymous LDAP bind for reconnaissance** — no authentication record.
* **Legacy Basic Auth against Exchange** where Modern Auth should be enforced — indicates a protocol-downgrade attempt.

**Hunting Approach:** Baseline *expected* 4624 patterns for each service, then alert on service access (network connection, application-layer log entry) that occurs without a corresponding 4624.

### Principle 2: "4624 Exists but IP Is Not Trustworthy" Requires Upstream Correlation
All terminal logon types (Type 10 / 5 / 2) are downstream evidence. The authoritative 
`SourceNetworkAddress` lives in the paired upstream Type 3.

* **RDP with NLA** — Type 10 shows `::1`; Type 3 shows real IP.
* **PsExec** — Type 5 shows `NT AUTHORITY\SYSTEM`; Type 3 shows the attacker's source.
* **WinRM** — process creation under `wsmprovhost.exe` shows nothing useful; Type 3 shows the source.

**Hunting Approach:** Never alert on a terminal logon alone. Always pivot to the upstream Type 3 within a 1–5 second window matching `TargetUserName + TargetDomainName`.

### Principle 3: "Single-Source 4624" Is Insufficient for Complete Coverage
Modern environments span Windows LSA, cloud IdP, and per-application authentication. No 
single log source covers the full authentication surface.

Required telemetry sources for complete visibility:

| Telemetry Source | Covers |
|---|---|
| Windows Security Event Log (4624/4625/4776) | LSA-mediated authentications |
| Entra ID Sign-in Logs | Modern Auth, cloud apps |
| Entra ID Unified Audit Log | Admin actions, consent grants, mailbox operations |
| Exchange Mailbox Audit Log | Mailbox-level access (on-prem) |
| SQL Server Audit | SQL Authentication logins |
| IIS Access Logs | Web application authentication attempts |
| RADIUS / NPS Logs | VPN and 802.1X authentication |
| WinRM Operational Log | PowerShell Remoting sessions |
| DC Directory Services Log (Event 2889) | Unsigned LDAP binds |

**Hunting Approach:** For any authentication-related investigation, determine which protocols are in scope and query all relevant sources in parallel. Treating Security Log as ground truth produces false negatives.
