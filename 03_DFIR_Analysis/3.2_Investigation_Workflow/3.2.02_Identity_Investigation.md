# Identity Investigation

> **Focus:** Structured workflow for investigating a suspicious account, SID, or logon session — from session origin tracing to full account lifecycle reconstruction.

> **Environment:** Splunk · Windows Security Events · Sysmon

> **Enter here when you have:** A suspicious account name, SID, `Logon_ID`, or an anomalous authentication event (4624/4625/4648/4672).

> **Pivot keys produced:** `Logon_ID`, `Target_SID`, session origin IP — consumed by [`3.2.03`](3.2.03_Process_Execution_Investigation.md) and [`3.2.05`](3.2.05_Kerberos_AD_Investigation.md).

> **Note:** Replace `<ACCOUNT>`, `<SID>`, `<LOGON_ID>`, `<HOST>`, and `<IP>` with case-specific values. All timestamps UTC.

> **SPL Reference:** Security event `rex` templates → [`6.06 §6`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#windows-security-event--message-field-extraction) · Field normalisation → [`6.06 §3.6`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#36-field-normalisation-across-sources-coalesce) · Session pivot pattern → [`6.06 §7.3`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#73-cross-sourcetype-session-pivot-logonid--logon_id)

## Phase 0: Scope

*Before querying individual EIDs, establish the full telemetry picture for the target account and its associated hosts.*

### Step 1: Account Presence Across Sources

*Identify every index and sourcetype that contains events for the target account. Prevents wasted pivots against sources that have no data.*

```spl
index=* ("<ACCOUNT>" OR "<SID>")
| stats count by ComputerName, index, sourcetype, EventCode
| sort - count
```

### Step 2: Host Footprint

*Surface every host the account has touched to define the blast radius before drilling into individual machines.*

```spl
index=* EventCode IN (4624, 4625, 4648, 4672, 4768, 4769)
    (Account_Name="<ACCOUNT>" OR Security_ID="<SID>")
| stats
    min(_time) as First_Seen,
    max(_time) as Last_Seen,
    dc(EventCode) as Unique_EIDs,
    values(EventCode) as EIDs
    by ComputerName
| eval
    First_Seen=strftime(First_Seen, "%Y-%m-%d %H:%M:%S"),
    Last_Seen=strftime(Last_Seen, "%Y-%m-%d %H:%M:%S")
| sort - Last_Seen
```

> **Hunting Tip:** An account appearing on hosts outside its expected scope (e.g. a service account logging into workstations, or a standard user account present on a DC) is the primary lateral movement signal at this phase — note each anomalous host before proceeding.

## Phase 1: Authentication Audit

*Reconstruct every logon session for the target account: when, from where, with what privilege level, and via which authentication method.*

### Step 1: Successful Logons (EID 4624)

*Full logon table with session context. See [`6.06 §6.2`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#62-extended-new-logon-block--domain-and-sid) for the extended extraction template.*

```spl
index=* EventCode=4624
    (Account_Name="<ACCOUNT>" OR Security_ID="<SID>")
| rex field=Message "Subject:[\s\S]*?Account Name:\s+(?<Subject_Account>[^\s]+)"
| rex field=Message "New Logon:[\s\S]*?Security ID:\s*(?<Target_SID>[^\r\n]+)"
| rex field=Message "New Logon:[\s\S]*?Account Name:\s+(?<Target_Account>[^\s]+)"
| rex field=Message "New Logon:[\s\S]*?Account Domain:\s+(?<Target_Domain>[^\s]+)"
| rex field=Message "Workstation Name:\s*(?<Workstation_Name>.*?)\s*Source Network Address:"
| eval Workstation_Name=if(trim(Workstation_Name)="", "N/A", Workstation_Name)
| search Target_Account="<ACCOUNT>"
| table _time, ComputerName, EventCode, Subject_Account, Target_Domain,
    Target_Account, Target_SID, Logon_Type, Logon_ID, Workstation_Name,
    Authentication_Package, Elevated_Token, Source_Network_Address, Source_Port, Logon_Process
| sort _time
```

**Logon_Type reference — anomaly triggers:**

| Type | Meaning | Anomaly Signal |
| :--- | :--- | :--- |
| `2` | Interactive (console) | Admin account logging into workstation directly |
| `3` | Network | Expected for file shares and PsExec; unexpected source IP is the signal |
| `4` | Batch | Scheduled task execution — check the task definition |
| `5` | Service | Service account logon — unexpected host is the signal |
| `7` | Unlock | Workstation unlock — mismatched host suggests RDP session |
| `10` | RemoteInteractive | RDP — expected on jump hosts, anomalous elsewhere |

### Step 2: Failed Logons (EID 4625)

*Pattern of failures before a success indicates brute force or password spray. Sub Status code identifies the failure reason.*

```spl
index=* EventCode=4625
    (Account_Name="<ACCOUNT>" OR Target_Account_Name="<ACCOUNT>")
| rex field=Message "Failure Information:[\s\S]*?Sub Status:\s*(?<Sub_Status>[^\s]+)"
| stats
    count as Failures,
    values(Sub_Status) as Failure_Reasons,
    dc(ComputerName) as Unique_Hosts,
    values(ComputerName) as Hosts,
    dc(Source_Network_Address) as Unique_Sources,
    values(Source_Network_Address) as Sources
    by Account_Name
| sort - Failures
```

**Sub Status reference:**

| Code | Reason | Implication |
| :--- | :--- | :--- |
| `0xC000006A` | Wrong password | Brute force or fat-finger |
| `0xC0000064` | Account does not exist | Username enumeration / spray against wrong domain |
| `0xC000006D` | Bad username or auth | Generic failure — check source IP |
| `0xC0000072` | Account disabled | Attempted use of a disabled account — backdoor attempt? |
| `0xC000006F` | Outside allowed hours | Policy-based restriction triggered |
| `0xC0000234` | Account locked out | Brute force threshold exceeded |

### Step 3: Explicit Credential Use (EID 4648)

*EID 4648 fires when a process uses credentials other than the currently logged-on user — RunAs, PtH, Impacket, and most lateral movement tools generate this.*

```spl
index=* EventCode=4648
    (Account_Name="<ACCOUNT>" OR Target_Account_Name="<ACCOUNT>")
| rex field=Message "Subject:[\s\S]*?Account Name:\s+(?<Subject_Account>[^\s]+)"
| rex field=Message "Account Whose Credentials Were Used:[\s\S]*?Account Name:\s+(?<Used_Account>[^\s]+)"
| rex field=Message "Target Server:[\s\S]*?Target Server Name:\s*(?<Target_Server>[^\r\n]+)"
| table _time, ComputerName, Subject_Account, Used_Account, Target_Server,
    Logon_ID, Process_Name
| sort _time
```

> **Hunting Tip:** `Subject_Account` ≠ `Used_Account` is the defining signal — the logged-on user is invoking a different credential. `Target_Server` identifies the destination being accessed. A non-interactive process (`Process_Name` not in `{explorer.exe, runas.exe}`) generating 4648 is a strong lateral movement indicator.

## Phase 2: Privilege Audit

*Determine what privileges the account holds and on which hosts — escalated privileges on unexpected machines confirm the account has been compromised and used laterally.*

### Step 1: Privileged Token Assignment (EID 4672)

*See [`6.06 §6.5`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#65-privilege-use-eid-4672--canonical-privilege-set) for the full canonical privilege extraction template.*

```spl
index=* EventCode=4672
    (Account_Name="<ACCOUNT>" OR Security_ID="<SID>")
| rex field=Message "Subject:[\s\S]*?Account Name:\s+(?<Subject_Account>[^\s]+)"
| rex "(?s)Privileges:\s+(?<Privileges_Raw>.*)"
| search NOT Subject_Account="-"
| rex field=Privileges_Raw max_match=0 "(?<Privilege_List>Se[A-Za-z]+Privilege)"
| eval Privileges_Canonical=mvjoin(mvsort(Privilege_List), ", ")
| stats earliest(_time) as First_Seen, latest(_time) as Last_Seen
    by Subject_Account, Privileges_Canonical, ComputerName
| eval
    First_Seen=strftime(First_Seen, "%Y-%m-%d %H:%M:%S"),
    Last_Seen=strftime(Last_Seen, "%Y-%m-%d %H:%M:%S")
| sort - Last_Seen
```

### Step 2: Privilege Escalation Signal — Unexpected Host Scope

*Filter for privileged sessions on hosts where the account is not expected.*

```spl
index=* EventCode=4672
    Security_ID="<SID>"
    NOT ComputerName IN ("<EXPECTED_HOST_1>", "<EXPECTED_HOST_2>")
| rex field=Message "Subject:[\s\S]*?Account Name:\s+(?<Subject_Account>[^\s]+)"
| table _time, ComputerName, Subject_Account, Logon_ID
| sort _time
```

## Phase 3: Session Deep-Dive

*Given a `Logon_ID` recovered from Phase 1 or Phase 2, reconstruct everything that happened within that session.*

### Step 1: Session Origin Confirmation

```spl
index=* (Logon_ID="<LOGON_ID>" OR LogonId="<LOGON_ID>") EventCode=4624
| rex field=Message "Subject:[\s\S]*?Account Name:\s+(?<Subject_Account>[^\s]+)"
| rex field=Message "New Logon:[\s\S]*?Account Name:\s+(?<Target_Account>[^\s]+)"
| rex field=Message "Workstation Name:\s*(?<Workstation_Name>.*?)\s*Source Network Address:"
| eval Workstation_Name=if(trim(Workstation_Name)="", "N/A", Workstation_Name)
| table _time, ComputerName, Subject_Account, Target_Account, Logon_ID,
    Logon_Type, Workstation_Name, Source_Network_Address, Authentication_Package,
    Logon_Process, Elevated_Token
```

### Step 2: Process Activity Under Session (Cross-Sourcetype Pivot)

*See [`6.06 §7.3`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#73-cross-sourcetype-session-pivot-logonid--logon_id) for the full pivot pattern and field name gotcha.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=1
    (LogonId="<LOGON_ID>" OR LogonId="<LOGON_ID_HEX>")
| table _time, ComputerName, LogonId, ParentImage, ParentProcessGuid,
    Image, ProcessGuid, CommandLine
| sort _time
```

> **Hunting Tip:** The `ProcessGuid` values returned here are the input for [`3.2.03`](3.2.03_Process_Execution_Investigation.md) — hand them off to open a full process execution investigation without restarting from the account level.

### Step 3: Session Termination (EID 4634 / 4647)

*Establish the session duration — an unusually long session or one that never terminates cleanly may indicate a persistent implant or a sleeping shell.*

```spl
index=* EventCode IN (4634, 4647)
    Logon_ID="<LOGON_ID>"
| table _time, ComputerName, EventCode, Account_Name, Logon_ID
| sort _time
```

## Phase 4: Account Lifecycle Reconstruction

*Determine whether the account itself was modified, created, or weaponised during the incident window. Attackers use two distinct patterns — each leaves a different EID trail and requires a different detection approach.*

**Pattern A — New account creation:** Noisier, easier to detect. Generates EID 4720 → 4722 → 4728 → 4738 in sequence.

**Pattern B — Dormant account reactivation:** Lower noise, harder to detect without baselining. Attacker identifies a long-forgotten service or admin account, resets its password (EID 4724) and enables it (EID 4722). No 4720 is generated — the account already exists. This pattern is increasingly preferred in modern red team operations precisely because it avoids new-object creation alerts.

### Step 1: Full Account Modification Chain (Pattern A + Pattern B combined)

*Run EIDs 4720, 4722, 4724, 4728, and 4738 in a single pass — surface both patterns simultaneously. See [`6.06 §6.3`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#63-account-management-events-eid-4720-4722-4738-4741) for the full `rex` templates.*

```spl
index=* EventCode IN (4720, 4722, 4724, 4728, 4738)
    (Account_Name="<ACCOUNT>" OR SAM_Account_Name="<ACCOUNT>")
| rex "(?ms)Subject:\s+Security ID:\s+(?<Subject_SID>S-[0-9\-]+)\s+Account Name:\s+(?<Subject_Account_Name>.*?)\s+Account Domain:"
| rex "(?ms)(?:Target Account|New Account):\s+Security ID:\s+(?<Target_SID>S-[0-9\-]+)\s+Account Name:\s+(?<Target_Account_Name>.*?)\s+Account Domain:"
| eval Event_Type = case(
    EventCode=4720, "Account Created",
    EventCode=4722, "Account Enabled",
    EventCode=4724, "Password Reset (Admin)",
    EventCode=4728, "Added to Group",
    EventCode=4738, "Account Modified",
    true(), "Other"
)
| table _time, EventCode, Event_Type, Subject_Account_Name,
    Target_Account_Name, Target_SID, Logon_ID
| sort _time
```

> **Hunting Tip — Pattern A:** The 4720 → 4722 → 4728 → 4738 sequence with the same `Subject_Account_Name` within a short window is a definitive new-account backdoor. Use `Logon_ID` from these events to cross-reference with Phase 3 Step 1 — the session that created the account is the same session the attacker was operating from.

> **Hunting Tip — Pattern B:** A 4724 (admin password reset) followed by 4722 (account enabled) with no preceding 4720 is the dormant account reactivation signal. The absence of a 4720 is intentional on the attacker's part — they chose an existing account specifically to avoid new-object creation. Proceed to Step 2 to confirm the account was dormant before the reset.

### Step 2: Dormant Account Reactivation — Silence Period Verification

*Confirm the target account was inactive before the password reset. A `count` of zero or near-zero confirms dormancy — the reset reactivated a forgotten account rather than maintaining a legitimately active one.*

```spl
index=* EventCode=4624
    (Account_Name="<TARGET_ACCOUNT>" OR Target_Account_Name="<TARGET_ACCOUNT>")
    earliest=-90d latest="<RESET_TIMESTAMP>"
| stats count as Logons_Before_Reset
```

*If logons exist, check their frequency to distinguish occasional legitimate use from true dormancy:*

```spl
index=* EventCode=4624
    (Account_Name="<TARGET_ACCOUNT>" OR Target_Account_Name="<TARGET_ACCOUNT>")
    earliest=-90d latest="<RESET_TIMESTAMP>"
| timechart span=1w count
```

> **Hunting Tip:** Zero logons in 90 days followed by a password reset and immediate use is the clearest dormancy confirmation. Accounts with names containing `svc`, `service`, `admin`, `mgmt`, `backup`, or `scan` that show this pattern warrant immediate escalation — these are high-value targets precisely because they often carry elevated privileges accumulated over years without review. If the account has group memberships inconsistent with its apparent purpose (e.g. a `svc_backup` account in Domain Admins), that is a separate pre-existing misconfiguration that the attacker exploited.

### Step 3: Scope the Reactivated Account's Activity Window

*Once the reset timestamp is established, pull all logon and privilege events for the account after the reset — this is the attacker's operational window.*

```spl
index=* EventCode IN (4624, 4648, 4672)
    (Account_Name="<TARGET_ACCOUNT>" OR Target_Account_Name="<TARGET_ACCOUNT>")
    earliest="<RESET_TIMESTAMP>"
| rex field=Message "New Logon:[\s\S]*?Account Name:\s+(?<Target_Account>[^\s]+)"
| rex field=Message "Workstation Name:\s*(?<Workstation_Name>.*?)\s*Source Network Address:"
| eval Workstation_Name=if(trim(Workstation_Name)="", "N/A", Workstation_Name)
| table _time, EventCode, ComputerName, Target_Account, Logon_ID,
    Logon_Type, Workstation_Name, Source_Network_Address, Elevated_Token
| sort _time
```

### Step 4: Group Membership Changes — High-Value Groups

*See [`6.06 §6.4`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#64-group-membership-changes-eid-4728-4732-4756). Applies to both Pattern A (attacker adds new account to privileged groups) and Pattern B (attacker may further elevate the reactivated account if its existing memberships are insufficient).*

```spl
index=* EventCode IN (4728, 4732, 4756)
    (Account_Name="<ACCOUNT>" OR SAM_Account_Name="<ACCOUNT>"
     OR Message="*<ACCOUNT>*")
| rex "(?ms)Subject:\s+Security ID:\s+(?<Subject_SID>S-[0-9\-]+)\s+Account Name:\s+(?<Subject_Account_Name>.*?)\s+Account Domain:"
| search Message="*Domain Admins*" OR Message="*Enterprise Admins*"
    OR Message="*Schema Admins*" OR Message="*Backup Operators*"
    OR Message="*Account Operators*" OR Message="*Remote Desktop Users*"
| table _time, EventCode, Subject_Account_Name, Subject_SID, Logon_ID, Message
| sort _time
```

## Investigation QA (Self-Check)

- **[ ]** Have I confirmed the session origin IP for every anomalous `Logon_ID` via Phase 3 Step 1?
- **[ ]** Have I handed off `ProcessGuid` values from Phase 3 Step 2 to [`3.2.03`](3.2.03_Process_Execution_Investigation.md)?
- **[ ]** Have I checked `Logon_Type` for all successful logons — unexpected type on a sensitive account is itself a finding?
- **[ ]** Have I verified EID 4672 on every host where the account appeared, not just the primary host?
- **[ ]** Have I checked for **both** account backdoor patterns — new creation (4720 chain) **and** dormant account reactivation (4724 → 4722 without preceding 4720)?
- **[ ]** For any 4724 event where `Subject_Account_Name` ≠ `Target_Account_Name`, have I run the 90-day silence check in Phase 4 Step 2?
- **[ ]** If the account was created or reactivated during the incident window, have I traced the `Subject_Account_Name` back to its own logon session via Phase 3?
- **[ ]** Are all `Target_SID` values and origin IPs logged in `7.2_Evidence_Artifact_Log`?
