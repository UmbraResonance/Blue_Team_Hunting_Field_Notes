# Network & C2 Investigation

> **Focus:** Structured workflow for investigating a suspicious IP, domain, or outbound connection — from initial attribution to full C2 profile and lateral movement scope.

> **Environment:** Splunk · Sysmon · Windows Security Events · DNS Logs

> **Enter here when you have:** A suspicious destination IP, domain name, anomalous outbound connection, or a Sysmon EID 3 alert.

> **Pivot keys produced:** Beaconing `ProcessGuid`, lateral movement target hosts, C2 infrastructure profile — `ProcessGuid` feeds into [`3.2.03`](3.2.03_Process_Execution_Investigation.md); lateral movement hosts re-enter this workflow or [`3.2.02`](3.2.02_Identity_Investigation.md).

> **Note:** Replace `<IP>`, `<DOMAIN>`, `<GUID>`, `<HOST>`, and `<PORT>` with case-specific values. All timestamps UTC.

> **SPL Reference:** C2 beacon profiling → [`6.06 §7.1`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#71-c2-beacon-profiling-sysmon-eid-3) · Port sweep scoring → [`6.06 §7.2`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#72-port-sweep-behavioral-scoring-sysmon-eid-3) · Scope discovery → [`6.06 §7.5`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#75-investigation-scope-discovery)

## Phase 0: Scope

*Before profiling a specific connection, establish which hosts communicated with the target and what telemetry is available.*

### Step 1: IP / Domain Footprint Across the Environment

*Identify every host that contacted the target — this defines the lateral scope of the potential compromise.*

```spl
index=* ("<IP>" OR "<DOMAIN>")
| stats count by ComputerName, index, sourcetype, EventCode
| sort - count
```

### Step 2: First Contact Timestamp

*Establish the earliest observed communication — anchors the incident timeline and bounds the investigation window.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=3
    (DestinationIp="<IP>" OR DestinationHostname="*<DOMAIN>*")
| stats
    min(_time) as First_Contact,
    max(_time) as Last_Contact,
    dc(ComputerName) as Affected_Hosts,
    values(ComputerName) as Hosts
    by DestinationIp, DestinationHostname
| eval
    First_Contact=strftime(First_Contact, "%Y-%m-%d %H:%M:%S"),
    Last_Contact=strftime(Last_Contact, "%Y-%m-%d %H:%M:%S")
```

> **Hunting Tip:** `First_Contact` is the minimum bound for the compromise window — the actual initial access likely preceded it. Work backwards from this timestamp when reviewing Phase 1 authentication events in [`3.2.02`](3.2.02_Identity_Investigation.md) and Phase 0 Sysmon activity in [`3.2.03`](3.2.03_Process_Execution_Investigation.md).

## Phase 1: Connection Attribution

*Identify which process on which host is responsible for the suspicious connection, and recover the `ProcessGuid` for handoff to [`3.2.03`](3.2.03_Process_Execution_Investigation.md).*

### Step 1: Process Attribution (Sysmon EID 3)

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=3
    (DestinationIp="<IP>" OR DestinationHostname="*<DOMAIN>*")
| table _time, ComputerName, User, Image, ProcessId, ProcessGuid,
    SourceIp, SourcePort, DestinationIp, DestinationHostname,
    DestinationPort, Protocol, Initiated
| sort _time
```

### Step 2: Process Validation — Is the Connecting Process Expected?

*For each `Image` returned above, verify it is the expected process for that connection type.*

| Connecting Process | Connection Type | Assessment |
| :--- | :--- | :--- |
| Browser (`chrome.exe`, `firefox.exe`, `msedge.exe`) | HTTP/S on 80/443 | Expected |
| `svchost.exe` | Windows Update, telemetry | Expected — verify destination |
| `powershell.exe`, `cmd.exe` | Any external | High suspicion — check command line |
| `mshta.exe`, `wscript.exe`, `cscript.exe` | Any external | Definitive IOC |
| `rundll32.exe`, `regsvr32.exe` | Any external | Definitive IOC |
| `lsass.exe` | Any | Extremely anomalous — see [`6.06 §7.2`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#72-port-sweep-behavioral-scoring-sysmon-eid-3) |
| Any process | Non-standard port (not 80/443/53) | Investigate port purpose |

### Step 3: DNS Resolution Audit (Sysmon EID 22)

*Confirm which process resolved the suspicious domain and recover the resolved IP for correlation with EID 3 results.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=22
    (QueryName="*<DOMAIN>*" OR QueryResults="*<IP>*")
| table _time, ComputerName, User, Image, ProcessGuid,
    QueryName, QueryResults
| sort _time
```

> **Hunting Tip:** `QueryResults` contains the resolved IP — if the same domain resolves to multiple IPs across different hosts or time windows, the C2 infrastructure uses fast-flux DNS. Cross-reference each resolved IP independently through Phase 0 Step 1.

## Phase 2: C2 Beacon Profiling

*Characterise the connection pattern to determine whether it is automated beaconing, interactive C2, or data exfiltration. See [`6.06 §7.1`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#71-c2-beacon-profiling-sysmon-eid-3) for the full template and interpretation guide.*

### Step 1: Heartbeat Profile — Per ProcessGuid

*Compute connection frequency and average interval for the implant process.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=3
    ProcessGuid="<GUID>"
    DestinationIp="<IP>"
| stats
    min(_time) as First_Seen,
    max(_time) as Last_Seen,
    count as Total_Connections,
    dc(DestinationPort) as Unique_Ports,
    values(DestinationPort) as Ports,
    values(Protocol) as Protocols
    by ComputerName, Image, DestinationIp
| eval
    First_Seen=strftime(First_Seen, "%Y-%m-%d %H:%M:%S"),
    Last_Seen=strftime(Last_Seen, "%Y-%m-%d %H:%M:%S"),
    Duration_Seconds = strptime(Last_Seen, "%Y-%m-%d %H:%M:%S") - strptime(First_Seen, "%Y-%m-%d %H:%M:%S"),
    Avg_Heartbeat_Interval = round(Duration_Seconds / Total_Connections, 2)
| table ComputerName, Image, DestinationIp, Ports, Protocols,
    First_Seen, Last_Seen, Total_Connections, Avg_Heartbeat_Interval
```

### Step 2: Jitter Detection — Individual Interval Distribution

*A consistent `Avg_Heartbeat_Interval` masks jitter in individual connections. Export raw timestamps and compute deltas to confirm whether the beacon interval is fixed or randomised.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=3
    ProcessGuid="<GUID>" DestinationIp="<IP>"
| sort _time
| streamstats current=f last(_time) as Prev_Time
| eval Interval_Seconds = round(_time - Prev_Time, 2)
| where Interval_Seconds > 0
| stats
    avg(Interval_Seconds) as Avg_Interval,
    stdev(Interval_Seconds) as StdDev_Interval,
    min(Interval_Seconds) as Min_Interval,
    max(Interval_Seconds) as Max_Interval
    by ComputerName, Image, DestinationIp
```

> **Hunting Tip:** High `StdDev_Interval` relative to `Avg_Interval` (ratio > 0.3) indicates configured jitter — a deliberate evasion mechanism. This is a strong indicator of a commercial or mature C2 framework (Cobalt Strike, Sliver, Brute Ratel) rather than a simple reverse shell.

### Step 3: Data Volume Analysis — Exfiltration Signal

*Sysmon EID 3 does not capture byte counts. Use Windows Firewall or NetFlow logs if available. If not, use connection count asymmetry as a proxy — a high-frequency beacon with sudden spikes in connection count may correspond to data transfer bursts.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=3
    ProcessGuid="<GUID>" DestinationIp="<IP>"
| bin _time span=5m
| stats count as Connections_Per_5min by _time, ComputerName
| sort _time
```

## Phase 3: Internal Lateral Movement Detection

*Distinguish C2 traffic directed outbound from attacker-controlled tooling moving laterally between internal hosts.*

### Step 1: Internal-to-Internal Connection Anomalies

*Flag connections between workstations — direct workstation-to-workstation traffic is rare in most environments and is a primary lateral movement signal.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=3
    ComputerName="<SOURCE_HOST>"
    NOT DestinationIp IN ("127.0.0.1", "::1")
    NOT DestinationIsIpv6=true
    Initiated=true
| stats
    count as Connection_Count,
    dc(DestinationPort) as Unique_Ports,
    values(DestinationPort) as Ports,
    dc(DestinationIp) as Unique_Destinations
    by Image, DestinationIp
| where Unique_Destinations < 5 AND Unique_Ports > 5
| sort - Connection_Count
```

### Step 2: PsExec / SMB Lateral Movement (Sysmon EID 3 + Security EID 4624)

*PsExec uses SMB (port 445) to copy and execute a service binary on the target. Correlate EID 3 on port 445 from the source with EID 4624 Logon_Type=3 on the destination.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=3
    SourceIp="<ATTACKER_HOST_IP>"
    DestinationPort=445
    NOT DestinationIp IN ("127.0.0.1", "::1")
| table _time, ComputerName, Image, ProcessGuid,
    SourceIp, DestinationIp, DestinationPort
| sort _time
```

*Then on the destination host — confirm the network logon arrival:*

```spl
index=* EventCode=4624
    ComputerName="<TARGET_HOST>"
    Logon_Type=3
    Source_Network_Address="<ATTACKER_HOST_IP>"
    NOT Source_Network_Address IN ("::1", "127.0.0.1", "-")
| rex field=Message "New Logon:[\s\S]*?Account Name:\s+(?<Target_Account>[^\s]+)"
| rex field=Message "Workstation Name:\s*(?<Workstation_Name>.*?)\s*Source Network Address:"
| eval Workstation_Name=if(trim(Workstation_Name)="", "N/A", Workstation_Name)
| table _time, ComputerName, Target_Account, Logon_ID, Logon_Type,
    Workstation_Name, Source_Network_Address, Authentication_Package, Elevated_Token
| sort _time
```

> **Hunting Tip:** Extract `Logon_ID` from the destination EID 4624 result and hand it to [`3.2.02`](3.2.02_Identity_Investigation.md) Phase 3 for full session reconstruction on the target host. Extract `Target_Account` and hand it to [`3.2.02`](3.2.02_Identity_Investigation.md) Phase 1 to audit that account's broader authentication history.

### Step 3: WMI / DCOM Lateral Movement (EID 3 port 135 + EID 1)

*WMI and DCOM lateral movement initiates with a connection to port 135 (RPC endpoint mapper) followed by a dynamic high port.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=3
    DestinationPort=135
    Initiated=true
    NOT DestinationIp IN ("127.0.0.1", "::1")
    ComputerName="<SOURCE_HOST>"
| table _time, ComputerName, Image, ProcessGuid,
    SourceIp, DestinationIp, DestinationPort
| sort _time
```

*On the destination — WMI execution spawns `WmiPrvSE.exe` as the parent:*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=1
    ComputerName="<TARGET_HOST>"
    ParentImage="*\\WmiPrvSE.exe"
| table _time, ComputerName, User, LogonId,
    ParentImage, Image, ProcessGuid, CommandLine
| sort _time
```

## Phase 4: Port Sweep & Reconnaissance Detection

*Identify scanning activity originating from a compromised host. See [`6.06 §7.2`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#72-port-sweep-behavioral-scoring-sysmon-eid-3) for the full behavioral scoring template.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=3
    ComputerName="<COMPROMISED_HOST>"
    Initiated=true
    NOT DestinationIp IN ("127.0.0.1", "::1", "<KNOWN_INFRA>")
| stats
    dc(DestinationPort) as Unique_Ports_Targeted,
    count as Total_Connections,
    dc(DestinationIp) as Unique_Targets,
    values(DestinationIp) as Targets
    by Image, ProcessGuid
| eval Port_to_Connection_Ratio = round(Unique_Ports_Targeted / Total_Connections, 2)
| eval Behavioral_Assessment = case(
    Port_to_Connection_Ratio > 0.90 AND Unique_Targets > 3, "High Probability Network Sweep",
    Port_to_Connection_Ratio > 0.90, "High Probability Port Sweep — Single Target",
    Port_to_Connection_Ratio > 0.50, "Elevated — Investigate",
    true(), "Normal Traffic Pattern"
)
| table Image, ProcessGuid, Unique_Targets, Unique_Ports_Targeted,
    Total_Connections, Port_to_Connection_Ratio, Behavioral_Assessment
| sort - Unique_Ports_Targeted
```

## Investigation QA (Self-Check)

- **[ ]** Have I handed every beaconing `ProcessGuid` to [`3.2.03`](3.2.03_Process_Execution_Investigation.md) for full process investigation?
- **[ ]** Have I confirmed `First_Contact` timestamp and entered it into `7.1_Timeline_Tracker`?
- **[ ]** Have I checked DNS (EID 22) to recover the full resolution chain for any domain-based C2?
- **[ ]** Have I re-entered this workflow for each lateral movement target host identified in Phase 3?
- **[ ]** Have I handed lateral movement `Logon_ID` values to [`3.2.02`](3.2.02_Identity_Investigation.md) Phase 3?
- **[ ]** If jitter was detected (Phase 2 Step 2), have I noted the framework fingerprint in the evidence log?
- **[ ]** Have I checked whether the C2 IP resolves to a known cloud provider (AWS/Azure/GCP) — bulletproof hosting vs. legitimate cloud abuse changes the containment approach?
