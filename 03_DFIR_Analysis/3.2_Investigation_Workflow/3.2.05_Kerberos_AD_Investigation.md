# Kerberos & AD Investigation

> **Focus:** Structured workflow for investigating Kerberos abuse and Active Directory attacks — from ticket anomalies to replication rights abuse and delegation exploitation.

> **Environment:** Splunk · Windows Security Events (DC-sourced) · Sysmon

> **Enter here when you have:** A 4769 RC4 spike, a DCSync alert (EID 4662), anomalous replication traffic, an AS-REP roasting indicator, or a delegation misconfiguration finding.

> **Pivot keys produced:** Roasted account list, DCSync actor `Logon_ID`, compromised SID set — all feed into [`3.2.02`](3.2.02_Identity_Investigation.md) for session tracing.

> **Note:** Replace `<ACCOUNT>`, `<SID>`, `<LOGON_ID>`, `<HOST>`, `<DC_HOST>`, and `<IP>` with case-specific values. All timestamps UTC. All queries below are scoped to DC-sourced Security events unless stated otherwise.

> **SPL Reference:** EID 4769 extraction → [`6.06 §6.7`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#67-kerberos-service-ticket-requests-eid-4769) · DCSync (EID 4662) → [`6.06 §6.6`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#66-object-access--dcsync-eid-4662) · Logon event extraction → [`6.06 §6.1`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#61-logon-events-eid-4624-4625-4648--subject-and-new-logon-blocks)

## Prerequisite: DC Telemetry Verification

*All Kerberos and AD events are generated on Domain Controllers. Confirm DC logs are present and current before proceeding — missing DC telemetry invalidates the entire investigation.*

```spl
index=* ComputerName="<DC_HOST>"
    EventCode IN (4624, 4662, 4768, 4769, 4771, 4776)
| stats
    min(_time) as Earliest,
    max(_time) as Latest,
    count by EventCode
| eval
    Earliest=strftime(Earliest, "%Y-%m-%d %H:%M:%S"),
    Latest=strftime(Latest, "%Y-%m-%d %H:%M:%S")
| sort EventCode
```

> **If DC logs are absent:** Note the telemetry gap in `7.2_Evidence_Artifact_Log` before continuing. Absence of EID 4662 on a DC where DCSync is suspected is itself a finding — log forwarding may have been disabled by the attacker.

## Phase 1: Kerberoasting Detection

*Kerberoasting requests service tickets for accounts with SPNs using RC4 encryption (downgraded from AES), then cracks the tickets offline. EID 4769 is the primary detection surface.*

### Step 1: RC4 Encryption Spike — Full Dataset Stack

*Stack all service ticket requests by encryption type. RC4 (`0x17`) requests in a modern environment that defaults to AES are the primary signal. See [`6.06 §6.7`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#67-kerberos-service-ticket-requests-eid-4769).*

```spl
index=* EventCode=4769 ComputerName="<DC_HOST>"
| rex field=Message "Account Name:\s+(?<Requesting_Account>\S+)"
| rex field=Message "Service Name:\s+(?<Target_Service>\S+)"
| rex field=Message "Ticket Encryption Type:\s+(?<Encryption_Type>\S+)"
| rex field=Message "Client Address:\s+(?<Client_IP>\S+)"
| eval Client_IP=replace(Client_IP, "::ffff:", "")
| stats
    count as Request_Count,
    values(Target_Service) as Services_Requested,
    values(Requesting_Account) as Requestors,
    dc(Target_Service) as Unique_Services
    by Encryption_Type
| sort - Request_Count
```

**Encryption type reference — see [`6.06 §6.7`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#67-kerberos-service-ticket-requests-eid-4769) for full table.**

| Code | Assessment |
| :--- | :--- |
| `0x12` (AES-256) | Expected |
| `0x11` (AES-128) | Expected |
| `0x17` (RC4-HMAC) | **Kerberoasting indicator** |
| `0x1` (DES) | Legacy misconfiguration |

### Step 2: Targeted RC4 Request Detail

*For confirmed RC4 requests — recover the requesting account, source IP, and full list of targeted services.*

```spl
index=* EventCode=4769 ComputerName="<DC_HOST>"
    Ticket_Encryption_Type="0x17"
    NOT Service_Name="*$"
    NOT Service_Name="krbtgt"
| rex field=Message "Account Name:\s+(?<Requesting_Account>\S+)"
| rex field=Message "Service Name:\s+(?<Target_Service>\S+)"
| rex field=Message "Client Address:\s+(?<Client_IP>\S+)"
| eval Client_IP=replace(Client_IP, "::ffff:", "")
| table _time, ComputerName, Requesting_Account, Target_Service,
    Client_IP, Ticket_Encryption_Type
| sort _time
```

> **Hunting Tip:** Filter `NOT Service_Name="*$"` removes machine account tickets. Filter `NOT Service_Name="krbtgt"` removes TGT requests. What remains is exclusively SPN-targeted service tickets — the Kerberoasting target list. Hand `Requesting_Account` to [`3.2.02`](3.2.02_Identity_Investigation.md) Phase 1 to audit the account that issued the requests.

### Step 3: Burst Detection — Single Account Requesting Multiple SPNs

*An attacker roasting many accounts in a single session generates a burst of 4769 RC4 events within seconds. A legitimate user rarely requests more than one or two service tickets in a short window.*

```spl
index=* EventCode=4769 ComputerName="<DC_HOST>"
    Ticket_Encryption_Type="0x17"
    NOT Service_Name="*$"
| rex field=Message "Account Name:\s+(?<Requesting_Account>\S+)"
| rex field=Message "Service Name:\s+(?<Target_Service>\S+)"
| bin _time span=5m
| stats
    count as Requests_in_Window,
    dc(Target_Service) as Unique_Services,
    values(Target_Service) as Services
    by _time, Requesting_Account
| where Unique_Services > 3
| sort - Unique_Services
```

## Phase 2: AS-REP Roasting Detection

*AS-REP roasting targets accounts with Kerberos pre-authentication disabled (`DONT_REQ_PREAUTH`). The attacker requests an AS-REP without credentials and cracks the encrypted portion offline. EID 4768 with `Pre_Authentication_Type=0` is the signal.*

### Step 1: Pre-Auth Disabled Ticket Requests (EID 4768)

```spl
index=* EventCode=4768 ComputerName="<DC_HOST>"
    Pre_Authentication_Type=0
    NOT Account_Name="*$"
| rex field=Message "Account Name:\s+(?<Target_Account>\S+)"
| rex field=Message "Client Address:\s+(?<Client_IP>\S+)"
| eval Client_IP=replace(Client_IP, "::ffff:", "")
| rex field=Message "Ticket Encryption Type:\s+(?<Encryption_Type>\S+)"
| table _time, ComputerName, Target_Account, Client_IP, Encryption_Type
| sort _time
```

### Step 2: Accounts with Pre-Auth Disabled — AD Exposure Audit

*Enumerate all accounts where `DONT_REQ_PREAUTH` is set — these are permanently exposed to AS-REP roasting regardless of attacker activity.*

```spl
index=* EventCode=4738 ComputerName="<DC_HOST>"
| rex field=Message "Target Account:[\s\S]*?Account Name:\s+(?<Target_Account>\S+)"
| rex field=Message "User Account Control:[\s\S]*?(?<UAC_Change>Don't Require Preauth[^\r\n]*)"
| search UAC_Change=*
| table _time, ComputerName, Target_Account, UAC_Change
| sort _time
```

> **Hunting Tip:** EID 4738 fires when account attributes change — filtering for `Don't Require Preauth` changes surfaces both historical exposure and real-time attacker modification. An attacker who modifies this flag on an account before roasting it generates a detectable 4738 event that leaves a `Subject_Account_Name` audit trail. Hand the `Target_Account` to [`3.2.02`](3.2.02_Identity_Investigation.md) Phase 4 to check for other modifications.

## Phase 3: DCSync Detection

*DCSync abuses `DS-Replication-Get-Changes-All` — a legitimate AD replication right — to request password hashes directly from a DC via RPC, without touching lsass. EID 4662 on the DC is the primary detection surface. See [`6.06 §6.6`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#66-object-access--dcsync-eid-4662) for the full template and GUID reference.*

### Step 1: Replication Right Abuse (EID 4662)

```spl
index=* EventCode=4662 ComputerName="<DC_HOST>"
| rex field=Message "Subject:[\s\S]*?Security ID:\s*(?<Subject_Security_ID>[^\s]+)"
| rex field=Message "Subject:[\s\S]*?Logon ID:\s*(?<Extracted_Logon_ID>[^\s]+)"
| rex field=Message "Properties:\s*(?<Extracted_Properties>[\s\S]*?)(?=\s*Additional Information:|$)"
| search NOT Account_Name="*$"
| search Access_Mask=0x100
    AND (Extracted_Properties=*1131f6aa-9c07-11d1-f79f-00c04fc2dcd2*
      OR Extracted_Properties=*1131f6ad-9c07-11d1-f79f-00c04fc2dcd2*)
    AND Object_Type="%{19195a5b-6da0-11d0-afd3-00c04fd930c9}"
| table _time, ComputerName, EventCode, Account_Name, Subject_Security_ID,
    Extracted_Logon_ID, Object_Server, Object_Type
| sort _time
```

### Step 2: Session Origin Trace — Where Did the DCSync Come From?

*Extract `Extracted_Logon_ID` from Step 1 and pivot to the originating logon session. The `Source_Network_Address` reveals the machine that issued the replication request.*

```spl
index=* EventCode=4624 ComputerName="<DC_HOST>"
    (Logon_ID="<EXTRACTED_LOGON_ID>" OR Logon_ID="<EXTRACTED_LOGON_ID>")
| rex field=Message "Subject:[\s\S]*?Account Name:\s+(?<Subject_Account>[^\s]+)"
| rex field=Message "New Logon:[\s\S]*?Account Name:\s+(?<Target_Account>[^\s]+)"
| rex field=Message "Workstation Name:\s*(?<Workstation_Name>.*?)\s*Source Network Address:"
| eval Workstation_Name=if(trim(Workstation_Name)="", "N/A", Workstation_Name)
| table _time, ComputerName, Subject_Account, Target_Account, Logon_ID,
    Logon_Type, Workstation_Name, Source_Network_Address,
    Authentication_Package, Logon_Process, Elevated_Token
```

> **Hunting Tip:** `Source_Network_Address` from Step 2 is the machine that performed DCSync. If it is not a DC, it is an attacker-controlled host. Enter that host into [`3.2.03`](3.2.03_Process_Execution_Investigation.md) to identify the process that issued the replication call. Hand `Target_Account` to [`3.2.02`](3.2.02_Identity_Investigation.md) to audit the compromised account used to perform DCSync.

### Step 3: Sysmon Corroboration — Replication RPC on the Attacking Host

*DCSync issues DRSUAPI RPC calls over dynamic high ports. On the source host, Sysmon EID 3 will show the process connecting to the DC on port 135 followed by a high port. This corroborates the EID 4662 finding with endpoint telemetry.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=3
    ComputerName="<ATTACKER_HOST>"
    DestinationIp="<DC_IP>"
    DestinationPort IN ("135", "445", "49152", "49153", "49154", "49155")
| table _time, ComputerName, Image, ProcessGuid,
    SourceIp, DestinationIp, DestinationPort
| sort _time
```

## Phase 4: Pass-the-Ticket / Golden Ticket Detection

*Forged or stolen Kerberos tickets are characterised by anomalous field values in 4768/4769 events — particularly impossible encryption combinations and source anomalies.*

### Step 1: Encryption Downgrade on TGT Request (EID 4768)

*A TGT requested with RC4 encryption from a host that should use AES indicates either a legacy system or a Pass-the-Hash/Pass-the-Ticket attack.*

```spl
index=* EventCode=4768 ComputerName="<DC_HOST>"
    Ticket_Encryption_Type="0x17"
    Result_Code="0x0"
    NOT Account_Name="*$"
| rex field=Message "Account Name:\s+(?<Target_Account>\S+)"
| rex field=Message "Client Address:\s+(?<Client_IP>\S+)"
| eval Client_IP=replace(Client_IP, "::ffff:", "")
| table _time, ComputerName, Target_Account, Client_IP,
    Ticket_Encryption_Type, Pre_Authentication_Type
| sort _time
```

### Step 2: Service Ticket Without Prior TGT (Overpass-the-Hash Signal)

*A 4769 event with no preceding 4768 from the same source within the expected TGT lifetime (typically 10 hours) suggests the attacker is using a forged or injected TGT rather than obtaining one legitimately.*

```spl
index=* EventCode IN (4768, 4769) ComputerName="<DC_HOST>"
| rex field=Message "Account Name:\s+(?<Account>\S+)"
| rex field=Message "Client Address:\s+(?<Client_IP>\S+)"
| eval Client_IP=replace(Client_IP, "::ffff:", "")
| eval Event_Type=if(EventCode=4768, "TGT_Request", "Service_Ticket_Request")
| stats
    values(Event_Type) as Events_Seen,
    min(_time) as First_Event
    by Account, Client_IP
| where !match(Events_Seen, "TGT_Request")
| eval First_Event=strftime(First_Event, "%Y-%m-%d %H:%M:%S")
| table Account, Client_IP, Events_Seen, First_Event
```

> **Hunting Tip:** Accounts appearing in 4769 without a 4768 from the same source are operating with a ticket that was not issued through the normal authentication flow for that source IP. This is the primary detection pattern for Overpass-the-Hash and Golden Ticket usage. Cross-reference `Account` against known compromised accounts from [`3.2.02`](3.2.02_Identity_Investigation.md).

### Step 3: Anomalous Ticket Lifetime or Source

*Golden Tickets can be forged with arbitrary lifetimes (attackers sometimes set 10 years). EID 4769 does not expose ticket lifetime directly, but the combination of an unusual source host and a non-DC-issued ticket field can surface forgeries.*

```spl
index=* EventCode=4769 ComputerName="<DC_HOST>"
    NOT Service_Name="*$"
    NOT Service_Name="krbtgt"
| rex field=Message "Account Name:\s+(?<Requesting_Account>\S+)"
| rex field=Message "Client Address:\s+(?<Client_IP>\S+)"
| eval Client_IP=replace(Client_IP, "::ffff:", "")
| stats
    dc(Client_IP) as Source_IPs,
    values(Client_IP) as Sources,
    dc(Service_Name) as Services_Accessed,
    min(_time) as First_Seen
    by Requesting_Account
| where Source_IPs > 3
| eval First_Seen=strftime(First_Seen, "%Y-%m-%d %H:%M:%S")
| sort - Source_IPs
```

> **Hunting Tip:** A single account generating service ticket requests from many different source IPs simultaneously indicates a Golden Ticket being used across multiple hosts — the ticket was distributed to multiple attacker-controlled systems. An account appearing from more than 3 distinct source IPs within a short window warrants immediate investigation.

## Phase 5: Delegation Abuse Detection

*Kerberos delegation misconfigurations allow a service account to impersonate any user to any service (Unconstrained) or a specific set of services (Constrained). Both can be abused for privilege escalation.*

### Step 1: Unconstrained Delegation — TGT Coercion Signal (EID 4769)

*Unconstrained delegation causes any user authenticating to the delegating service to have their full TGT forwarded to it. Attackers coerce DC machine accounts to authenticate (e.g. via PrinterBug/PetitPotam) and capture TGTs.*

```spl
index=* EventCode=4769 ComputerName="<DC_HOST>"
    Service_Name="<UNCONSTRAINED_DELEGATION_HOST>$"
    Ticket_Options="0x60810010"
| rex field=Message "Account Name:\s+(?<Requesting_Account>\S+)"
| rex field=Message "Client Address:\s+(?<Client_IP>\S+)"
| eval Client_IP=replace(Client_IP, "::ffff:", "")
| table _time, Requesting_Account, Service_Name, Client_IP, Ticket_Options
| sort _time
```

> **Hunting Tip:** `Ticket_Options=0x60810010` indicates a forwardable TGT was requested — the precondition for unconstrained delegation abuse. DC machine accounts (`DCNAME$`) authenticating to a non-DC service with a forwardable ticket is the coercion success signal.

### Step 2: Resource-Based Constrained Delegation (RBCD) — msDS-AllowedToActOnBehalfOfOtherIdentity Modification

*RBCD attacks write the attacker-controlled account's SID into `msDS-AllowedToActOnBehalfOfOtherIdentity` on the target computer object. EID 5136 fires on directory service object modification.*

```spl
index=* EventCode=5136 ComputerName="<DC_HOST>"
    AttributeLDAPDisplayName="msDS-AllowedToActOnBehalfOfOtherIdentity"
| rex field=Message "Subject:[\s\S]*?Account Name:\s+(?<Subject_Account>[^\s]+)"
| rex field=Message "Object:[\s\S]*?Object DN:\s*(?<Object_DN>[^\r\n]+)"
| table _time, ComputerName, Subject_Account, Object_DN, AttributeLDAPDisplayName,
    AttributeValue, OperationType
| sort _time
```

> **Hunting Tip:** `Object_DN` identifies which computer object was modified — this is the target of the RBCD attack. `Subject_Account` is the account that made the modification. Hand both to [`3.2.02`](3.2.02_Identity_Investigation.md) — `Subject_Account` for session tracing, `Object_DN` for follow-on S4U2Proxy ticket requests in EID 4769.

## Phase 6: NTLM Relay & Credential Exposure

### Step 1: NTLM Authentication Audit (EID 4776)

*EID 4776 fires for every NTLM credential validation attempt on the authenticating DC. Failures from unexpected sources indicate relay or spray activity.*

```spl
index=* EventCode=4776 ComputerName="<DC_HOST>"
    Error_Code!=0x0
| rex field=Message "Logon Account:\s+(?<Logon_Account>\S+)"
| rex field=Message "Source Workstation:\s+(?<Source_Workstation>\S+)"
| stats
    count as Failures,
    dc(Logon_Account) as Unique_Accounts,
    values(Logon_Account) as Accounts,
    dc(Source_Workstation) as Unique_Sources
    by Error_Code, Source_Workstation
| sort - Failures
```

**Error Code reference:**

| Code | Meaning | Implication |
| :--- | :--- | :--- |
| `0xC000006A` | Wrong password | Spray or brute force |
| `0xC0000064` | No such user | Username enumeration |
| `0xC000006D` | Generic auth failure | Relay attempt with wrong hash |
| `0xC000015B` | Logon type not granted | Account restricted from network logon |

### Step 2: NTLM Relay Success Indicator

*A successful NTLM authentication (EID 4776 `Error_Code=0x0`) from an unexpected source workstation — particularly one that is not the account's normal host — indicates a successful relay.*

```spl
index=* EventCode=4776 ComputerName="<DC_HOST>"
    Error_Code=0x0
| rex field=Message "Logon Account:\s+(?<Logon_Account>\S+)"
| rex field=Message "Source Workstation:\s+(?<Source_Workstation>\S+)"
| search NOT Logon_Account="*$"
| table _time, ComputerName, Logon_Account, Source_Workstation
| sort _time
```

## Investigation QA (Self-Check)

- **[ ]** Have I confirmed DC log availability and currency in the Prerequisite step before drawing any conclusions?
- **[ ]** For any Kerberoasting finding — have I identified the `Requesting_Account` and handed it to [`3.2.02`](3.2.02_Identity_Investigation.md) to trace the originating session?
- **[ ]** For DCSync — have I traced `Extracted_Logon_ID` to a source IP and entered that host into [`3.2.03`](3.2.03_Process_Execution_Investigation.md)?
- **[ ]** Have I checked both EID 4768 and EID 4769 for the same account to detect Overpass-the-Hash in Phase 4 Step 2?
- **[ ]** For AS-REP roasting findings — have I checked EID 4738 to determine whether `DONT_REQ_PREAUTH` was recently modified by an attacker?
- **[ ]** Have I logged the full set of targeted SPNs and roasted accounts in `7.2_Evidence_Artifact_Log`?
- **[ ]** If RBCD abuse is confirmed via EID 5136, have I checked for subsequent S4U2Proxy 4769 requests from the attacker-controlled account?
