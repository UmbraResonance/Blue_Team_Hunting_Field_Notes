# Process Execution Investigation

> **Focus:** Structured workflow for investigating a suspicious process — from parent chain validation to full execution timeline reconstruction.

> **Environment:** Splunk · Sysmon · Windows Security Events

> **Enter here when you have:** A suspicious process name, executable path, `ProcessGuid`, or an EDR/Sysmon alert on process creation.

> **Pivot keys produced:** `ProcessGuid`, `LogonId`, child process chain — consumed by [`3.2.04`](3.2.04_Network_C2_Investigation.md). `LogonId` feeds back into [`3.2.02`](3.2.02_Identity_Investigation.md) to identify the originating session.

> **Note:** Replace `<PROCESS>`, `<PATH>`, `<GUID>`, `<HOST>`, and `<LOGON_ID>` with case-specific values. All timestamps UTC.

> **SPL Reference:** Multi-EventCode activity labeling → [`6.06 §7.4`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#74-multi-eventcode-activity-labeling-sysmon-eid-1--11--13) · Session pivot → [`6.06 §7.3`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#73-cross-sourcetype-session-pivot-logonid--logon_id) · Scope discovery → [`6.06 §7.5`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#75-investigation-scope-discovery)

## Phase 0: Scope

*Establish what telemetry exists for the target process before committing to a query path.*

### Step 1: Process Presence Across Sources

```spl
index=* ("<PROCESS>" OR "<PATH>")
| stats count by ComputerName, index, sourcetype, EventCode
| sort - count
```

### Step 2: First and Last Seen

*Bound the investigation window before querying individual events.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=1
    (Image="*<PROCESS>*" OR CommandLine="*<PATH>*")
| stats
    min(_time) as First_Execution,
    max(_time) as Last_Execution,
    count as Total_Executions,
    dc(ComputerName) as Unique_Hosts,
    values(ComputerName) as Hosts
    by Image
| eval
    First_Execution=strftime(First_Execution, "%Y-%m-%d %H:%M:%S"),
    Last_Execution=strftime(Last_Execution, "%Y-%m-%d %H:%M:%S")
```

> **Hunting Tip:** A process that executed on many hosts within a short window indicates automated deployment — lateral movement tooling or a worm. A process that executed exactly once on a single host and never again is equally suspicious — one-off execution is the profile of a staged payload.

## Phase 1: Parent Chain Validation

*Legitimate system processes have fixed, known parent chains. Deviation from the expected parent is the highest-confidence process-level IOC.*

### Step 1: Process Creation Context (EID 1)

*Capture the full creation context: parent, command line, hash, and logon session.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=1
    (Image="*<PROCESS>*" OR CommandLine="*<PATH>*")
    ComputerName="<HOST>"
| table _time, ComputerName, User, LogonId,
    ParentImage, ParentProcessGuid, ParentCommandLine,
    Image, ProcessGuid, CommandLine, Hashes,
    CurrentDirectory, IntegrityLevel
| sort _time
```

### Step 2: Parent Chain Anomaly Reference

> **Reference:** For the complete expected parent chain map, see [`1.2_Windows_Process_Genealogy`](../../01_Hunting_Cheatsheets/1.2_Windows_Process_Genealogy.csv). Any `ParentImage` value not listed as expected for the target process in that table is a finding — escalate immediately without waiting for further corroboration.

### Step 3: Process Tree — Children of the Suspicious Process

*Enumerate everything the target process spawned. A legitimate process should have a predictable, bounded set of children.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=1
    ParentProcessGuid="<GUID>"
| table _time, ComputerName, User, LogonId,
    ParentImage, ParentProcessGuid,
    Image, ProcessGuid, CommandLine, Hashes
| sort _time
```

*Recursive — pull grandchildren using GUIDs from the above result:*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=1
    ParentProcessGuid IN ("<CHILD_GUID_1>", "<CHILD_GUID_2>")
| table _time, ComputerName, User, ParentImage, ParentProcessGuid,
    Image, ProcessGuid, CommandLine
| sort _time
```

## Phase 2: Execution Timeline

*Reconstruct everything the process did after spawning: files written, registry keys modified, and further process creations. See [`6.06 §7.4`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#74-multi-eventcode-activity-labeling-sysmon-eid-1--11--13) for the full labeling template.*

### Step 1: Unified Activity Timeline (EID 1 / 11 / 13)

```spl
index=* sourcetype="wineventlog:sysmon"
    EventCode IN (1, 11, 13)
    ProcessGuid="<GUID>"
| eval Action_Details = case(
    EventCode==1,  "Process Created: "    . Image          . " | CMD: "   . CommandLine,
    EventCode==11, "File Created: "       . TargetFilename . " | By: "    . Image,
    EventCode==13, "Registry Modified: " . TargetObject   . " | Value: " . Details,
    true(), "Other: EventCode=" . tostring(EventCode)
)
| table _time, EventCode, ParentImage, ProcessGuid, Action_Details
| sort _time
```

### Step 2: File Drops — Suspicious Paths

*Scope file creation events to high-risk directories. Files written to these paths warrant immediate hash collection and VirusTotal pivot.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=11
    ProcessGuid="<GUID>"
    (TargetFilename="*\\Temp\\*"
     OR TargetFilename="*\\AppData\\*"
     OR TargetFilename="*\\ProgramData\\*"
     OR TargetFilename="*\\Windows\\Temp\\*"
     OR TargetFilename="*\\Users\\Public\\*")
| table _time, ComputerName, Image, ProcessGuid, TargetFilename
| sort _time
```

### Step 3: Registry Persistence Keys

*Scope registry modifications to known persistence locations.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=13
    ProcessGuid="<GUID>"
    (TargetObject="*\\CurrentVersion\\Run*"
     OR TargetObject="*\\CurrentVersion\\RunOnce*"
     OR TargetObject="*Winlogon*"
     OR TargetObject="*Image File Execution Options*"
     OR TargetObject="*AppInit_DLLs*"
     OR TargetObject="*\\Services\\*")
| table _time, ComputerName, Image, ProcessGuid, TargetObject, Details
| sort _time
```

### Step 4: DLL Loading (EID 7)

*Identify suspicious modules loaded by the process — unsigned DLLs, DLLs loaded from non-standard paths, or known injection DLL names.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=7
    ProcessGuid="<GUID>"
    (NOT Signed=true OR ImageLoaded="*\\Temp\\*" OR ImageLoaded="*\\AppData\\*")
| table _time, ComputerName, Image, ProcessGuid,
    ImageLoaded, Signed, Signature, SignatureStatus
| sort _time
```

## Phase 3: LOLBin Detection

*Living-off-the-Land Binaries are signed Microsoft tools abused by attackers to blend into normal activity. Filter out known-good invocations (Splunk UF, management tooling) before escalating.*

### Step 1: LOLBin Execution Sweep — Host Scoped

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=1
    ComputerName="<HOST>"
    (Image="*\\powershell.exe"
     OR Image="*\\cmd.exe"
     OR Image="*\\wscript.exe"
     OR Image="*\\cscript.exe"
     OR Image="*\\mshta.exe"
     OR Image="*\\rundll32.exe"
     OR Image="*\\regsvr32.exe"
     OR Image="*\\certutil.exe"
     OR Image="*\\bitsadmin.exe"
     OR Image="*\\msiexec.exe"
     OR Image="*\\wmic.exe")
    NOT Image="*\\SplunkUniversalForwarder\\*"
| table _time, ComputerName, User, LogonId, ParentImage,
    Image, ProcessGuid, CommandLine
| sort _time
```

### Step 2: High-Risk Command Patterns

*Scope to command lines that contain known abuse signatures — encoding, download cradles, and remote execution flags.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=1
    ComputerName="<HOST>"
    (CommandLine="*-enc*" OR CommandLine="*-EncodedCommand*"
     OR CommandLine="*IEX*" OR CommandLine="*Invoke-Expression*"
     OR CommandLine="*DownloadString*" OR CommandLine="*WebClient*"
     OR CommandLine="*FromBase64String*"
     OR CommandLine="*bypass*" OR CommandLine="*-nop*"
     OR CommandLine="*regsvr32*scrobj*"
     OR CommandLine="*certutil*decode*"
     OR CommandLine="*bitsadmin*transfer*")
| table _time, ComputerName, User, LogonId, ParentImage,
    Image, ProcessGuid, CommandLine
| sort _time
```

> **Hunting Tip:** `-enc` and `-EncodedCommand` are only meaningful in `powershell.exe` context. `certutil -decode` and `bitsadmin /transfer` in any context are download-cradle signals. `regsvr32 /s /n /u /i:<URL> scrobj.dll` is Squiblydoo — a signed-binary proxy execution technique that bypasses AppLocker.

## Phase 4: Injection Detection

*Identify whether the process injected into or was injected by another process.*

### Step 1: Outbound Injection (EID 8 — CreateRemoteThread)

*Target process created a thread in another process.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=8
    SourceProcessGuid="<GUID>"
| table _time, ComputerName, SourceImage, SourceProcessGuid,
    TargetImage, TargetProcessId, TargetProcessGuid,
    StartAddress, StartFunction, StartModule
| sort _time
```

### Step 2: Inbound Injection — Target Process Receiving Threads

*Another process injected into the target. Particularly relevant when investigating `svchost.exe`, `explorer.exe`, or `lsass.exe` alerts.*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=8
    TargetProcessGuid="<GUID>"
| table _time, ComputerName, SourceImage, SourceProcessGuid,
    SourceProcessId, TargetImage, TargetProcessGuid,
    StartFunction, StartModule
| sort _time
```

> **Hunting Tip:** `StartModule` pointing to a path in `\Temp\`, `\AppData\`, or `\ProgramData\` rather than a system path confirms the injected code is not a legitimate DLL. `StartFunction=LoadLibraryA` indicates reflective DLL injection. Feed `SourceProcessGuid` back into Phase 1 of this workflow to investigate the injector.

### Step 3: Process Access (EID 10)

*The target process was opened by another process with access rights consistent with memory reading or injection (`GrantedAccess` values of `0x1010`, `0x1F3FFF`, `0x1FFFFF`).*

```spl
index=* sourcetype="wineventlog:sysmon" EventCode=10
    TargetProcessGuid="<GUID>"
    GrantedAccess IN ("0x1010", "0x1F3FFF", "0x1FFFFF", "0x143A")
| table _time, ComputerName, SourceImage, SourceProcessGuid,
    TargetImage, TargetProcessGuid, GrantedAccess, CallTrace
| sort _time
```

## Phase 5: Session Attribution

*Identify the logon session that spawned the process, then pivot to [`3.2.02`](3.2.02_Identity_Investigation.md) to trace the session back to its network origin and account context.*

### Step 1: Recover LogonId from Process Event

*Already captured in Phase 1 Step 1 — extract the `LogonId` value from that result.*

### Step 2: Cross-Sourcetype Pivot to Security Logon Event

*See [`6.06 §7.3`](../../06_Tool_Command_Vault/6.06_Splunk_SPL_Syntaxes.md#73-cross-sourcetype-session-pivot-logonid--logon_id) for the field name gotcha (`LogonId` vs `Logon_ID`).*

```spl
index=* (LogonId="<LOGON_ID>" OR Logon_ID="<LOGON_ID>") EventCode=4624
| rex field=Message "Subject:[\s\S]*?Account Name:\s+(?<Subject_Account>[^\s]+)"
| rex field=Message "New Logon:[\s\S]*?Account Name:\s+(?<Target_Account>[^\s]+)"
| rex field=Message "Workstation Name:\s*(?<Workstation_Name>.*?)\s*Source Network Address:"
| eval Workstation_Name=if(trim(Workstation_Name)="", "N/A", Workstation_Name)
| table _time, ComputerName, Subject_Account, Target_Account, Logon_ID,
    Logon_Type, Workstation_Name, Source_Network_Address,
    Authentication_Package, Logon_Process, Elevated_Token
```

> **Hunting Tip:** `Source_Network_Address` from this query is the true network origin of the session that spawned the suspicious process. Hand `Target_Account` and `Logon_ID` to [`3.2.02`](3.2.02_Identity_Investigation.md) Phase 1 to audit the full authentication history of that account.

## Investigation QA (Self-Check)

- **[ ]** Have I cross-referenced `ParentImage` against [`1.2_Windows_Process_Genealogy`](../../01_Hunting_Cheatsheets/1.2_Windows_Process_Genealogy.csv) for every process in the chain?
- **[ ]** Have I checked both outbound (EID 8 source) and inbound (EID 8 target) injection for this `ProcessGuid`?
- **[ ]** Have I handed `ProcessGuid` values for all child processes to [`3.2.04`](3.2.04_Network_C2_Investigation.md) for C2 profiling?
- **[ ]** Have I handed `LogonId` to [`3.2.02`](3.2.02_Identity_Investigation.md) to trace the originating session?
- **[ ]** Are all file drops from Phase 2 Step 2 hashed and logged in `7.2_Evidence_Artifact_Log`?
- **[ ]** Have I checked `IntegrityLevel` from Phase 1 Step 1 — a standard user process running at `High` or `System` indicates privilege escalation?
