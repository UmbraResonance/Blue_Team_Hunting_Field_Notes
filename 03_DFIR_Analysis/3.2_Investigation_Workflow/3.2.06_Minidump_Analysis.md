# Minidump Analysis (dumpex)

> **Focus:** Structured workflow for process-level `.DMP` file analysis — from initial triage to TTP detection, IOC extraction, and pivot back to log-based investigation.

> **Environment:** Windows / Linux · Python 3.10+ · [dumpex](https://github.com/bitbug0x55AA/dumpex)

> **Engine:** dumpex (`python -m dumpex`)

> **Enter here when you have:** A process `.DMP` file from EDR capture, Windows Error Reporting (WER), a crash dump, or a suspected attacker-generated dump via `MiniDumpWriteDump`.

> **Pivot keys produced:** Injected PE hashes, C2 host/IP/User-Agent from beacon config, named pipe names, IOC strings — all feed into [`3.2.04`](3.2.04_Network_C2_Investigation.md) for C2 profiling and [`3.2.03`](3.2.03_Process_Execution_Investigation.md) for process chain correlation.

> **Note:** Replace `<DUMP>` with your `.DMP` file path. Add `--verbose` to any hunt command to expand addresses and region details. Add `--json results.json` to any command to capture structured output for reporting.

---

## Tool Positioning

This workflow covers **process-level minidumps** — a distinct artifact class from full RAM images.

| Capability | Volatility 3 | MemProcFS | dumpex |
|---|---|---|---|
| Full RAM image analysis | ✅ | ✅ | — |
| Cross-process visibility | ✅ | ✅ | — |
| **Process .DMP triage (no full image)** | ❌ | ❌ | ✅ |
| **CS Beacon config extraction** | Manual | Manual | ✅ Automated |
| **Sleep Mask XOR key recovery** | ❌ | ❌ | ✅ |
| **Pre/post dump memory diff** | ❌ | ❌ | ✅ `--diff` |
| **Address-anchored alert triage** | Partial | Partial | ✅ `--report` |
| Kernel / rootkit analysis | ✅ | ✅ | — |
| Execution artifacts (Prefetch, Amcache) | ❌ | ✅ | — |

**When to use this workflow instead of `3.2.01`:**

- A full RAM image is not available, but a `.DMP` exists
- The alert is process-scoped (EDR flagged a specific PID, not the whole system)
- You need to confirm injection or C2 config at the memory level to corroborate a Sysmon or network finding
- Two dumps of the same process are available and you need to diff them (e.g. before/after EDR quarantine)

## Phase 0: Dump Triage

*Verify the dump is readable and establish basic process context before running detection.*

### Step 1: System and Process Identity

```bash
# OS, host, username, PID, command line
python -m dumpex <DUMP> --sysinfo

# Process ID only (quick check)
python -m dumpex <DUMP> --pid
```

Key fields to record:
- `Hostname` and `Username` — confirm this matches the alerted endpoint
- `Image Path` and `Command Line` — validate against Sysmon EID 1 from [`3.2.03`](3.2.03_Process_Execution_Investigation.md)
- `Process Start (UTC)` — anchor to the investigation timeline

### Step 2: PEB Integrity Check

```bash
python -m dumpex <DUMP> --peb
```

> **Hunting Tip:** `BeingDebugged=True` in a production process is anomalous — it indicates the process was running under a debugger or a tool that set this flag deliberately. Some malware sets this to interfere with analysis. Compare `ImagePath` against `CommandLine` — a mismatch mirrors the `PEB_MASQ` signal in MemProcFS FindEvil and is a direct process hollowing indicator.

### Step 3: Module Inventory

```bash
python -m dumpex <DUMP> --modules
```

Flags to escalate immediately:
- `[NO NAME]` — a loaded module with no path; consistent with reflective injection
- `[OLD TIMESTAMP]` — PE compiled before 1980; common in hand-crafted shellcode loaders
- Any module path resolving to `\Temp\`, `\AppData\`, `\ProgramData\`, or `\Users\Public\`

## Phase 1: Memory Layout

*Establish the memory map before running detection — understanding region distribution reduces false positive interpretation later.*

### Step 1: Full Region Map

```bash
python -m dumpex <DUMP> --list
```

### Step 2: Filter by Suspicious Protection

```bash
# RWX regions only
python -m dumpex <DUMP> --list --filter PAGE_EXECUTE_READWRITE

# All executable regions
python -m dumpex <DUMP> --list --filter PAGE_EXECUTE
```

> **Hunting Tip:** In a clean process, `PAGE_EXECUTE_READWRITE` regions should not exist. Legitimate JIT engines (browsers, .NET CLR) use `PAGE_EXECUTE_READ` after the write phase completes. A persistent `PAGE_EXECUTE_READWRITE` region backed by `MEM_PRIVATE` with no module owner is the classic shellcode staging signature.

### Step 3: Thread Inventory

```bash
python -m dumpex <DUMP> --threads
```

Key signals:
- `⚠ NOT IN ANY MODULE` — thread start address falls outside all loaded modules; direct injection indicator
- `[EXITED]` threads with non-zero `ExitStatus` — may indicate a staging thread that completed payload delivery
- `[DUMPER]` — the thread that triggered the dump; note its start address for corroboration with Sysmon EID 8

## Phase 2: TTP Detection

*Run the detection engine. Start with `--hunt all` for a summary, then drill into flagged categories.*

### Step 1: Full TTP Sweep

```bash
python -m dumpex <DUMP> --hunt all --verbose
```

The summary card scores each TTP category independently. A non-zero score on any category is the entry point for the corresponding phase below.

```
  Process Injection         HIGH CONFIDENCE  (3/3)
  Process Hollowing         CLEAN            (0/4)
  Module Stomping           POSSIBLE         (1/2)
  Named Pipe C2 / Lat. Move HIGH CONFIDENCE  (3/4)
  Cobalt Strike Beacon      BEACON CONFIG FOUND (1 config)
  YARA Rules                RULES MATCHED: CS_Beacon_Config_XOR69
  Obfuscation Detection     LIKELY           (2/6)
```

### Step 2: Process Injection

```bash
python -m dumpex <DUMP> --hunt injection --verbose
```

Three independent signals — each scored separately:

| Signal | Implication |
|---|---|
| RWX memory regions | Staging area for shellcode or reflective PE |
| Hidden PE headers (MZ not in module list) | Injected PE resident in memory but not registered |
| Unbacked threads | Active execution from injected code |

> **Pivot:** If hidden PE is confirmed, extract it for static analysis — see Phase 3 Step 2. If unbacked threads are found, note the thread start address and correlate with Sysmon EID 8 (`CreateRemoteThread`) in [`3.2.03`](3.2.03_Process_Execution_Investigation.md) Phase 4.

### Step 3: Process Hollowing

```bash
python -m dumpex <DUMP> --hunt hollowing
```

Checks image base memory type (`MEM_PRIVATE` instead of `MEM_IMAGE`), MZ header integrity, RWX at image base, and PEB name vs module list consistency.

> **Pivot:** A hollowing finding here directly corroborates Volatility `hollowprocess` output from [`3.2.01`](3.2.01_Memory_Forensics.md) Phase 7 if a full RAM image is also available. Use both to triangulate.

### Step 4: Named Pipe C2

```bash
python -m dumpex <DUMP> --hunt pipe --verbose
```

Detects pipe names in non-system memory, C2 artifacts (IP/URL) co-located with pipe names, known framework patterns (Cobalt Strike, Metasploit, PsExec, PrintNightmare), and unbacked threads in the same region.

> **Pivot:** Any pipe name found here feeds directly into [`3.2.04`](3.2.04_Network_C2_Investigation.md) — search for it in Sysmon EID 17/18 (pipe create/connect) logs to identify which host connected to this pipe and when.

### Step 5: Cobalt Strike Beacon

```bash
python -m dumpex <DUMP> --hunt cs-beacon --verbose
```

Extracts the full beacon configuration if present: C2 host, port, URI, User-Agent, pipe name, License ID, sleep/jitter, SpawnTo, Malleable C2 profile, process injection settings.

> **Pivot:** The C2 host extracted here is the definitive network IOC. Enter it into [`3.2.04`](3.2.04_Network_C2_Investigation.md) Phase 0 Step 1 to scope which other hosts in the environment communicated with it. The User-Agent string feeds into the HTTP/Web Audit in the [Network Forensics Playbook](../3.1_Playbooks/3.1.02_Network_Analysis_Playbook.md) Phase 2 Step 1.

### Step 6: Obfuscation Detection

```bash
python -m dumpex <DUMP> --hunt obfuscation --verbose
```

Five detection layers in sequence:

| Layer | What It Finds |
|---|---|
| 0 — CS Sleep Mask | Beacon memory XOR-encoded before sleeping; recovers key via frequency analysis |
| 1 — Shannon Entropy | High-entropy private regions (encrypted/packed payloads) |
| 2 — Base64 | Standard and URL-safe encoded blobs with decoded content classification |
| 3 — XOR single-byte | Brute-forces single-byte XOR keys; validates by IOC string presence in decoded output |
| 4 — GZIP/ZLIB | Magic byte scan + decompress attempt |

## Phase 3: IOC Extraction

*Extract actionable indicators from flagged regions for reporting and threat intelligence pivot.*

### Step 1: Alert Triage — Anchor to a Known IOC

If the investigation started from a specific indicator (EDR alert address, Sysmon TID, or a known string from threat intel):

```bash
# Anchor to a memory address from an EDR alert
python -m dumpex <DUMP> --report --report-addr 0x<ADDR>

# Anchor to a thread ID from Sysmon EID 1
python -m dumpex <DUMP> --report --report-tid 0x<TID>

# Search all memory for a known C2 IP or domain
python -m dumpex <DUMP> --report --report-string "192.168.1.1"
python -m dumpex <DUMP> --report --report-string "evil.domain.com"
```

The triage report produces a MECE verdict scoring four independent dimensions:

| Dimension | Signal |
|---|---|
| Unbacked thread | Thread start address outside all known modules |
| RWX + MEM_PRIVATE | Anomalous memory protection combination |
| Injected PE | MZ header in unregistered private memory |
| IOC strings | Known-bad patterns matched in region |

### Step 2: Extract Flagged Region for Static Analysis

```bash
# Extract raw bytes from a region flagged by --hunt injection or --report
python -m dumpex <DUMP> --extract 0x<ADDR> -o payload.bin

# If region size is unknown, dumpex auto-resolves from the memory map
python -m dumpex <DUMP> --extract 0x<ADDR> -o payload.bin
```

Post-extraction triage path:
- `MZ` header present → PE payload → submit to VirusTotal / pestudio / FLOSS for static analysis
- No `MZ` header → shellcode → run through scdbg or speakeasy for API call reconstruction
- High-entropy blob → likely encrypted stage → note for lateral correlation

### Step 3: String Extraction with IOC Filtering

```bash
# Extract strings from a specific region with regex filter
python -m dumpex <DUMP> --strings 0x<ADDR> --grep "http|cmd|pipe|\d{1,3}\.\d{1,3}"

# Unicode strings only (covers Windows API names, wide-char C2 configs)
python -m dumpex <DUMP> --strings 0x<ADDR> --encoding unicode --min-len 6
```

## Phase 4: Diff Analysis (Two Dumps)

*Compare two dumps of the same process captured at different points — useful when an EDR captures a before/after pair, or when comparing a suspicious process against a known-clean baseline.*

```bash
# Full diff — modules, threads, memory
python -m dumpex before.DMP --diff after.DMP

# Memory only — focus on protection changes and new RWX regions
python -m dumpex before.DMP --diff after.DMP --diff-mode memory --verbose

# Module diff — detect DLL injection between captures
python -m dumpex before.DMP --diff after.DMP --diff-mode modules
```

Key diff signals:

| Signal | Implication |
|---|---|
| New `RWX` region in after dump | Shellcode staged between captures |
| Module added, path in `\Temp\` | DLL injected after first capture |
| Protection changed to `RWX` | Existing region weaponised |
| New unbacked thread in after dump | Payload delivery occurred between captures |

## Phase 5: Structured Output for Reporting

```bash
# Full hunt with JSON output for evidence log
python -m dumpex <DUMP> --hunt all --verbose --json hunt_results.json

# Modules and threads as CSV for timeline reconstruction
python -m dumpex <DUMP> --modules --csv modules.csv
python -m dumpex <DUMP> --threads --csv threads.csv

# Plain-text copy of all output for chain of custody documentation
python -m dumpex <DUMP> --hunt all --verbose --txt report.txt

# Combine all output formats in one pass
python -m dumpex <DUMP> --hunt all --verbose \
  --json results.json \
  --csv ./output/ \
  --txt report.txt
```
