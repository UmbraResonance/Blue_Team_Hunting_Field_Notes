# Minidump Analysis (dumpex)

> **Focus:** Structured investigation of a Windows process minidump (`.dmp`) — establish the evidence boundary, then enter through either TTP-driven hunting (`--hunt`) or alert-driven analysis (`--report`) before preserving artifacts and pivoting into endpoint, network, and malware analysis.

> **Environment:** Windows / Linux · Python 3.10+ with Git, or the optional Windows x64 standalone release · [dumpex v3.5.1](https://github.com/bitbug0x55AA/dumpex/releases/tag/v3.5.1)

> **Pinned workflow baseline:** dumpex **v3.5.1**, source commit [`fc74bb35f74d701fb93af44e0add77d260340e7a`](https://github.com/bitbug0x55AA/dumpex/commit/fc74bb35f74d701fb93af44e0add77d260340e7a), JSON schema **v2.13** (reviewed 2026-08-27). The commands, output semantics, and disposition guidance in this workflow apply to that release. Later releases and the `main` branch are out of scope until this document is explicitly revalidated.

> **v3.5.1 boundary:** The 3.5.x line restructures the internal hunt analyzer registry and documentation while retaining the shipped seven-hunter public CLI and schema v2.13. This workflow documents only public v3.5.1 commands; it does not anticipate targeted-rescan capabilities or other extensions still under development.

> **Enter here when you have:** A process minidump plus either a broad TTP hypothesis, or an alert anchor such as a thread ID, virtual address, or IOC string. The dump may have been collected by EDR, Windows Error Reporting (WER), a crash handler, or an authorized use of `MiniDumpWriteDump`.

> **Pivot keys produced:** Process identity, module and thread addresses, suspicious memory regions, handle and named-pipe evidence, Beacon configuration fields, YARA matches, extracted artifacts, IOC strings, coverage gaps, and ATT&CK hypotheses.

> **Notation:** Replace `<DUMP>`, `<CASE_ID>`, `<ANALYST>`, `<ADDR>`, `<TID>`, and `<BASELINE_DUMP>` with case values. Examples use the `dumpex` entry point; `python -m dumpex` is equivalent. Exactly one primary command is required per invocation.

## Tool Positioning and Evidence Boundary

dumpex answers a narrow but valuable question: **what evidence was captured inside one process at one point in time?** It complements broader sources rather than replacing them.

| Evidence source | Primary question | Typical tools |
|---|---|---|
| Process minidump | What process, module, thread, handle, and captured-memory evidence exists inside this process? | dumpex |
| Full RAM image | What was present across processes and the kernel? | Volatility 3 / MemProcFS |
| Endpoint and event telemetry | What happened before and after the capture? | EDR / Sysmon / Windows events |
| Network telemetry | Did the host communicate with an extracted endpoint? | DNS / proxy / firewall / NDR |
| Binary and payload artifacts | What does the recovered code do? | YARA / FLOSS / disassembler / sandbox |

Use this workflow when a process `.dmp` is the best or only memory artifact, the alert is process-scoped, or two comparable dumps are available for change analysis.

### Two analysis entry points

After evidence profiling and process reconstruction, `--hunt` and `--report` are peer entry points that answer different investigative questions. Neither command is merely a prerequisite for the other.

| Entry point | Start here when | Primary question | Typical continuation |
|---|---|---|---|
| `--hunt` | You have a TTP hypothesis or need broad triage without a precise anchor | Does the captured evidence support injection, hollowing, stomping, pipe C2, Beacon, YARA, or obfuscation hypotheses? | Send suspicious addresses, TIDs, or IOC values into `--report` |
| `--report` | An EDR/Sysmon/threat-intelligence alert already supplies a TID, address, or string | What memory, module, thread, string, PE/header, verdict, and coverage context surrounds this alert? | Extract/review the region and, where warranted, run the relevant focused `--hunt` |

The relationship is bidirectional: `--hunt` discovers pivots that `--report` can explain in context, while an alert-first `--report` can identify which focused hunter should be run next. Because dumpex accepts exactly one primary command per invocation, each transition is a separate, separately preserved run.

### Non-negotiable interpretation rule

A minidump contains only the streams and bytes selected by its collector. Therefore:

- `DETECTED` with partial coverage is still a positive finding.
- `NOT_DETECTED_IN_SCANNED_SCOPE` is only a scoped non-detection.
- `INCONCLUSIVE` and `NOT_EVALUATED` must never be rewritten as “clean.”
- Missing bytes, streams, or context cannot be treated as evidence of absence.

## Phase 0: Prepare and Preserve

### Step 1: Install the Pinned Investigator Version

Choose the installation route that matches the analysis workstation:

| Workstation condition | Recommended route |
|---|---|
| Python 3.10+ and Git are already managed analyst dependencies | Isolated Python install from the pinned Git commit |
| Python/Git is unavailable, installation is prohibited, or a portable Windows tool is required | Official Windows x64 release bundle |

#### Option A — isolated `pip` install from Git (recommended when Python and Git are available)

This avoids a source checkout and avoids manually managing a release archive. It also lets `pip` install dumpex's validated Python dependencies and the optional YARA feature set. Always install into a dedicated virtual environment. For evidentiary reproducibility, the command below pins the immutable commit behind release `v3.5.1`; an unqualified Git URL would follow mutable repository state, while a tag is less strict because repository administrators can move it.

```bash
# Create and activate an isolated environment
python3 -m venv dumpex-v3.5.1-venv
source dumpex-v3.5.1-venv/bin/activate

# Install the full investigator feature set from the exact v3.5.1 commit
python -m pip install --upgrade pip
python -m pip install \
  "dumpex[full] @ git+https://github.com/bitbug0x55AA/dumpex.git@fc74bb35f74d701fb93af44e0add77d260340e7a"

# Verify the resolved package version
python -c "import dumpex; print(dumpex.__version__)"
# Expected: 3.5.1
```

For Windows Python, create the environment with `py -3 -m venv dumpex-v3.5.1-venv` and activate it with `.\dumpex-v3.5.1-venv\Scripts\Activate.ps1`. The installation exposes both `dumpex` and `python -m dumpex`.

> **Operational tradeoff:** The Git installation is convenient when Python and Git are already approved, but it is not dependency-free. Initial installation requires network access to GitHub and the Python package index unless dependencies are internally mirrored or cached. Preserve the resolved package inventory (`python -m pip freeze`) with the case or tool-validation record.

#### Option B — Windows x64 standalone release

Use the release bundle for a portable or offline Windows workflow. It does not require Python, Git, a source checkout, or Python dependency resolution.

1. Download [`dumpex-v3.5.1-windows-x64.zip`](https://github.com/bitbug0x55AA/dumpex/releases/download/v3.5.1/dumpex-v3.5.1-windows-x64.zip) and the official [`SHA256SUMS.txt`](https://github.com/bitbug0x55AA/dumpex/releases/download/v3.5.1/SHA256SUMS.txt).
2. Verify the bundle before extraction:

```powershell
Get-FileHash -LiteralPath .\dumpex-v3.5.1-windows-x64.zip -Algorithm SHA256

# Expected SHA-256:
# 40CF824013AD9F9C9ED3C272998654E5FD02C5821AA6C932613079644A3EA04E
```

3. Extract it into a versioned tool directory and verify the executable starts:

```powershell
Expand-Archive -LiteralPath .\dumpex-v3.5.1-windows-x64.zip `
  -DestinationPath .\dumpex-v3.5.1

.\dumpex-v3.5.1\dumpex.exe --help
```

The bundle includes `dumpex.exe`, output-schema files, build dependency inventory, source notice, and license material. Keep the bundle, checksum file, and extracted `SOURCE.txt` with the case tooling record. Later examples use `dumpex`; either add this versioned directory to the analyst session's `PATH` or replace `dumpex` with the full path to `dumpex.exe`.

> **Why not `pip install -e .`?** Editable installation is appropriate for development because execution remains linked to a mutable source checkout. It is not the default for an investigator who needs a stable, auditable tool version. Developers working on dumpex should follow the pinned release's [Contributing guide](https://github.com/bitbug0x55AA/dumpex/blob/v3.5.1/CONTRIBUTING.md) and keep that environment separate from casework.

Whichever route is used, record `v3.5.1`, commit `fc74bb35f74d701fb93af44e0add77d260340e7a`, the installation method, Python/dependency versions where applicable, and rules provenance in the case notes.

### Step 2: Protect the Source Evidence

- Work from a forensic copy; retain the original dump read-only.
- Store output outside the source-evidence directory where practical.
- Use a new output filename for every command. dumpex refuses input/output collisions and will not overwrite existing output unless `--force` is explicitly supplied.
- Treat JSON, transcripts, extracted strings, and environment data at the same sensitivity as the dump.

> **Privacy note:** `--redact-paths` reduces filesystem paths to basenames in JSON metadata only. It does **not** sanitize command lines, environment values, credentials, tokens, IOCs, or other memory content.

## Phase 1: Establish the Evidence Boundary

*Run coverage profiling before interpreting an empty inventory or a negative hunt result.*

### Step 1: Profile Captured Streams and Capabilities

```bash
dumpex <DUMP> --profile \
  --json profile.json \
  --case-id <CASE_ID> \
  --analyst <ANALYST>
```

`--profile` reports the raw stream directory, captured-memory facts, and six capability states:

- memory-region assessment;
- module assessment;
- injection-artifact assessment;
- thread assessment;
- handle assessment; and
- injector-handle assessment.

Each capability is `available`, `limited`, or `unavailable`. These are evidence-availability states, not malicious/clean verdicts. `--profile` may complete successfully even when downstream capabilities are unavailable because the required streams were never captured.

### Step 2: Record Dump and Host Identity

```bash
dumpex <DUMP> --sysinfo --json sysinfo.json
```

Record the dump filename, size, SHA-256, recoverable dump time, OS/build, architecture, hostname, CPU, and captured environment facts. Use `--sysinfo --verbose` only when environment values are operationally necessary; they may expose secrets or internal paths.

### Evidence-boundary decision

| Profile result | Disposition |
|---|---|
| Required capability `available` | Continue and interpret results within the reported scope |
| Capability `limited` | Continue, but record the limitation and plan targeted follow-up or recollection |
| Capability `unavailable` | Mark that analysis question as not evaluated; use endpoint/full-memory evidence or recollect |

## Phase 2: Reconstruct Process Context

### Step 1: Consolidated Process Identity

```bash
dumpex <DUMP> --process --verbose --json process.json
```

Review:

- PID, image name/path, command line, start time, and image base;
- which captured source supplied each identity claim;
- bounded IAT entries and their resolved targets;
- PEB/module identity verification states; and
- extended PEB fields shown by `--verbose`.

Correlate PID, image path, command line, start time, and process identity with Sysmon EID 1 or EDR process telemetry in [`3.2.03`](3.2.03_Process_Execution_Investigation.md).

> **Interpretation:** A PEB/module-list conflict is a lead requiring corroboration. It can support a hollowing or identity-masquerade hypothesis, but it is not independently proof of process hollowing. `BeingDebugged` is also contextual; legitimate debugging and analysis tooling can set it.

### Step 2: Handle Inventory

```bash
dumpex <DUMP> --handles --verbose --json handles.json
```

Use captured handle descriptors to identify named pipes and cross-process-relevant access. Interpret access rights according to the row's object type; a granted right shows capability, not proof that the process exercised it maliciously.

- `(unnamed)` means the captured descriptor has no name.
- `(unreadable)` means a name was expected but could not be recovered; this is a coverage gap.
- If `HandleDataStream` was not captured, handle analysis is `NOT_EVALUATED` rather than clean.

### Step 3: Memory, Module, and Thread Inventories

```bash
dumpex <DUMP> --list --json memory.json
dumpex <DUMP> --modules --json modules.json
dumpex <DUMP> --threads --json threads.json

# Fast projections for review; these are not detection verdicts
dumpex <DUMP> --list --filter PAGE_EXECUTE_READWRITE
dumpex <DUMP> --list --filter PAGE_EXECUTE
```

Correlate regions, modules, and threads rather than judging one field in isolation:

| Observation | Analyst interpretation |
|---|---|
| Executable `MEM_PRIVATE` or RWX region | Prioritize for review; JIT engines, packers, debuggers, and security products can create benign examples |
| Valid PE structure outside the registered module map | Stronger injection lead; validate structure and execution context |
| Thread instruction pointer in suspicious private memory | Execution context that strengthens an injection hypothesis |
| Unexpected module path or identity | Validate signer, hash, load context, and host telemetry |
| Missing or empty stream | Check `coverage.sources`; “not captured” and “captured but empty” are different states |

## Phase 3: Choose the Analysis Entry Point

After Phases 0–2, select the route that matches the evidence already in hand:

| Starting condition | Route |
|---|---|
| No precise alert anchor, or a broad TTP hypothesis | Continue below with **Path A: `--hunt`** |
| Known alert TID, virtual address, or IOC string | Go directly to **Phase 5: `--report`** |
| Both are available | Run both as independent commands and correlate their evidence references, addresses, TIDs, and coverage gaps |

### Path A: TTP-Driven Broad Triage (`--hunt`)

Use `--hunt` as the hypothesis-driven entry point. `--hunt all` provides broad triage; a focused hunter tests a narrower TTP hypothesis.

#### Step 1: Broad Hunt with Case-Ready Output

```bash
dumpex <DUMP> --hunt all --verbose \
  --json hunt.json \
  --txt hunt.txt \
  --case-id <CASE_ID> \
  --analyst <ANALYST>
```

`--hunt all` runs seven hunters in a fixed order:

1. `injection`
2. `hollowing`
3. `stomping`
4. `pipe`
5. `cs-beacon`
6. `yara`
7. `obfuscation`

`--verbose` changes console detail only. JSON already retains the full structured records, coverage, limitations, diagnostics, and provenance.

#### Step 2: Read Results in the Correct Order

For JSON, review:

1. `result.execution_status` and `diagnostics` — did the command itself complete?
2. `result.coverage.status` — was run-wide evidence complete, partial, or not evaluated?
3. `result.summary` — what is the overall hunt summary and follow-up queue?
4. `result.data.records[]` — what did each hunter detect, and with what coverage?
5. Each record's findings, facts, inference, confidence, limitations, and evidence references.

| Hunter `status` | Meaning | Required disposition |
|---|---|---|
| `DETECTED` | Eligible evidence supporting the hunter was found | Escalate and corroborate, even when coverage is partial |
| `NOT_DETECTED_IN_SCANNED_SCOPE` | No indicator was found in the examined scope | Record as a scoped non-detection only |
| `INCONCLUSIVE` | Some analysis ran but could not support a positive or clean scoped result | Resolve limitations or acquire better evidence |
| `NOT_EVALUATED` | Required evidence was absent or unusable | Record the question as not checked |

> **Automation warning:** Exit codes describe coverage, not detection: `0` = complete, `3` = partial, `4` = not evaluated. Never use exit code `0` as a “no detection” test; inspect `status` and `verdict_level`.

#### Step 3: Focused Hunters and Their Boundaries

```bash
dumpex <DUMP> --hunt injection --verbose --json injection.json
dumpex <DUMP> --hunt hollowing --verbose --json hollowing.json
dumpex <DUMP> --hunt pipe --verbose --json pipe.json
dumpex <DUMP> --hunt cs-beacon --verbose --json cs-beacon.json
dumpex <DUMP> --hunt obfuscation --verbose --json obfuscation.json
```

| Hunter | Stronger evidence | Important boundary |
|---|---|---|
| `injection` | Validated hidden PE plus executable private memory and thread execution context | RWX or `MZ` alone is not proof |
| `hollowing` | Correlated image-base, mapping, header, protection, and identity inconsistencies | One anomaly is a lead; missing PEB/module/memory evidence reduces coverage |
| `pipe` | OS-recorded pipe handle corroborated by content or execution context | A pipe-like string is an unscored lead; handle proof requires `HandleDataStream` |
| `cs-beacon` | Structurally valid decoded Beacon configuration plus memory/thread context | Config presence does not prove active callbacks or that every parsed endpoint was used |
| `obfuscation` | Confirmed Sleep Mask decode or structurally validated PE payload | Entropy, Base64-like content, and compression magic are benign-compatible leads |

##### Module stomping requires a trusted reference

```bash
dumpex <DUMP> --hunt stomping \
  --ref-dir <TRUSTED_SAME_BUILD_MODULE_DIR> \
  --verbose --json stomping.json
```

Without `--ref-dir`, scored content comparison cannot run and the result is `INCONCLUSIVE`, not clean. Reference DLL/EXE files must match architecture, `SizeOfImage`, timestamp, OS build, and patch level. Prefer binaries from the affected host or an authoritative matching image. Dumpex normalizes supported x86/x64 base relocations before comparison, but legitimate hotpatches, security hooks, and runtime changes can still modify code.

##### YARA uses packaged or analyst-controlled rules

```bash
# Packaged YARA rules (requires the full install)
dumpex <DUMP> --hunt yara --verbose --json yara-packaged.json

# Case-specific rules
dumpex <DUMP> --hunt yara --yara-dir <CASE_YARA_DIR> \
  --verbose --json yara-case.json
```

YARA scans only captured bytes using rules that compiled successfully. Preserve the rule directory with the case; JSON records rule-file hashes, aggregate hash, and compile provenance.

For case-specific TTP thresholds or patterns, use an explicit `--rules-file <FILE>`. A missing, unreadable, malformed, or unsupported override fails closed; dumpex does not silently fall back to a different ruleset.

## Phase 4: Close `--hunt` Coverage Gaps (Path A)

Review `coverage.reasons`, structured `coverage.limitations[]`, and, for `--hunt all`, `result.summary.investigation_actions`.

Common gaps include missing streams, short/unreadable data, oversized regions, exhausted scan budgets, YARA failures, and missing module-stomping references.

### Optional Deep Triage of Skipped Targets

```bash
dumpex <DUMP> --hunt all --triage-skipped \
  --verbose --json hunt-deep-triage.json
```

`--triage-skipped` performs bounded generic content checks against the skipped-target queue. It can surface IOC strings, network patterns, or PE headers, but:

- it does not rerun or replace the skipped hunter;
- it does not change the original hunter verdict, coverage, or exit code; and
- empty `content_reason_codes` means no generic indicator was found in the bytes actually examined, not that the target is clean.

For a limitation target:

- `file_offset` present — the captured range may be reportable or extractable;
- `file_offset: null` — the bytes are absent from this dump and require recollection.

The `CORRELATED REGIONS` console/`--txt` section means multiple hunters placed evidence in the same normalized region. It is a location correlation, not a new verdict or score.

## Phase 5: Alert-Driven and Hunt-Follow-Up Analysis (`--report`)

`--report` has two deliberate roles:

1. **Alert-driven entry point:** begin here when EDR, Sysmon, another forensic tool, or threat intelligence already supplies a TID, virtual address, or string. Running `--hunt` first is not required.
2. **Hunt follow-up:** use a suspicious address, thread, or IOC discovered by `--hunt` to examine its local memory and execution context in greater depth.

| Anchor source | Suitable report anchor | Purpose |
|---|---|---|
| EDR or thread-aware event | `--report-tid <TID>` | Validate the thread's captured region, module backing, protection, neighboring threads, and strings |
| EDR alert, instruction pointer, or hunter evidence reference | `--report-addr <ADDR>` | Build a region-centred triage card and optionally preserve the surrounding bytes |
| Threat-intelligence IOC, alert string, pipe name, command fragment, or hunter IOC value | `--report-string "<STRING>"` | Locate actionable private-memory occurrences and assess each surrounding region |

Prefer one anchor per invocation for clear provenance. When several anchors describe the same alert, preserve separate report runs and correlate their evidence rather than obscuring which anchor produced a card.

```bash
# Alert-driven entry: thread ID from thread-aware EDR telemetry or a remote-thread event
dumpex <DUMP> --report --report-tid <TID> --json report-tid.json

# Alert-driven or hunt follow-up: virtual address from EDR, a hunter, or an instruction pointer
dumpex <DUMP> --report --report-addr <ADDR> --json report-addr.json

# Alert-driven or hunt follow-up: exact IOC, pipe, command fragment, or tool marker
dumpex <DUMP> --report --report-string "<STRING>" --json report-string.json
```

> **TID caution:** A process ID from Sysmon EID 1 is not a thread ID. For Sysmon EID 8, validate which source/target thread field your data source exposes before using it as `<TID>`.

The report correlates the anchor with its memory region, module backing, protection, thread context, notable strings, PE/header context, verdict dimensions, and coverage. String mode creates a card for each actionable private-memory hit; module-backed hits remain summary context.

A string “not found” result is not clean when any region was unreadable, truncated, skipped, or scan-clamped.

### Select the Next Step from the Report

`--report` performs focused correlation and triage; it does not replace the TTP-specific validation logic in `--hunt`. Use the report's facts to decide whether a focused hunter is justified:

| Report evidence | Separate follow-up run |
|---|---|
| Executable private/RWX memory, unregistered PE context, or a thread executing in the region | `--hunt injection` |
| Image-base, mapping, header, protection, or PEB/module identity inconsistency | `--hunt hollowing` |
| Suspicious code inside a registered module | `--hunt stomping --ref-dir <TRUSTED_SAME_BUILD_MODULE_DIR>` |
| Pipe syntax or framework-like pipe string | `--hunt pipe` |
| Beacon-like configuration material | `--hunt cs-beacon` |
| Encoded, compressed, or high-entropy content | `--hunt obfuscation` |
| Content matching a case hypothesis | `--hunt yara --yara-dir <CASE_YARA_DIR>` |

Conversely, when `--hunt` is the entry point, select the most actionable `base_address`, thread identifier, or IOC value from its structured findings and feed that value into the matching report anchor. Preserve both JSON results so the broad/focused evidence chain remains reproducible.

## Phase 6: Extract and Preserve Artifacts

### Step 1: Extract Captured Bytes

```bash
# Extract a specific captured range
dumpex <DUMP> --extract <ADDR> --size 0x1000 \
  --output region.bin --json extract.json

# Extract the captured region around a report anchor
dumpex <DUMP> --report --report-addr <ADDR> \
  --output report-region.bin --json report-extract.json
```

Without `--output`, `--extract` creates `region_0x<address>.bin`. A short captured range may still be written and reported with partial coverage. Record the source virtual address, requested size, bytes recovered, output SHA-256, and associated JSON.

Suggested handoff:

| Recovered content | Next analysis |
|---|---|
| Valid PE structure | Hashing, signature review, YARA, FLOSS, PE inspection, disassembly, sandboxing |
| Raw shellcode or non-PE executable bytes | Disassembly/emulation in an isolated malware-analysis environment |
| Encoded or high-entropy blob | Determine container/encoding, attempt controlled decoding, correlate with neighboring evidence |
| Configuration or strings | Validate syntax and pivot into DNS, proxy, firewall, EDR, and threat-intelligence data |

Do not upload proprietary or sensitive memory artifacts to public services without authorization.

### Step 2: Targeted String Review

```bash
dumpex <DUMP> --strings <ADDR> --size 0x1000 \
  --min-len 8 \
  --strings-encoding both \
  --grep '(?i)https?://|powershell|cmd\.exe|pipe'
```

`--strings-encoding` accepts `ascii`, `unicode`, or `both`. The older hidden `--encoding` alias remains for compatibility, but new documentation and scripts should use `--strings-encoding`.

## Phase 7: Compare Two Dumps

*Use only when the target and reference captures are meaningfully comparable.*

```bash
# Positional dump = target/suspect; --diff argument = baseline/reference
dumpex suspect.dmp --diff <BASELINE_DUMP> \
  --diff-scope all --verbose --json diff-all.json

dumpex suspect.dmp --diff <BASELINE_DUMP> \
  --diff-scope memory --verbose --json diff-memory.json

dumpex suspect.dmp --diff <BASELINE_DUMP> \
  --diff-scope modules --verbose --json diff-modules.json
```

`--diff-scope` accepts `modules`, `threads`, `memory`, or `all`. The older hidden `--diff-mode` alias remains accepted, but new usage should prefer `--diff-scope`.

“Added,” “new,” and “changed to” describe the positional target relative to the baseline. A difference is an observation, not automatically malicious. Validate capture time, process identity, architecture, collection method, and expected process lifecycle before drawing conclusions.

| Difference | Investigation action |
|---|---|
| New executable private/RWX region | Run focused injection/report analysis on the target address |
| New thread in an unbacked or suspicious region | Correlate the thread and address with EDR/Sysmon injection telemetry |
| New or changed module | Validate path, signer, hash, load time, build identity, and reference provenance |
| Protection change | Determine whether JIT/runtime behavior explains it; correlate with thread execution and content |

## Phase 8: Reporting and Cross-Telemetry Pivots

### Case-Ready Output

```bash
dumpex <DUMP> --hunt all --verbose \
  --json result.json \
  --txt transcript.txt \
  --case-id <CASE_ID> \
  --analyst <ANALYST>
```

JSON is the canonical structured format; `--txt` is an ANSI-free human transcript. Current dumpex no longer supports `--csv`.

Record findings and recovered artifacts in [`7.2_Evidence_Artifact_Log`](../../07_Reporting_Templates/7.2_Evidence_Artifact_Log.csv).

| Finding | Pivot |
|---|---|
| Process identity or PEB/module conflict | [`3.2.03`](3.2.03_Process_Execution_Investigation.md) — process ancestry, command line, signer, hashes, and timeline |
| C2 host, URI, port, or User-Agent from Beacon/config strings | [`3.2.04`](3.2.04_Network_C2_Investigation.md) — scope DNS, proxy, firewall, and EDR network evidence |
| Named pipe | Sysmon EID 17/18 and EDR handle telemetry; identify creator/client processes and host scope |
| Suspicious thread or memory address | [`3.2.03`](3.2.03_Process_Execution_Investigation.md) — correlate injection telemetry and process chain |
| Injected PE or shellcode extracted | Static/dynamic malware analysis; hash and preserve the artifact before analysis |
| YARA match | Validate rule quality, namespace, matched offsets/strings, memory context, and rules provenance |
| Coverage gap | Recollect a richer minidump or full RAM image; pivot to endpoint telemetry |
| Full-memory corroboration required | [`3.2.01`](3.2.01_Memory_Forensics.md) |

### Suggested ATT&CK hypotheses

| Hunter | Primary hypothesis |
|---|---|
| `injection` | T1055 Process Injection |
| `hollowing` | T1055.012 Process Hollowing |
| `stomping` | T1055.013 per dumpex's current methodology; report the exact observed behavior and evidence |
| `pipe` | T1090 Proxy and T1071 Application Layer Protocol, depending on corroborated use |
| `cs-beacon` | T1071 Application Layer Protocol / T1219 Remote Access Software context |
| `yara` | Depends on the matched rule and validated behavior |
| `obfuscation` | T1027 Obfuscated/Compressed Files and Information |

ATT&CK mappings describe the behavior a hunter is designed to surface; they do not prove the technique occurred. Prefer the mapping emitted with the finding and document the supporting facts.

## Analytical QA (Self-Check)

- **[ ] Evidence identity:** Did I preserve the original dump and record its SHA-256, size, recoverable time, host, OS/build, architecture, tool version, and case metadata?
- **[ ] Version control:** Did I use the pinned dumpex v3.5.1 baseline, verify the Python package version or Windows bundle SHA-256, and avoid silently substituting `main` or a later release?
- **[ ] Evidence boundary:** Did I run `--profile` and distinguish `available`, `limited`, and `unavailable` capabilities?
- **[ ] Process context:** Did I correlate `--process`, `--handles`, regions, modules, and threads with endpoint telemetry?
- **[ ] Result semantics:** Did I keep `execution_status`, hunter `status`, `coverage.status`, `verdict_level`, and `confidence` separate?
- **[ ] Negative claims:** Did I avoid translating `INCONCLUSIVE`, `NOT_EVALUATED`, partial coverage, or uncaptured data into “clean”?
- **[ ] Stomping references:** If I used `--ref-dir`, are the reference binaries trusted and matched to architecture/build/patch level?
- **[ ] Rule provenance:** Did I preserve explicit TTP/YARA rules and verify their hashes/compile status in JSON?
- **[ ] Entry point:** Did I record whether the investigation began TTP-first with `--hunt`, alert-first with `--report`, or used both independently?
- **[ ] Focused triage:** For an alert-first case, did I run `--report` directly on the supplied anchor? For hunt findings, did I send the highest-priority TID, address, or IOC into `--report` and record all scan limitations?
- **[ ] Artifact handling:** Did I hash extracted bytes, retain source address/size, avoid unauthorized public uploads, and log chain of custody?
- **[ ] Cross-telemetry pivots:** Did I validate process, pipe, C2, and thread leads against Sysmon/EDR/network/full-memory evidence?
- **[ ] Reporting:** Did I separate confirmed findings, analyst leads, scoped non-detections, and coverage gaps?
